### Added

- **Rust: range indexes — `GraphDb::enable_range_index(name, label, field)`, `disable_range_index(name)` and `range_indexes()` — refused until the V11 format lands.** A range index on `(label, field)` keeps the field's values sorted, so the storage layer answers `<`, `<=`, `>`, `>=`, closed ranges and `STARTS WITH` as well as exact matches (`UnifiedIndex::lookup_range`, `lookup_prefix`, `lookup_eq`; `PropertyIndex` is now another name for `UnifiedIndex`). Every lookup answers exactly as a scan of the same comparison does: integers and floats compare as one numeric class (`2 = 2.0`, by `f64` total order for `<`), `Bool` values are not ordered, and two `DateTime`s at one instant are equal but ordered by offset. Existing nodes are indexed when the index is declared, and the index is rebuilt from the stored values at every open. It shares its entries with an equality index on the same pair: dropping the range index keeps an equality index or a unique constraint's index, and `disable_index` refuses a pair that only a range index covers. A range index cannot cover a property a view owns: `enable_range_index` refuses one, and `create_view` refuses a property a range index covers. Cypher reads a range index for exact matches (`MATCH (n:L {f: $x})`, `WHERE n.f = $x`), as it reads an equality index; it does not use one for ranges or `STARTS WITH` yet. The declaration is a new WAL record that 0.9.x cannot read, so until the V11 format lands `enable_range_index` fails with `not supported in mushroomdb 0.10 yet: range indexes cannot be declared until the V11 format lands` and the store is unchanged.

### Fixed

- **An equality index no longer changes a query's answer for numbers (ledger row 125).** `= 2` through an index on the property found nodes holding the integer 2 but not those holding the float 2.0, and `= 0` missed `-0.0`, where the same query without the index found both. Index lookups now treat integers and floats as one numeric class, as the scan always has.
