### Added
- **A node needs neither an `id` nor a label, and `CREATE` takes several patterns.** `CREATE ()`, `CREATE (:Person {name: 'Ada'})`, `CREATE ({name: 'Ada'})`, `CREATE (a:A), (b:B), (a)-[:R]->(b)`, `CREATE ()-[:K]->()` and several `CREATE` clauses in one statement now run, auto-commit and inside a transaction, over HTTP, Bolt, Python, TypeScript and MCP. A string `id` is still the key, exactly as before (a duplicate is `DuplicateKey`, `MERGE` upserts by it, agent memory is unchanged). A node without one gets a generated key, `_:` followed by 32 lowercase hex digits: random, never a live key, written to the log with the node, so a reopen, a snapshot, `open_at`, a backup and an export give the same key back. A node without a label is stored under the empty label: `MATCH (n)` finds it, `MATCH (n:L)` does not, `labels(n)` is `[]`, `n.label` is null, Bolt sends an empty `labels` list and `CALL db.labels()` leaves it out; a role scoped to labels neither sees nor creates one. An `id` that is not a string (`{id: 1}`) is an ordinary property, and `MATCH (n {id: 1})` finds it. No format change: a generated key is a key and the empty label is a label, so 0.9.x reads such a store. `MERGE` patterns that are not a key MERGE (no label, no property, several properties, a non-string value) match by label and properties as openCypher does, bind every match, and create with a generated key when nothing matches; a key MERGE (a label and one string property) is unchanged. The JSONL and CSV imports take an empty label, and the Cypher export writes `MERGE (n {id: …})` for a node with no label. `mushroomdb::is_generated_key` and `GENERATED_KEY_PREFIX` are public. The openCypher TCK pass rate rises from 60.2% to 72.2%. (QL-NM)
- **A node stored under the empty label now reads as having no label.** A node an earlier release let `remember` or `insert_node("")` write under the empty label now reads `labels(n) = []` and `n.label = null`, where it read `[""]` and `""`. (QL-NM)
