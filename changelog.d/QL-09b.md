### Added
- **Cypher clauses after `UNWIND`.** `UNWIND $rows AS r CREATE (:Person {id: r.id, name: r.name})` is the bulk-load idiom, and it works with `MERGE` (node and relationship forms, `ON CREATE SET` / `ON MATCH SET`), `MATCH … SET` (including `SET n += r`), `REMOVE`, `DELETE` and `DETACH DELETE`. The writes run row by row and commit as one atomic batch (one WAL frame): a failure on any row writes nothing, and a write reads what the statement has written so far. `UNWIND [1, 1] AS x MATCH (n:C {id: 'c'}) SET n.count = n.count + 1` adds two, `SET n.v = 10 SET n.w = n.v` sets `w` to 10, `UNWIND ['a', 'a'] AS k MERGE (n:C {id: k}) ON CREATE SET n.count = 1 ON MATCH SET n.count = n.count + 1` counts each key, and `UNWIND [1, 1] AS x MERGE (:N {id: x})` creates one node. The `MATCH`, `WITH` and `WHERE` still run once, before the writes, so the rows do not change as the writes go. A `RETURN` after the writes returns one row per row written, with the committed values, even when the write changes what the `MATCH` filtered on. 10,000 `CREATE` rows take about as long as `ingest`. Reads after `UNWIND` work too: `UNWIND $ids AS id MATCH (n {id: id}) RETURN n`, and a map element is read with `r.id`. Not in an interactive transaction (refused by name); a read clause after a write clause is refused by name. (QL-09b).

### Fixed
- **A plain `MATCH … SET` read a property from before the statement, not from its own earlier writes.** `MATCH (n:C {id: 'c'}), (m:D) SET n.count = n.count + 1` added 1 however many `D` rows matched, and `SET n.v = 10, n.w = n.v + 0` set `w` to the old `v`. Each value is now read as its row is written (the count goes up once per row, `w` is 10), in both `SET n.f = expr` and `SET n += {…}`. A statement that matches each node once is unchanged. (QL-09b).
