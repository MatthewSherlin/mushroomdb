### Fixed
- **A pattern could use one relationship twice, and separate MATCH clauses could not share one.** Within one `MATCH` clause no relationship is now bound twice, across fixed and variable-length hops and across comma-separated parts: `MATCH (a)<-[*1..1]-(b)-[:X]->(c)` over a single `X` edge returned a row that walked that edge back and then forward again, and a named path over it listed the relationship twice. Separate clauses no longer share the rule: `MATCH (a)-[r]->(b) MATCH (c)-[s]->(d)` over one edge returned nothing where it should return one row, and an `OPTIONAL MATCH` could not bind an edge the `MATCH` before it had bound. A relationship variable an earlier clause bound now matches that same relationship in a later clause instead of being bound again to every other edge. Naming one relationship variable for two hops of one `MATCH` (`MATCH (a)-[r]->(b)-[r]->(c)`) is now a named error instead of a pattern that never matches. Writes driven by such a MATCH used the same wrong rows: on 0.9.x, over `a -> b -> c -> d`, `MATCH (s {id: 'b'})<-[*1..2]-(x)-[:R]->(y) DETACH DELETE y` deleted `b`. Present in released 0.9.x (ledger row 134).
