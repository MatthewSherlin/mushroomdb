### Added
- **Cypher `SET n = {…}` and `SET n += {…}`.** `MATCH … SET n += {k: v, …}` sets the listed properties and leaves the rest (a `null` value removes that property); `SET n = {…}` replaces the node's user properties with exactly the map. Both go through the ordinary write path in one WAL frame, so rules re-evaluate every set and removal and unique constraints apply. `id`, `ns` and view-owned properties are never removed by `=`; a map that changes `id` or `ns`, or names a view-owned property, is refused. Map values may be expressions and `$parameters`; the map is a literal or a `$parameter` holding a map, and a parameter that is not a map is an error. `MERGE … SET n = {…}` is refused by name. Inside an interactive transaction the map forms are refused by name. (QL-06).

#### BREAKING
- **On a node whose `id` property equals its key, setting `id` to another value and removing `id` are refused; use the rename API to change a key.** `id` mirrors the node's key (what `CREATE` and the default ingest produce), and a write that gave such a node a different `id` used to change the property without renaming the key, so the two diverged (ledger row 128). The engine now refuses it on every API, not only Cypher: `set_prop`, `set_props`, batches, compare-and-set, upsert, HTTP `PUT`/`DELETE /node/{key}/prop/id`, the Python binding, and Cypher `SET`/`REMOVE`/`MERGE`. Writing the node's own key is accepted. A node whose `id` differs from its key, or that has none, is not covered, so ingest and CSV import with another `key_field` and an unrelated `id` column keep working. `rename_node` (Rust, Python, MCP) renames the key and moves a matching `id` with it. (QL-06).
