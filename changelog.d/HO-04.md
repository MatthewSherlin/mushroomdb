### Added
- **Access keys: `keys.json` beside the store, holding hashes, with `mushroomdb keys add`.** Each key gives a token a tier. `admin` is full access. `write` may read and mutate but is refused `/backup`, `/stats`, `/metrics`, `/watch` and `/subscribe`. `read` with a `role` is that role's masked view and never writes, even when the role has a write scope. `mushroomdb keys add <db-dir> <name> --tier admin|write|read [--role R]` prints a random 32-byte token once and stores only its blake3 hash, in a file created mode 0600; `mushroomdb keys hash` hashes a token you already have. Tokens must be at least 32 bytes. `serve` refuses a `keys.json` that group or others can read or that another account owns (Unix only; Windows has no check), one with a plaintext `token`, one that does not parse, and a token configured both as a key and as `--token`, `MUSHROOMDB_TOKEN` or a role token. Keys work on HTTP and as Bolt `HELLO` credentials with the same tiers, and add to `MUSHROOMDB_TOKEN` and `MUSHROOMDB_ROLE_TOKENS`. SIGHUP re-reads the file without a restart, picks up a `keys.json` created after the start, and is a logged no-op with none (on Unix; the server always handles it); a bad file keeps the old keys on reload, and removing every key locks the server rather than opening it. New library API: `mushroomdb::AccessKeys`, `hash_token`, `add_key`, `server::router_with_access_keys`, `server::watch_sighup`. (HO-04).
