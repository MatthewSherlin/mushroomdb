### Added
- **Relationships carry properties written from Cypher.** `CREATE (a)-[:KNOWS {since: 2019}]->(b)` and `-[:T $props]->` store a map on the relationship, and `MERGE (a)-[r:T {k: v}]->(b)` matches the pair and then its map. `SET r.p = v`, `SET r += map`, `SET r = map` and `REMOVE r.p` write them, auto-commit and inside a transaction, counted in `properties_set` (a `CREATE` or `MERGE` map is part of the creation and is not, as a created node's properties are not; the driver counters, Bolt `properties-set`, do count it). A relationship is identified by its type, start and end node, so it has one property map: a `CREATE` with a map on a pair that already has its relationship, or a `MERGE` whose map differs from it, is refused with `a relationship between these nodes with this type already exists; use MERGE … SET to change its properties`; a `CREATE` without a map keeps the multiplicity behaviour. `count` stays reserved (writes refused by name, reads work), and a rule-owned edge type takes no user property write. The properties live where a rule's weights already did (the edge-property overlay and snapshot section 5) and reach the WAL as two new V11 records, `SetEdgePropId` (28) and `RemoveEdgePropId` (29): the first one moves a store to V11, so 0.9.x refuses it by name. Role scopes gain `update_edge_types` for writing an existing relationship's properties; creating one with its map needs only `create_edge_types`. New `BatchOp::SetEdgeProp` / `BatchOp::RemoveEdgeProp`. Not carried by the JSONL export or the CSV import yet, and announced on no `/watch` or `/subscribe` stream yet. (QL-RP)
