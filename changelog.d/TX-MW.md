### Added
- **Every write statement runs inside a transaction, with the results and counts it gives auto-commit.** `MATCH (a {id: $a}), (b {id: $b}) CREATE (a)-[:K]->(b)`, `MATCH … MERGE`, `UNWIND … <write>` (such as `UNWIND $rows AS r MATCH … CREATE …`), the `SET n = {…}` / `SET n += {…}` map forms and `SET` / `REMOVE … RETURN` now run inside `SharedDb::begin_transaction`, HTTP `/tx` and Bolt `BEGIN` … `COMMIT`, so a driver's managed write transaction (`session.execute_write` and the like) runs them. They read the transaction's own earlier writes, and what they write stays private to it until `COMMIT`; `ROLLBACK` leaves nothing. They compute their writes through the same code as auto-commit, so a value that reads a property sees the statement's own earlier rows exactly as it does there. Such a statement conflicts on every node it read, as a plain read does: if another writer changes a node its `MATCH` bound or filtered on (named or not) before `COMMIT`, the commit fails with `CasConflict`. Commit-time checks still apply: two transactions that connect the same pair conflict (the second commit fails with `CasConflict` and writes nothing), and constraints are checked at `COMMIT`. Schema statements are still refused inside a transaction, and a role-bound or `read` transaction still cannot write. (TX-MW)
### Fixed
- **The commonest driver write failed inside a transaction.** Inside a transaction (Rust, HTTP `/tx`, Bolt `BEGIN`) `MATCH … CREATE`, `MATCH … MERGE`, `UNWIND … <write>`, the `SET` map forms and `SET` / `REMOVE … RETURN` were refused with `not supported in mushroomdb 0.10 inside a transaction: …`, so "find two nodes, connect them" failed in a driver's managed write transaction; only an auto-commit `RUN` worked. Introduced in 0.10, never released (ledger row 144). (TX-MW)
- **`MATCH … SET` inside a transaction read the state before the statement.** Rows that matched one node, or a later item of the same `SET`, did not see the statement's earlier writes: `MATCH (n {id: 'a'}), (m:Person) SET n.v = n.v + 1` over four rows added 1 instead of 4, and `SET n.v = 10, n.w = n.v + 0` set `w` from the old `v`. Auto-commit was right. Introduced in 0.10, never released (ledger row 145). (TX-MW)
- **`MATCH … DETACH DELETE` inside a transaction counted an edge between two deleted nodes twice.** The `deleted` count now matches auto-commit's. Introduced in 0.10, never released (ledger row 146). (TX-MW)
- **`DETACH DELETE` counted a self-loop as two deleted relationships.** `MATCH (n {id: 's'}) DETACH DELETE n` on a node with a self-loop reported the loop twice in `deleted` (once from each end), and `delete_node`'s `DeleteReport.manual_edges` did too. A self-loop is one relationship, auto-commit and inside a transaction alike. Counter only; the data was always correct. Present since 0.9.x (checked against v0.9.2, ledger row 147). (TX-MW)
