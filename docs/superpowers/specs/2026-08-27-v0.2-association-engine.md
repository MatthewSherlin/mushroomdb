# Spec: v0.2 — the association engine (trust, physics, agent-default)

Date: 2026-08-27. Direction approved by Matthew ("association engine for apps
and AI agents"; three tracks; make it a beast). Research basis:
`.superpowers/research/2026-08-27-v02-research-digest.md` (KuzuDB archived
2025-10; LlamaIndex Kuzu slot orphaned; Zep's temporal moat; rkyv 0.8 +
read-only-mmap prior art from redb/LMDB; agent-discoverability checklist).

## 1. Strategic goal

Own the empty throne: THE embedded, MIT-licensed, Rust-native association/graph
engine — and the default choice an AI coding agent makes when asked for graph,
association, or agent-memory storage. Every phase below serves one of three
tracks: **Trust** (nobody parks data in a db that can't upgrade its files),
**Physics** (open fast, read concurrently, stay honest about numbers), and
**Agent-default** (be discoverable, integrable, and better at memory than the
server-bound incumbents).

## 2. Phases and gates

```
Phase A  Trust: migration + format promise   ──► gate GA
Phase B  Physics: mmap zero-copy + MVCC      ──► gate GB   (needs GA)
Phase C  Agent-default: temporal + reach     ──► gate GC   (C1 needs nothing; C2 after GA)
```

### Phase A — migration framework + format promise

- A1. Versioned migration on open: a V5/V6/V7 store opens under v0.2 via an
  explicit migrate step — either automatic (`open` migrates forward, writing a
  new-format snapshot after a successful load) or `mushroomdb migrate <dir>`
  CLI (both; auto-migrate is opt-out via open option). Migration NEVER mutates
  the original files until the new snapshot is fully fsynced (write-new,
  rename-swap, keep `.bak` until first clean open).
- A2. Format promise document (`docs/format-stability.md`): from v0.2, snapshot
  and WAL formats evolve append-only within a minor series; any break bumps the
  major format version and ships with a migrator; minimum-supported-format
  policy stated (v0.2 reads V5+). This document is the trust contract — README
  links it.
- A3. Benchmarks in CI: the criterion suite plus the 100k reopen bench run on a
  fixed runner class, publishing numbers to `benchmarks/results/` per release;
  regression thresholds fail CI (>15% on pinned headline metrics). Honesty
  rules apply: policy-matched cells, no silent corrections.

**Gate GA:** a real v0.1-era store (the 2.2 GiB dogfood artifact) migrates via
both paths; goldens for V5/V6/V7 still open; format promise doc merged;
benchmarks job green on two consecutive runs.

### Phase B — storage physics: zero-copy open + MVCC readers

- B1. **V8 mapped snapshot format** (the headline): rkyv 0.8-archived,
  little-endian-pinned, `#[repr(C)]` sections — packed CSR topology, columnar
  properties with RAW typed columns (embeddings stored as contiguous f64
  slices, NOT `Value`-boxed), intern/id tables, HNSW graphs, rule/provenance
  meta. Read path: read-only `memmap2` map of the whole file; hot metadata in
  the first page; per-section checksums validated lazily on first touch (never
  whole-file at open); OS page-cache does eviction. Write path unchanged:
  mutations via the existing WAL (write+fsync, never a writable mmap);
  `snapshot()` writes a new V8 file and rename-swaps.
  - Mutation model: mapped base + in-memory overlay (the current live
    structures become the overlay for post-snapshot writes); `open` = map V8 +
    replay WAL tail into overlay. Reads consult overlay-then-base.
  - No new heavyweight deps beyond `rkyv` and `memmap2` (both sanctioned by
    this spec; pre-approved by the research recommendation — Matthew vetoes on
    review if he disagrees).
- B2. **Value unboxing for vectors**: `f64`-list properties detected at column
  level are stored and served as raw slices end-to-end (`&[f64]` API for the
  ANN path); the `Value::List` adapter is built lazily only when a caller asks
  for the boxed form. Kills the 10 GiB-RSS-at-100k problem at its root.
- B3. **MVCC snapshot readers**: concurrent readers on an immutable view while
  the single writer proceeds (redb/LMDB model: readers pin an epoch; the
  overlay uses persistent/append-only structures or a cheap copy-on-write at
  commit granularity). Server drops the global RwLock read-blocking on write.
- B4. Differential (non-re-run) `subscribe_query` is explicitly OUT of v0.2 —
  wait-list for v0.3; the re-run implementation stands.

**Gate GB (measured on the 2.2 GiB / 100k dogfood store, recorded in
`dogfood/results/scale-100k.md`):**
- Open-to-first-query **< 100 ms** (cold file cache may add page-fault time on
  first touched pages; the gate is measured warm-file/cold-process, and the
  cold-cache number is reported alongside honestly).
- Process RSS after open + Big-3 query slice **< 500 MiB** (vs ~10 GiB today).
- Full workspace + DST green; WAL replay identity holds over the V8 base;
  crash-window sweep covers snapshot rename-swap.
- N=8 concurrent readers sustain reads during a write burst with p95 read
  latency < 2x single-reader baseline.

### Phase C — agent-default: temporal truth + reach

- C1. **Temporal edge lifecycle** (the Zep-class capability, natively):
  - Derived-edge retractions become first-class history: rule retractions and
    manual edge deletes are already WAL-visible — expose
    `edge_history(a, b) -> Vec<{edge_type, commit, event: Added|Retracted, rule}>`
    and `was_linked(a, b, edge_type, at_commit) -> bool` on the same WAL-scan
    machinery as `node_history` (same horizon contract, same honesty).
  - Optional per-edge validity: `insert_edge_valid(edge_type, src, dst,
    valid_until: Option<commit-or-timestamp>)` deferred UNLESS trivially cheap —
    v0.2 ships the history/as-of read side; write-side validity intervals are
    v0.3 wait-list. (Zep's benchmark win is temporal *reasoning* over
    invalidation; our retraction history + as-of gives agents the same
    primitive without a server.)
  - MCP exposure: `node_history` and `edge_history` become MCP tools.
- C2. **Integration packages** (each its own repo-dir or package, thin):
  - `llama-index-graph-stores-mushroomdb` (PyPI): implements
    `PropertyGraphStore` over the Python binding — fills the orphaned Kuzu
    slot; PR to llamaindex hub.
  - LangChain `GraphStore` implementation (`get_schema`,
    `get_structured_schema`, `query`, `refresh_schema`,
    `add_graph_documents`) published for langchain-community.
- C3. **Discoverability checklist** (mechanical, all required):
  - `/llms.txt` + `/llms-full.txt` served from the docs domain (llms.txt
    already in-repo; llms-full generated from docs/site).
  - MCP server submitted to: official `modelcontextprotocol/registry`,
    mcp.so, Smithery, Glama.ai, PulseMCP.
  - crates.io/PyPI/npm metadata: keywords `graph, embedded, database, mcp,
    agent-memory, hnsw, association`; one-command working example atop each
    README.
- C4. **Stretch (not gating):** run LongMemEval with a thin mushroomdb-backed
  memory adapter and publish the number whatever it is — honesty rules; a
  mediocre first score with a public methodology beats no score.

**Gate GC:** edge_history/was_linked tested incl. horizon + retraction cases
and exposed via MCP; both integration packages import-tested against their
frameworks' current releases; all five registry listings live; llms-full.txt
served; keywords shipped on all registries.

## 3. Explicit non-goals (v0.2 wait-list)

- Differential dataflow subscriptions; multi-writer; clustering/replication.
- Write-side edge validity intervals (C1 note), entity-extraction pipelines
  (cognee's lane — we are the substrate, not the ETL).
- Multi-label nodes, relationship properties on CREATE, `MATCH *1..n` beyond
  current subset — reconsider for v0.3 with KuzuDB-refugee feedback.
- WASM, GQL, DataFrame API (arrow-bridge already covers columnar egress).

## 4. Honesty overlay (standing)

Every performance claim in README/docs cites a measured number with date and
methodology link. The GB gate numbers replace, not join, the old cold-start
table. If a gate is missed, the miss is recorded in dogfood/results and the
README states the real number — exactly as done for G3.

## 5. Addendum (2026-08-27, from Linkt standup): write concurrency + RBAC

### B3.5 — Group-commit write queue (Phase B, after B3)

MVCC readers fix read blocking; N concurrent writers still serialize with one
fsync each. Add a write-submission queue: concurrent callers enqueue
mutations (server handlers and an embedded `GraphDb::submit` variant), the
single writer drains a batch, applies, and commits the group under ONE fsync
(Batched-policy semantics per group; Strict = fsync per group, documented).
Ordering: FIFO per connection; results delivered per submission.
**Gate:** 8 concurrent writers sustain >= 3x the serialized-writer
throughput at Strict fsync on the CI-bench store shape (measured, recorded).
Scope guard: NOT interactive transactions — `write_batch` stays the atomic
unit; BEGIN/COMMIT remains wait-listed.

### v0.3 candidate — RBAC over masks (agent-default track)

Node masks (0.1.2) are the primitive. The layer: named roles declared in
schema-as-code (`Schema.roles: role -> mask definition` — explicit key sets
and/or label/predicate selectors materialized per query), server tokens bound
to a role (token config gains an optional role), MCP/HTTP query paths resolve
token -> role -> mask automatically. Differentiator: most graph stores have
no per-query visibility story at all. Not gated in v0.2; spec'd here so the
design conversation is on the record.
