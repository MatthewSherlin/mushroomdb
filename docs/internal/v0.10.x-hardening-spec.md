# 0.10.x hardening: find wrong answers before a user does

Status: accepted by the owner, 2026-10-28. Applies to the 0.10.x patch line.

Progress (2026-10-29): H-1, H-2, H-4 and H-5 are merged and run nightly
(`.github/workflows/nightly-hardening.yml`); H-3 is not started. The open
questions below were answered with their recommendations: the nightly run
files GitHub issues, and the bar is fourteen consecutive clean nights.

## Why

Silent wrong answers keep reaching released versions. Row 139 (a filtered scan with
LIMIT missed every node the snapshot held) was present from 0.2.0 to 0.9.2. Rows 157, 158
and 160 (aggregates over a variable, integer sums, boolean comparison) were in every
0.9.x. Rows 103, 107, 111, 113 and 154 were rule-engine state that went wrong only after
a snapshot. Each was found by a person or a reviewer reading code, then fixed with a
targeted test.

Two shapes cover almost all of them:

1. **The same logical graph answers differently depending on its physical state** —
   live overlay versus snapshot base, reopened versus never closed, `open_at` versus live,
   a reader versus the writer, a fused scan versus the general path. Rows 139, 103,
   107–113, 116 and 154 are this shape.
2. **A Cypher construct computes the wrong value** in a case no hand-written test named.
   Rows 129, 131, 132, 133, 157, 158 and 160 are this shape.

The existing randomized tests do not reach either shape for Cypher.
`sim-harness/tests/oracle_equivalence.rs` checks the storage and rule engine against
`Oracle`, and `query_equivalence.rs` checks 1-hop `MATCH` against `neighbors`.
`index_matches_scan.rs` checks one index against one scan. `parser_fuzz.rs` checks only
that the parser does not panic. Nothing generates a Cypher query with WHERE, aggregates,
ORDER BY or LIMIT and checks its answer.

## Goal

The 0.10.x line ships no new features. It adds generated tests that would have caught
every row listed above, fixes what they find, and runs them nightly. 0.10.x is ready for
a public launch when the exit criteria at the end hold.

## Workstreams

### H-1 Same graph, every physical state (highest yield, build first)

A generator produces an operation sequence (nodes, edges, property sets and removals,
deletes, rule and index declarations, snapshots) and a set of queries. Each query runs
against the same logical graph held in each of these states, and every answer must be
equal:

| State | How it is reached |
|---|---|
| live, never snapshotted | apply the sequence |
| snapshot base + overlay | snapshot at a random point in the sequence, keep writing |
| reopened | close and open the store after the sequence |
| WAL-only reopen | as above, with the snapshot removed |
| `open_at(last commit)` | historical handle at the final commit |
| reader | the lock-free reader handle |
| inside a transaction | `SharedDb::begin_transaction`, read before any write |
| with and without a range index | declare one on every filtered property |

No reference evaluator is needed: the states check one another. Rows 139, 103, 107–113,
116 and 154 each reproduce as a disagreement between two rows of this table. Before H-1
merges, each of those rows' original inputs must be shown to fail on the commit before
its fix (red on the old code).

### H-2 Query rewrites that must not change the answer

Also needs no reference evaluator. For a generated query `Q` and predicate `p`:

- **Ternary partition.** The rows of `Q` equal the multiset union of `Q WHERE p`,
  `Q WHERE NOT p` and `Q WHERE p IS NULL`. This catches three-valued logic errors (row 133)
  and comparisons that drop rows (row 160).
- **LIMIT and SKIP.** `Q ORDER BY <total order> SKIP s LIMIT n` equals that slice of
  `Q ORDER BY <total order>`. Without ORDER BY, the rows are a sub-multiset of `Q` and the
  count is `min(n, |Q| - s)`. This is row 139's shape.
- **Aggregate decomposition.** `count(x)` equals the row count of `Q WHERE x IS NOT NULL`.
  `sum` of integers is an integer equal to the sum of the collected values. `min` and `max`
  equal the first and last values of `collect(x)` under ORDER BY. These are rows 157 and 158.
- **Grouping.** `DISTINCT` and grouping keys agree with a client-side grouping of the
  ungrouped rows (row 131).
- **Parameter and literal.** A literal and the same value passed as a parameter give
  the same answer, over HTTP and Bolt as well as embedded.

### H-3 A reference evaluator for a Cypher core

A small, slow evaluator in `sim-harness`, written from the openCypher semantics and
not from `core-query`, over `Oracle`'s graph. It covers one- and two-hop `MATCH`,
variable-length paths up to three hops, `WHERE` with three-valued logic, `WITH`,
`UNWIND`, the aggregates, `DISTINCT`, `ORDER BY`, `SKIP` and `LIMIT`. A grammar-based
generator emits queries in that subset, and answers are compared as multisets, or as
sequences under a total ORDER BY. This is the only workstream that catches a construct
that is wrong in every physical state at once. It comes after H-1 and H-2 because it
costs the most and its own bugs have to be ruled out first.

### H-4 Time travel equals replay

For a generated sequence of commits, `open_at(commit c)` answers every H-1 query the
same as a fresh store that applied only the first `c` commits. This covers the
`snapshot --truncate` commit-numbering defect found during the docs work, which is
still not in the ledger: it gets a row when H-4 reproduces it.

### H-5 Rule engine under snapshots

Extend `oracle_equivalence.rs`: two to four rules over one edge type (top-k, weighted,
via-hop), with snapshots and reopens placed at random between writes, compared with
`Oracle` after each step. This is the class of rows 103–116.

## How it runs

- **Every pull request.** Each workstream runs a fixed seed and a case count that keeps
  the job under 10 minutes.
- **Nightly.** A new scheduled workflow runs the same tests with `PROPTEST_CASES` raised
  about a hundredfold. A failure opens an issue carrying the seed and the shrunk input.
- **Every failure becomes a test.** The shrunk input is checked in as a named regression
  test next to its fix, and the defect gets a ledger row.
- **Gates are not loosened.** A disagreement is a defect until it is shown to be the
  generator's fault. It is never skipped or allow-listed to get a run green.

## What 0.10.x does not do

- No new features. The paused 0.10 units (QL-RD, QL-UD, QL-AE, QL-SORT, TX-1c and the
  rest) wait for 0.11. A defect fix that one of them already contains may be taken alone.
- No format version change.
- No performance work, unless a fix makes something slower and the gates require it.

## Order

1. H-1, with red-on-old proof for the rows listed under it.
2. H-2.
3. 0.10.1: everything H-1 and H-2 found, plus the nightly workflow.
4. H-5 and H-4.
5. H-3.
6. 0.10.2: everything found by H-3–H-5.

## Exit criteria for a public launch

- H-1 to H-5 merged and running nightly.
- Fourteen consecutive clean nightly runs on `main`.
- No open High or Medium wrong-answer rows in the ledger.
- Every 0.10.0 package on its registry: `mushroomdb-bolt` and `mushroomdb-backup` on
  crates.io, both PyPI adapters published.

## Open questions for the owner

- Should the nightly runs file GitHub issues automatically, or only fail the run?
  Recommended: file issues. The project has never received an issue, and a public record
  of found-and-fixed defects is evidence of care.
- Are fourteen nights the right bar? Recommended: yes. Two weeks of clean nights at the
  raised case count is a stronger signal than any single long run, and it keeps the launch
  within weeks.
