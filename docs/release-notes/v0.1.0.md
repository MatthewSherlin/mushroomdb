## What mushroomdb is

An embedded Rust property-graph database with native incremental linking rules. You declare a
predicate once; every subsequent write maintains matching edges and retracts them when properties
change. The graph builds itself.

The five differentiators shipped in v0.1.0:

| Feature | Description |
|---|---|
| **Rules** | Declare once, maintained forever. FieldEqual, Overlap, KeyMatch, NumericWithin, VectorSimilar, All-combinator. |
| **Live subscriptions** | EdgeFired/EdgeRetracted events after WAL fsync, in-process and over WebSocket. |
| **Time-travel** | `open_at(dir, commit)` replays to any past commit; combined with `snapshot()` for forward-only windows. |
| **Views** | Degree counts and neighbor aggregates maintained incrementally on every edge change, zero query overhead. |
| **Suggest** | `suggest_rules()` profiles your data and proposes candidate rules with estimated edge counts and rationale. |

Plus in v0.1.0: **graph algorithms** (PageRank, WCC, Degree Centrality with write-back), **full-text search**
(incremental inverted index, `textMatches()` in Cypher WHERE), and a **TypeScript HTTP client**.

## Headline numbers

All numbers from runs executed against the v0.1.0 binary (release build, `maturin develop --release`
for Python bindings, `cargo test --release` for subscription latency).

### Four-engine two-hop join

**Dataset:** 10,000 nodes (seed=20260819, 70/20/10 Talent/Company/Job), 5,810,000 INDUSTRY_ALIGNMENT
edges (FieldEqual on `industry`; per-source top-k, effectively uncapped at 10k scale).  
**Warmup policy:** fresh process/container, 3 warmup executions discarded, median of 10 measured runs.  
**Policy:** mushroomdb derives edges automatically via `create_rule`; competitors pre-loaded via UNWIND
MERGE (neo4j, memgraph) or COPY FROM CSV (kuzu). All engines return 200 rows.

| Engine | Median | Embed? |
|---|---|---|
| mushroomdb | **261.6 µs** | yes (no network RTT) |
| KùzuDB | 1.59 ms | yes (no network RTT) |
| Memgraph | 1.96 ms | no (bolt/localhost) |
| Neo4j | 3.99 ms | no (bolt/localhost) |

Full contamination guard log: `benchmarks/results/four-way-twohop-20260821-044100.md`.

### Rule maintenance three-way comparison

On 10k nodes with 1,000 specialty updates. All three strategies produce identical edge sets (drift = 0).

| Strategy | Wall | Notes |
|---|---|---|
| Per-op hand-rolled | 64.93 min | Individual delete_edge/insert_edge, one WAL fsync each |
| Batched hand-rolled | 24.98 s | `batch_edges` API, one WAL frame per update |
| Rule engine | **17.58 s** | `create_rule` + `set_prop`, fully automatic |

Full log: `benchmarks/results/handrolled-vs-rules.md`.

### 100k cold-start trio (v0.1.0 measured)

**Dataset:** 100,000 nodes (70k Talent, 20k Company, 10k Job, 500 User), 9 backfill rules,
~10.5M derived edges.

| Phase | Time | Notes |
|---|---|---|
| Backfill (9 rules, max_edges=1M each) | **28.65 s** | Measured; closes "~21.5s estimate" debt |
| V5 snapshot open (`open_with`) | **8.71 s** | Deserializes derived edges + IVF centroids; no rule re-fire |
| Snapshot write (`snapshot()`) | **25.09 s** | Serializes ~10.5M derived edges (~2.2 GiB) |
| WAL-only open | **8.25 min** | Re-derives from node data; IVF-Flat dominates (~7.68 min) |

Full methodology: `dogfood/results/scale-100k.md`.

### Subscription latency (v0.1.0 measured)

**Methodology:** 1,000 events, 50 warmup, `t_recv − t_post` where t_post is set after WAL fsync.
Release build (`cargo test -p mushroomdb-server --test sub_latency --release`). Clock: `std::time::Instant`.

| Channel | p50 | p95 |
|---|---|---|
| In-process (`subscribe_writes`) | **0.17 µs** | **0.42 µs** |
| WebSocket localhost (`/subscribe`) | **86 µs** | **226 µs** |

## Limitations

**RAM-bound.** The in-memory store holds the full graph in process memory. Design target is 10M nodes
(~5–15 GB with properties). mmap-backed storage is on the roadmap.

**Single process.** No replication, no sharding. One writer, multiple concurrent readers via `SharedDb`.
A read-write lock mediates access.

**Crash-atomic writes; no interactive transactions or isolation.** `write_batch` is all-or-nothing per WAL
frame. **Readers may observe intermediate states while a committed batch is being applied in memory.**
There are no BEGIN/COMMIT interactive transactions in v1.

**Cypher subset.** Read and write Cypher are supported with named errors for unsupported forms.
Not supported: CASE WHEN, pattern comprehension, list comprehension, EXISTS subquery, CALL procedures,
schema ops (CREATE INDEX / CONSTRAINT). SET RHS is literal or `$param` only. Combined MATCH…SET…RETURN
is rejected. `+` and `/` in expressions produce lex errors. Full coverage table: [`docs/site/query.md`](../site/query.md).

**Pre-1.0 format policy.** WAL and snapshot formats may change without migration tooling before 1.0.
Snapshot V5 is incompatible with V4 (V4 snapshots are rejected at open). Breaking format changes will
be called out in release notes.

**Full-text-lite is not a search engine.** No stemming, no phrase search, no BM25, no language analysis,
no field boosting. The inverted index is for lightweight graph-native keyword matching. For production
full-text, index into a dedicated engine via the subscription API.

**Approximate vector mode is opt-in.** `approximate: true` enables IVF-Flat. Per-query recall ≥ 0.90
quiesced per spec. Set-coverage recall at 100k is bounded at ~3% by the 1M-edge cap vs ~28M global
positives — not an IVF quality issue. Measure per-query recall (uncapped probe graph) before enabling
in completeness-critical workloads.
