# v0.7.1 Correctness Release — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close four defects 0.7.0 shipped with — a rename that leaves the `id` property behind, a tool schema that refuses a call the skill teaches, a missing-index notice that stops one write too early, and an image pushed before its release exists — and prepare 0.7.1 for the owner to tag.

**Architecture:** Each defect is one task and one commit, and each task carries its own tests, its own documents and its own ledger row, so any of them can be reviewed, or cut, alone. The rename fix lives in the one batch arm every rename can reach, with `GraphDb::rename_node` delegating to it; the schema fix copies `edges_at`'s shape so the two time-travel tools cannot drift; the notice is one read-only function in `core-api` that two surfaces print and that never declares anything. The release task bumps, re-targets what 0.7.1 does not fix, runs every gate, writes the owner's checklist and stops before anything leaves the machine.

**Tech Stack:** Rust 1.92.0 (`rust-toolchain.toml`), a cargo workspace of 10 crates; the Python binding is its own workspace at `bindings/python` (pyo3 0.26, `abi3-py310`), tested with pytest from `bindings/python/.venv`; Python 3 standard library plus PyYAML 6.0.3 (present on this machine) for one read-only check; bash 5.3 at `/opt/homebrew/bin/bash` (first on `PATH` here); `actionlint` 1.7.12 is installed locally at `/opt/homebrew/bin/actionlint`.

**Spec:** ledger rows 61, 71, 72 and 73 in `docs/roadmap/v0.6.10-defects.md` (index rows at `:76`, `:86`, `:87`, `:88`; sections at `:2340`, `:2386`, `:2392`, `:2398`), and `docs/roadmap/v0.7-memory-write-path-spec.md` §3.1 and §3.5 for row 73.

**Base:** `main` at `4251e8c`, tag `v0.7.0`. Every `file:line` below is `4251e8c`'s. Tasks 1–4 move lines in files they share (the table under "File map"); find a site by the text quoted, not by its number.

> **How this plan was checked.** Unlike the 0.7.0 release plan, this one was run before it was written. On 2026-10-02, at `4251e8c`: each of the four defects was reproduced on the debug binary; every test below was written, shown RED, and then shown GREEN against a prototype of the fix; the whole end state — all four fixes, every document edit, the bump to 0.7.1, the ledger edits — was assembled in the working tree, put through fmt, both clippy runs, the workspace suite, the multiprocess suite and every script gate, and then reverted with `git checkout -- .`. ### Procedure R — driving the MCP server from a shell

Tasks 1, 2 and 3 reproduce their defect on the binary first. Write this once per task into scratch; it speaks to one `mushroomdb mcp <store> --all-tools` process the way `scripts/measure-tool-listing.py` does. It was used for every reproduction in this plan.

```bash
S=/private/tmp/claude-501/-Users-nilrehsttam-Repos-graph-db/77900640-3d9d-41a8-8eb6-bea6c4cd90c9/scratchpad/x71; mkdir -p $S; cat > $S/mcpcall.py <<'EOF'
#!/usr/bin/env python3
"""Drive one `mushroomdb mcp <store> --all-tools` process over stdio.

    mcpcall.py <binary> <store> <tool> '<json args>' [<tool> '<json args>' ...]

Each call's reply text is printed under a `## tool args` line. The pseudo-tool
`schema-of` prints one tool's entry from `tools/list` instead of calling it:

    mcpcall.py <binary> <store> schema-of '{"tool": "was_linked"}'
"""
import json
import subprocess
import sys

binary, store, rest = sys.argv[1], sys.argv[2], sys.argv[3:]
calls = [(rest[i], json.loads(rest[i + 1])) for i in range(0, len(rest), 2)]
requests = [
    {"jsonrpc": "2.0", "id": 1, "method": "initialize",
     "params": {"protocolVersion": "2024-11-05", "capabilities": {},
                "clientInfo": {"name": "mcpcall", "version": "0"}}},
    {"jsonrpc": "2.0", "method": "notifications/initialized"},
]
for n, (tool, args) in enumerate(calls):
    if tool == "schema-of":
        requests.append({"jsonrpc": "2.0", "id": 100 + n, "method": "tools/list"})
    else:
        requests.append({"jsonrpc": "2.0", "id": 100 + n, "method": "tools/call",
                         "params": {"name": tool, "arguments": args}})
stdin = "".join(json.dumps(r) + "\n" for r in requests)
out = subprocess.run([binary, "mcp", store, "--all-tools"], input=stdin,
                     capture_output=True, text=True, timeout=120).stdout
replies = {}
for line in out.splitlines():
    reply = json.loads(line)
    replies[reply.get("id")] = reply
for n, (tool, args) in enumerate(calls):
    reply = replies.get(100 + n, {})
    print(f"## {tool} {json.dumps(args, ensure_ascii=False)}")
    if "error" in reply:
        print("JSON-RPC error:", json.dumps(reply["error"]))
        continue
    result = reply.get("result", {})
    if tool == "schema-of":
        entry = next(t for t in result["tools"] if t["name"] == args["tool"])
        print(json.dumps(entry, indent=1, ensure_ascii=False))
        continue
    flag = " [isError]" if result.get("isError") else ""
    for item in result.get("content", []):
        print(item.get("text", "") + flag)
EOF
```

`mushroomdb mcp` on a directory that holds no store creates one with the memory defaults (12 commits), so a scratch store made this way starts at commit 12. `mushroomdb query` on such a directory creates a store with no schema at all.

**Interfaces:**
- Consumes (all exist at `4251e8c`, all private to `db.rs` unless marked): `MutPreview::prop_value(&self, key: &str, field: &str) -> Option<Value>` (`:14785`); `MutPreview::note_set_prop(&mut self, key: &str, field: &str, value: &Value)` (`:14876`); `MutPreview::check_rename_node` (`:14924`), `note_rename_node` (`:14934`); `GraphDb::commit_batch(&mut self, ops: Vec<BatchOp>) -> Result<(usize, usize)>` (`:6670`); `ViewStore::view_for_prop(&str) -> Option<…>` as the `BatchOp::SetProp` arm uses it (`:6519`); `pub GraphDb::get_prop(&self, key: &str, field: &str) -> Option<Value>` (`:8194`); `WalRecord::RenameNode { old_key, new_key }`, `WalRecord::SetProp { key, field, value }`.
- Produces: no new name and no changed signature. `pub fn rename_node(&mut self, old: &str, new: &str) -> Result<()>` keeps its signature and its two errors (`KeyNotFound`, `DuplicateKey`). The behaviour produced: after any rename, a stored `id` that was `Value::Str(old)` is `Value::Str(new)`, written in the rename's own WAL frame.

**Why, and the design (D1, D2).** `upsert_entity`'s create path (`crates/core-api/src/memory/remember.rs:399`) and a Cypher `CREATE {id: …}` (`db.rs:10741`) store the key as an `id` property. The read path prefers a stored property and falls back to the key only when none is stored (`db.rs:932-942`, `:1143`), so a rename that moves the key and not the property makes `n.id` answer with a key the node no longer has. What was checked:

- **Rename is reached two ways.** The MCP tool (`crates/server/src/mcp.rs:1130`), the Python binding (`bindings/python/src/lib.rs:568`) and `ingest-git` (`crates/cli/src/ingest_git.rs:1640`) call `GraphDb::rename_node`. HTTP (`crates/server/src/http.rs:2324`) and `BatchBuilder::rename_node` (`db.rs:15104`) queue `BatchOp::RenameNode`, which never passes through that function. So the rewrite goes in the batch arm, and `rename_node` sends a node that has an `id` to move through it.
- **It stays one WAL frame.** Today `rename_node` logs a bare `RenameNode` record. With an `id` to move it logs `Batch[RenameNode, SetProp]`: one frame, one commit, no new discriminant. A node with no such `id` keeps the bare record, so its WAL bytes are what they were. The dense rewrite already resolves a `SetProp` on the new key inside the same batch (`db.rs:4905-4920`, "so subsequent InsertEdge / SetProp records in this batch can resolve the new key").
- **Time travel.** A read as of the commit before the rename returns the old key and the old `id`; at the rename's commit, the new key and the new `id` (pinned). `node_history` gains one `PropSet` of `id` at the rename's commit (pinned).
- **Rules.** The rewrite is an ordinary `SetProp`, so the engine re-evaluates the node for rules whose watched fields include `id` and for no others (`on_node_changed`, `crates/core-rules/src/engine.rs:3615`). No shipped rule watches `id`. Not pinned by a test.
- **`aliases` and `alias_keys` are untouched.** A rename does not edit them today and does not now; the former key still reaches `alias_keys` on the next describing write (`identity_lists`, `crates/core-api/src/memory/identity.rs`), and `a_former_key_is_kept_as_a_declared_alias` still passes (observed, in the full run).
- **A view that owns a property named `id`** makes that property read-only to callers (`db.rs:6519`). The rewrite is skipped then, rather than writing a view's column.
- **Two side effects of the frame being a batch**, stated so a reviewer does not rediscover them: under `FsyncPolicy::Batched` a two-mutation frame fsyncs where a bare rename did not (`wal_needs_sync`, `db.rs:5255-5271`); and a subscriber sees a `PropSet` event for `id` (`db.rs:335`; read, not exercised by a test).
- **`ingest-git` already wrote `id` after its own renames** (`ingest_git.rs:1644`). That line is now redundant and is left alone.
- **The unlisted tool's schema and description do not change**, so the listing's bytes do not move.

fn key_and_id(db: &GraphDb<core_api::RealFs>, where_clause: &str) -> Vec<(String, String)> {
    let cypher = format!("MATCH (n:Person) WHERE {where_clause} RETURN key(n), n.id");

- **Cost.** One `fulltext_pairs()` and one comparison per call on a store that has the defaults. On a store that lacks one, a pass over the node ids under that label, reading properties until the first node that carries the field.

/// The memory defaults' full-text fields this store has not declared and has
/// something to find in: each `(label, field)` of
/// [`memory_defaults`](crate::memory_schema::memory_defaults) that
/// `fulltext_pairs()` lacks while a live node under the label carries the
/// field. In the defaults' order.
///
/// `remember` declares `Note.text`, and the name of each `entities[].label`,
/// as it writes. So a store that never took the defaults stops being
/// "a store with no text index" at its first note, while the entities already
/// in it stay unsearchable by name. This is what `recall` and the session
/// brief name from then on, with the one command that indexes them.
///
/// Empty on a store that took the defaults. Empty too on a store whose schema
/// is its owner's and holds no node under a memory label: the defaults would
/// index nothing there, so it is never told to apply them. A field no node
/// carries is not reported, whatever the label holds.
///
/// Reads nodes only under a label whose default is undeclared, and stops at
/// the first that carries the field.
pub fn unindexed_memory_fields<F: Fs>(db: &GraphDb<F>) -> Vec<(String, String)> {
    let declared = db.fulltext_pairs();
    crate::memory_schema::memory_defaults()
        .fulltext
        .into_iter()
        .filter(|pair| !declared.contains(pair))
        .filter(|(label, field)| {
            db.nodes_with_label(label)
                .iter()
                .any(|n| n.prop(field).is_some())
        })
        .collect()
}

/// prints them.
pub fn unindexed_fields_list(fields: &[(String, String)]) -> String {

        .iter()
        .map(|(label, field)| format!("{label}.{field}"))
        .collect::<Vec<_>>()

## Known costs this plan accepts

- **A store that deliberately leaves named memory-label nodes unindexed is reminded** in each `recall` tool reply and once per session.
- **On a store missing a default, each `recall` tool call and each brief walks the node ids of the affected labels** until it finds one node carrying the field. A store with the defaults pays one `fulltext_pairs()` call.
- **The workflow change is unexercised until the tag.**
