# mushroomdb v0.6.0 — "the live code graph" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to
> implement this plan task-by-task on a branch off `main` (after PR #12 / v0.5.2 has merged).
> Keep a ledger at `.superpowers/sdd/v0.6-code-graph-plan/progress.md`. Steps use checkbox

> `Co-Authored-By` / `Claude-Session` trailers to commits (owner's standing rule — verify with
> `git log --format=%B origin/main..HEAD | grep -ci 'co-authored\|claude-session'` → must print 0
> before opening the PR). Never name the owner's private repositories in anything committed.

**Goal:** Ship the engine features that make mushroomdb a *solid embedded Rust graph database
for agents* — multi-process safety, multi-valued foreign keys, community detection — and put one
application on top that proves them: a live code graph that does what a static, re-extracted
graph cannot. The graph is **live**
(updated by the edit that changed it, and by every commit), **true** (every relationship is a
rule that retracts when its evidence changes), **explainable** (every edge carries its rule,
score, and the commits or lines that earned it), **historical** (every fact versioned and
queryable as-of), and **queryable** (Cypher + BM25 + vectors over one store). The MCP server and
the `/mushroom` skill are the surface; the engine is the product.

**Architecture:** Phase 0 hardens the engine (advisory write lock + WAL tailing so several
processes can share a store; `KeyMatch` over list fields; Louvain). Phase 1 adds sources
(tree-sitter structure, docs, mailmap, submodules, PRs) that write nodes and **list-valued props**
only — every edge is derived by a rule. Phase 2 adds task-shaped tools (`map`, `context`,
`impact`, `owners`, `why`, `recall`, `remember`, `sync`) shared by MCP and CLI, plus three hooks
(diff-aware prompt nudge, async post-edit refresh, git post-commit sync). Phase 3 makes install
one command (`npx -y mushroomdb@<exact>` entries; Claude Code plugin). Phase 4 proves it with
scripts that fail when the claims stop being true.

**Tech Stack:** Rust 1.92.0 (pinned; `std::fs::File::{lock,try_lock,unlock}` are stable since
1.89 — no lock crate), tree-sitter 0.27 + grammars (`tree-sitter-rust 0.24`, `-python 0.25`,
`-typescript 0.23`, `-javascript 0.25`, `-go 0.25`), `blake3`, serde_json, existing core crates;
Node 22 + `@modelcontextprotocol/sdk` (CI only); GitHub Actions.

**Spec:** this document is self-contained. "Why this release" is the why, "Product surface" the
what, the tasks the how. Background notes on the wider field live in the gitignored ledger
directory (`.superpowers/sdd/v0.6-code-graph-plan/landscape.md`); they are context for the
implementer only. **Nothing committed to this repository — code, docs, skill text, changelog,

## Why this release

**Thesis, stated so it can be falsified:** a real embedded graph database with rules, history,
explain and multi-process safety is the right foundation for an agent's code memory. Structure,
git, docs and the agent's own notes are sources that write nodes and list-valued props; rules
derive every relationship and retract it when the evidence changes; every answer is a query with
evidence; and the store stays true while three processes (the MCP server, an editor hook, a git
hook) write to it. If Phase 4's scripts cannot demonstrate that on this repository, the thesis is
wrong and the release does not ship.

What the engine must be able to do, and the task that proves it:

| Capability | Proven by |
|---|---|
| Several processes share one store safely; a long-lived handle sees other processes' commits | Task 1, Task 18 §6 |
| A list-valued property is a multi-valued foreign key; edges retract per element | Task 2, Task 6 |
| Communities and centrality are computed deterministically under a budget | Task 3, Task 8 |
| The graph reflects an edit within the same turn and a commit within seconds | Tasks 7, 12, 18 |
| `why A B` answers with the rule, the score, and the commits or lines that earned it | Task 9 |
| Ownership and coupling are answerable over time | Task 9 |
| One call gives 360° context on a file or symbol | Tasks 9, 11 |
| Install is one command and verified by a real client handshake | Tasks 14–17 |

**Scope boundaries for 0.6.0 (state them plainly in the docs):** six languages via tree-sitter
(Rust, Python, TypeScript/TSX, JavaScript/JSX, Go) with hash-only coverage for the rest;
Markdown/plain-text docs (the skill's semantic pass reads whatever the assistant can read);
assistants: Claude Code (plugin + install), Cursor, Codex; exports: jsonl, parquet, GraphML.

## Phase 0 — Engine

### Task 1: Multi-process safety — advisory write lock + WAL tailing

This is the release's most important engine change: it turns "embedded = one process" into
the many-readers / one-writer model (all processes see every commit). Without it
the hooks in Phase 2 would corrupt or diverge from the MCP server's view.

**Files:**
- Modify: `crates/core-storage/src/fs.rs` (`Fs` trait + `RealFs`), `crates/core-storage/src/lib.rs` (`GraphError::Busy`)
- Modify: `crates/core-api/src/db.rs` (`open_with_repair` replay loop factored into `apply_frames(&mut self, frames)`; frame cursor `wal_consumed: usize` + `snapshot_ident: Option<(u64 /*len*/, u64 /*mtime ns*/)>`; `refresh`, `is_stale`, `OpenOptions.read_only`), `crates/core-api/src/shared.rs`, `crates/core-api/src/lib.rs`
- Modify: `bindings/python/src/lib.rs` + `.pyi` (`refresh()`, `read_only=` kwarg, `MushroomBusy` exception), `bindings/python/README.md`
- Create: `crates/core-api/tests/multiprocess.rs`; `docs/site/concurrency.md`; update `docs/site/durability.md`, `docs/site/api.md`
- Test helper binary: `crates/core-api/examples/mp_worker.rs` (spawned by the tests: `mp_worker <db> write <n>` appends n nodes; `mp_worker <db> read` prints node count)

**Interfaces (produces):**
```rust
// core-storage fs.rs
pub trait Fs {
    /* existing */
    fn try_lock_exclusive(&mut self) -> std::io::Result<bool> { Ok(true) }   // LOCK file; RealFs: File::try_lock()
    fn unlock(&mut self) -> std::io::Result<()> { Ok(()) }
    fn wal_len(&self) -> std::io::Result<u64>;                                // RealFs: metadata().len(); SimFs: buffer len
    fn read_range(&self, file: FileId, from: u64) -> std::io::Result<Vec<u8>>; // bytes [from..]
    fn snapshot_ident(&self) -> std::io::Result<Option<(u64, u64)>>;          // (len, mtime_nanos) of snapshot.bin, None if absent
}
// core-api
impl<F: Fs> GraphDb<F> {
    pub fn refresh(&mut self) -> Result<u64>;
    pub fn is_stale(&self) -> Result<bool>;
}
pub struct OpenOptions { pub auto_migrate: bool, pub repair_wal: bool, pub read_only: bool }
pub const WRITE_LOCK_WAIT: Duration = Duration::from_secs(2);
pub const REFRESH_CHECK_INTERVAL: Duration = Duration::from_millis(50);
```

Semantics (write these as doc comments; each is a test):
1. **Refresh.** `is_stale` = `wal_len() != wal_consumed || snapshot_ident() != self.snapshot_ident`. `refresh`: if the snapshot identity changed or `wal_len < wal_consumed` (truncated/archived by another process's snapshot) → rebuild `*self` via the open path (same `OpenOptions`) and return the number of frames in the new tail; else decode `read_range(Wal, wal_consumed)` with `decode_all`, apply the **complete** frames through `apply_frames` (rules fire exactly as during open replay, derived edges included), advance `wal_consumed` by the decoded byte count, return the frame count. A trailing partial frame (another process mid-append) is left for the next refresh — never treated as corruption. Interners/id maps/indexes stay valid because `apply_frames` is the same code path open uses.
2. **Write lock.** Every mutation entry point that appends to the WAL goes through `SharedDb::write()`/`WriteGuard`, which (a) polls `try_lock_exclusive` every 10 ms up to `WRITE_LOCK_WAIT` (else `Err(GraphError::Busy)` from `write_with_wait`; plain `write()` panics? **No** — `write()` returns the guard as today but internally uses `write_with_wait(WRITE_LOCK_WAIT)` and converts `Busy` into a `GraphError` on the first mutation; simplest: change `write()` to return `WriteGuard` whose mutations return `Busy` if the lock was not obtained — pick this, keep the signature), (b) calls `refresh()` under the lock so the write applies on top of every other process's commits, (c) releases the lock on drop. A plain `GraphDb` (not `SharedDb`) opened with `read_only: false` takes the lock for the **handle lifetime** at open (`Busy` if held) — the CLI's one-shot commands (`ingest-git`, `touch`, `sync`, `query` writes) use this and therefore serialise against the server naturally; `read_only: true` never locks and can always open.
3. **Read refresh.** `SharedDb::read()` checks `is_stale` at most once per `REFRESH_CHECK_INTERVAL` (an `AtomicU64` of the last check instant); when stale it briefly takes the in-process write lock, `refresh()`es, then hands out the read guard. Readers never block on the cross-process lock.
4. **Snapshots** (`snapshot()`, `--snapshot-every`) take the cross-process lock; other processes detect the new snapshot identity and reopen on their next refresh.
5. **Hook commands** (`recall`) keep `read_only: true` and additionally call `refresh()` before reading (they open fresh each time, so this is implicit).
6. **Python binding**: `GraphDb(path, read_only=False)`, `db.refresh() -> int`, `MushroomBusy` maps `GraphError::Busy`; the README's concurrency section is rewritten: "one writer at a time across processes; readers see commits after `refresh()` or automatically via `SharedDb`".
