## Before anything leaves this machine

- [ ] **D5 — that line sits outside the brief's 4,000-byte cap and the digest's 1,200-byte
      budget**, as the "no text index" line already did.
- [ ] **D6 — the Python binding's `recall` rows are unchanged.**
- [ ] **D7 — the image job needs `github-release`**, not only the binaries, and `release.yml`
      still runs no test.
- [ ] **D8 — twelve rows 0.7.0 deferred to 0.7.1 move to 0.7.2**: 47, 48, 50, 51, 52, 53, 57,

- [ ] **D9 — 0.7.0's section of the changelog was edited**: three known limits now read
      "fixed in 0.7.1" and six read "deferred to 0.7.2".

Three more were decided during the work, on your behalf. Each changes what ships.

- [ ] **D4's check is bounded.** It reads the first 1,000 live nodes of each memory label and
      no further, so that `recall` and the brief do not pay a scan of the whole store. The
      cost: a store whose first 1,000 nodes of a label lack a field that a later node carries
      is not told. Unbounded, the check measured 39 ms to 125 ms a call on a debug build over
      100,000 such nodes (ledger section 73).
- [ ] **The `recall` tool's older "no text index" answer sanitizes the store path it prints.**
      A control character in the path is replaced with a space. Found beside D4's line and
      fixed in the same task.
- [ ] **A new ledger row, 79, ships as a known limit, deferred to 0.7.2.** In a batch built in
      Rust, the ops after a rename cannot see the renamed node's stored properties: an
      `insert_edge` from it passes the cross-namespace guard, a `remove_prop` on it does
      nothing, and a second rename does not move an `id` equal to the key in between. No
      served surface puts a rename beside another op. It predates 0.7.1; Task 1's review found
      it. The alternative is a fix in the batch preview before the tag.

## The merge

- [ ] **The plugin window opens again at the merge.** The marketplace serves the plugin from
      the default branch, and from the merge on `packaging/plugin/.mcp.json` and its hook
      script name `mushroomdb@0.7.1`, which the npm registry does not have until
      `publish.yml`'s launcher job finishes. Until then a new plugin install, or a copy of the
      Claude Desktop block from `docs/site/mcp.md` or `llms.txt`, gets a server that cannot
      start; a plugin already installed keeps the pin it has. 0.7.0 handled it by merging and
      then tagging as soon as `main` was green, and this checklist is in that order.
      `docs/roadmap/v0.7-release-checklist.md`, "The merge", sets out the other ordering and
      its costs.
- [ ] Merge, as a true merge commit: the tag goes on it. `pages.yml` deploys `docs/site/` on a
      push to `main` that touches it, and this branch changes `api.md`, `mcp.md`, `skill.md`
      and `timetravel.md` there.
- [ ] Wait for CI on `main` to finish green. The image now waits for the release, but
      `release.yml` still runs no test: the tag goes only on a commit already known green.

## The tag — nothing after this can be taken back

- [ ] If anything changed since the rehearsal, run it again on the commit you are about to tag.
- [ ] **Confirm the publish credentials.** `publish.yml` reads one secret, `NPM_TOKEN`, in both
      npm jobs. crates.io and PyPI use trusted publishing and read no secret.
- [ ] **Confirm no `v0.7.1` tag is on the remote**: `git ls-remote --tags origin 'v0.7.1'`
      prints nothing. There is none locally.
- [ ] Tag the merge commit on `main` with an annotated tag, as `v0.7.0` is, and push it:
      `git tag -a v0.7.1 -m v0.7.1 <the merge commit on main>` and `git push origin v0.7.1`.

What that starts. `release.yml` runs on the pushed tag; its `trigger-publish` job dispatches
`publish.yml` on the same tag, where the crates, PyPI and npm jobs run side by side.

| What | Where | Can it be undone? |
|---|---|---|
| Three binaries, `SHA256SUMS`, the Homebrew formula | the GitHub Release | Deletable — but the npm launcher downloads its binary from it, and so does the formula |
| `:latest` and `:v0.7.1` | `ghcr.io/matthewsherlin/mushroomdb` | Overwritable; images already pulled are out |
| Eight crates, in dependency order | crates.io | **Never.** Yank only; `0.7.1` cannot be published again |
| Three abi3 wheels | PyPI | **Never** for that version: a deleted file's name cannot be reused |
| `mushroomdb` and `mushroomdb-client` | npm | The number is burned once used |

- [ ] Watch `release.yml`: `binary-<target>` (three), `github-release`, then `docker` and
      `trigger-publish`. **`docker` should not start until `github-release` has finished.**
      This is the first run of that change. If it starts alongside the binaries, the `needs`
      line did not take effect: note it on ledger row 61, which this release closed.
- [ ] If `github-release` fails, a draft is left, `trigger-publish` does not run, no registry
      is touched and — new in this release — no image is pushed. **Do not publish that draft
      by hand**: `publish.yml` also runs on a release a person publishes. Re-run the failed
      job.
- [ ] **Approve the `pypi` environment.** It has a required reviewer, and at 0.7.0 you
      approved it by hand. `publish.yml`'s `PyPI` and `PyPI upload` jobs both name
      `environment: pypi`: they wait, marked as waiting for review, until you choose "Review
      deployments" on the run's page and approve. The crates and npm jobs do not wait for it,
      so an unapproved run is crates and a launcher with no wheel.
- [ ] Watch `publish.yml`: `crates.io`, `PyPI` (three builds) and `PyPI upload`,
      `npm (mushroomdb launcher)`, `npm (mushroomdb-client)`, `npx smoke test`.
- [ ] **If the crates job fails part-way, re-run the failed jobs of that run.** The crates step
      skips a crate already on the index, and both npm jobs skip a version already published.
      `PyPI upload` has no such skip: re-run it only if it failed. Do not delete the tag and do
      not re-tag.
