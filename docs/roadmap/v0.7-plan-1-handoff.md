## 1. What it delivers

On shipped v0.6.12, `upsert_entity` → `remember` → `recall` returned nothing. Two independent
causes, both now fixed:

- **`recall` refused to search anything not shaped like code.** `repograph::recall_digest` began
  with `identifier_terms(topic)` — paths, `mod::name`, snake_case, backticked words — and returned
  empty when it found none. Provable on one store with one note: `recall("graph_db")` HIT,
  ``recall("`concise`")`` HIT, `recall("Matthew")` **MISS**, with the note indexed and the word in
  it. A human name, the commonest subject in a memory store, was unreachable by design.
- **Only `Note.text` was ever indexed**, self-declared by `remember`, so `recall` could return
  notes but never the entities they were about.

Plus: a fact can now arrive before its subject (provisional entities), `remember` takes optional
extracted structure and caller-supplied provenance and returns a report of what it did, and three
release gates that could not see what they guarded now can.

**Verified state at `8e900c5`:** `cargo test --workspace --no-fail-fast` exit 0 — **120 binaries,
2533 passed, 0 failed, 31 ignored**. `fmt` and `clippy -D warnings` clean on both feature sets.
Zero attribution trailers across all 21 commits.

### Verified by driving the real binary, not by reading tests

```
upsert_entity{key:"matthew", label:"Person", props:{name:"Matthew Sherlin"}}  -> created
recall{topic:"Matthew Sherlin"}            -> matthew — Matthew Sherlin
remember{text:"...", about:["matthew"]}    -> entities 0 created, 1 matched
recall{topic:"What does Matthew prefer?"}  -> finds the note
```

- **Format compatibility: verified by round-trip.** Installed the released `mushroomdb@0.6.12`,
  wrote a demo store with it (60 nodes, 334 edges, 7 rules), opened it with the branch binary —
  identical stats, `COUNT(r)=334`. No new WAL discriminant, no format change.
- **Existing stores are never upgraded: verified byte-wise.** A 0.6.12-written store opened by
  0.7's `mcp` leaves `wal.bin` **byte-identical**. Nothing is written.
- **The newest gate is load-bearing: verified by reverting the fix.** With `crates/cli/src/main.rs`
  reverted, `an_mcp_created_store_can_find_the_entity_it_was_told_about` fails and the other four
  pass.

## 4. The design decision worth a second opinion

`recall` needed a relevance floor: without one, an unrelated topic returned a confident-looking
digest, because RRF replaces every BM25 score with `1/(60 + rank)` so the top hit of *any* query
scores `1/61` regardless of match strength.

I asked for a per-term BM25 floor mirroring `repograph`'s `MIN_HIT_SCORE = 0.05`. The implementer
argued a score threshold cannot work here and demonstrated it: the false-positive case's own BM25
is ~0.29, roughly six times that floor, because idf grows for any globally-rare term — a
coincidental single occurrence clears a fixed floor at any corpus size, not merely a small one.
`repograph`'s own gate test at N=3, df=1 scores idf≈0.981, about twenty times its own floor.

What shipped instead is **term coverage**, computed **per candidate node**: a candidate survives
only if a strict majority of the topic's surviving terms appear *in that node*. Corpus-size
independent by construction. It took two rounds — the first version computed coverage globally, and
a reviewer reproduced a store where "apple", "banana" and "cherry" each sat in a different unrelated
node and the topic "apple banana cherry" returned all three.

**Known limitation, disclosed in code and here:** a two-word topic now requires both words present
in the same node. That is a deliberate precision-over-recall choice for a memory store, and it is
the thing to revisit first if recall feels too tight in use.

## 5. Independent findings, not caused by this branch

- **The Cypher subset has no boolean-literal support.** `WHERE x = true` (or `= false`) on any Bool
  property errors `unbound variable 'true'`. Reproduced independently by two agents. The bare-truthy
  form `WHERE x` works and was verified to discriminate `true`/`false`/absent correctly, which is how
  a gate test was written around it. **Deserves its own issue.**
- **The full-text query parser and the indexer disagree about punctuation.** `parse_query_v2`
  strips non-alphanumerics into a single token while `tokenize()` splits on them at index time, so
  an unquoted `graph_db` is searched as `graphdb` against stored `graph`/`db`. This is why the naive
  "pass the topic straight through" approach could match neither a question nor a punctuated
  identifier.
- **A user-scope skill is shadowing the shipped one.** `~/.claude/skills/mushroom/SKILL.md` has
  drifted from `crates/cli/skills/mushroom/SKILL.md` — the installed copy advertises trigger words
  the shipped copy does not. `install` writes a skill; nothing detects an older user-scope skill
  shadowing it. Cheap check for `doctor`.
- The checked-in `db/` and `dogfood/results/scale-2000-db/` stores do not open on any current
  binary. They are dated Aug 18–19 (~v0.1.x) and the engine's own legacy path already declines them.
  Pre-existing, not a 0.7 regression.

## 7. Late findings — what the final review caught after §1 was written

`ed578a7`:

- **`serve` had the same gap `mcp` had.** The new-store schema application lived only in `run_mcp`,
  so a store created by `mushroomdb serve <new-dir>` had no memory schema and the HTTP surface kept

### The second late wave — six more, found after the branch was declared done a second time

The original final reviewer eventually delivered, having built v0.6.12 in a detached worktree and
probed every claim against a real binary. It found two MUST-FIX defects in work already signed off,
and four more items behind them. All are fixed in `1051271` and `8e900c5`:

- **A provisional entity could never become a `Person`, and `upsert_entity` returned `ok`.**
  `describe_entity` uses `label` only on create, and the engine has **no label-mutation API at all**
  — adding one needs a WAL discriminant the spec forbids. So `remember{about:[k]}` then
  `upsert_entity{key:k, label:"Person"}` left the node permanently `Entity`: invisible to
  `MATCH (n:Person)`, outside `memory_defaults()`'s equality indexes, and outside any per-label
  `SAME_AS` rule a later plan writes. Now a hard error naming both labels and both escapes. **I
  missed this because my own walkthrough ran `upsert_entity` first, then `remember` — the order
  that works. The provisional feature exists for the opposite order.**
- **`remember{entities:[{label:"Release"}]}` wrote an entity `recall` could not find** — §1.1(b),
  this release's own defect, reproduced through this release's own new feature, using spec §3.4's
  verbatim worked example. Now self-declares `<Label>.name` full-text on first sight of a label,
  guarded against the non-idempotent setter, reported in `RememberReport.fulltext_declared`, capped
  at `MAX_FULLTEXT_PAIRS = 32`.
- **Defect-ledger row 36 should never have been closed.** My Task 3 brief told the implementer to
  resolve it rather than re-defer; the reviewer probed the gate and found `DEFERRED to 0.8` passes
  it. I closed a live defect — one three files in this branch cite as the constraint shaping the
  design — to satisfy a gate that would have accepted an honest forward deferral. Reopened.
- **Spec §3.2's provisional cap did not exist**, while the plan's self-review claimed §3.2
  complete. Now `MAX_PROVISIONAL_PER_COMMIT = 20`, disclose-and-continue rather than refuse-all,
  itemised in `RememberReport.provisional_capped`.
- **The coverage filter scanned the entire corpus.** `search_top(field, term, 0)` means *no*
  truncation, so coverage cost `fields × terms` full-corpus scans per call to filter at most six
  results — and the self-declaration above grows `fields` without bound, so it had to be fixed in
  the same pass. Now checks each of the ≤48 candidates already in hand against its own tokenized
  prop value using the index's own `value_tokens_stemmed_with_positions`, equivalent by
  construction rather than approximately.
- Two one-liners: a `describe_entity` doc comment claiming "every surface" when only MCP calls it,
  and the no-index message printing a literal `<db>` placeholder — the one message this release
  shows every 0.6.x user who upgrades and calls `recall` before writing.

Both new bounds (`32` and `20`) are reasoned first guesses with no telemetry behind them. Revisit
when plans 2–3 show real extraction shapes.

### Not fixed here — settle before Plan 2 points the prompt hook at `memory::recall`

- **The coverage threshold is a co-occurrence requirement at n=2.** Strict majority
  (`present * 2 > terms.len()`, `recall.rs:306-309`) means a two-term topic needs both terms in the
  *same* node. The product's central shape is an entity node holding the name and a note holding the
  fact — precisely where they do not co-occur. `recall{topic:"What does Matthew prefer?"}` →
  `{matthew, prefer}`: the note survives 2/2, **the Person node scores 1/2 and is dropped.** Every
  existing "recall preserved" test uses a topic whose terms all co-occur in one node, so the suite
  structurally cannot detect this. I asked whether precision had been bought at recall's expense and
  the answer came from re-running those same tests.
- **A simpler instrument was available and matches the spec's own philosophy.** The digest discards
  the score entirely (`recall.rs:317-334`), which is *why* a hard gate felt necessary — weak and
  strong hits render identically. Spec §3.3's stated principle for `SAME_AS` is "a weak match is a
  weak edge, not silent corruption". Carrying coverage into the digest line (`reid — reid
  (1/3 terms)`) and ordering by it closes the false-positive case without dropping the 1-of-2
  entity: no threshold to tune, strictly more informative.
- **The floor's cost was never measured.** `recall.rs:296-305` calls `search_top(field, term, 0)`,
  and `k == 0` means *no limit*; there is no term cap where `repograph` has `MAX_QUERY_TERMS = 24`.
  Cost is terms × fields unlimited full-corpus searches per call, filtering a `search_hybrid` leg
  bounded to 6. Harmless today because the prompt hook still calls `repograph::recall_digest`; it
  becomes both a cost and a near-certain `NoMatch` when Plan 2 moves whole prompts onto this path.
- **Nine coherence findings inside `crates/core-api/src/memory/`.** The two that compound: `recall`
  has no notion of provisional, so a typo'd stub renders `  reid — reid` indistinguishably from a
  described entity and competes for the six hit slots; and `remember` self-declares only
  `Note.text` while writing `Entity.name` nodes, so on a store whose first write is `remember` the
  stub's own name is unindexed — the library-level twin of the `mcp` gap, still open for callers
  arriving through the library, HTTP or Python.
- **`upsert_entity`'s create path changed engine primitive, not just composition.** The plan said
  only the write composition would move; in fact `ingest(...)` was replaced with `insert_node` via
  `describe_entity`. 110/110 MCP tests pass and namespace behaviour was verified both ways, but
  nothing on record compares `ingest` and `insert_node` for behavioural equivalence on type
  coercion, list handling, or index maintenance. Worth one explicit check before release.
- **`ingest-git` is the last store-creating path without the memory schema.**
  `cli/src/ingest_git.rs:1142,1747`. `mcp`, `serve` and `demo` all declare it now; a store born
  from `ingest-git` still gets the no-index message until `schema apply`. Plan 2 owns
  `ingest-git`'s repositioning, so it belongs there.
- **The census still cannot fail a build** (`scripts/ignored-test-census.sh:50`). It reports, which
  is what spec §8.4 asks for, but nothing stops the unrun count growing — and this branch's own
  HNSW split pushed it from 20 to 21 by adding `adjacency_bytes_per_node_is_within_the_ceiling`,
  which no workflow names. Making it fail is a policy call that reddens CI today.
- **`matched` undercounts when `facts` name an already-existing endpoint** — that branch increments
  nothing (`remember.rs:339-351` has no `else`). Report semantics only, no data effect.
- **RRF flattens every field's top hit to `1/61`**, so digest *order* among survivors is close to
  meaningless and ties break by key ascending. Coverage now carries all the precision and ranking
  carries none. Inherent to the fusion; documenting it is the fix, not reordering.
- **The coverage floor is skipped entirely when every term is a stopword** — and this one is safe,
  which is worth recording because it looks alarming. The raw-topic fallback enters the index
  grammar as a single AND-group, requiring *every* word in the same document: 100% coverage, a
  **stricter** gate than the majority rule, not a missing one. Verified on a three-note store. The
  only real consequence is in the miss direction, on punctuated all-stopword topics.
