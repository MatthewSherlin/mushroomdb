## The merge

- [ ] **Know what breaks between the merge and the npm publish, and pick the merge time
      with that in mind.** The marketplace serves the plugin from the default branch
      (`.claude-plugin/marketplace.json` points at `./packaging/plugin`). From the merge on,
      `packaging/plugin/.mcp.json` and `packaging/plugin/hooks/run.sh` name
      `mushroomdb@0.7.0`, which the npm registry does not have until `publish.yml`'s
      `npm (mushroomdb launcher)` job finishes. In that window:
      - anyone who installs the plugin, or whose marketplace updates, gets an MCP server that
        cannot start and hooks that cannot resolve the launcher;
      - anyone who copies the Claude Desktop block from `docs/site/mcp.md` or `llms.txt`
        (both name `mushroomdb@0.7.0`) gets the same failure.

      A plugin already installed and not updated keeps its 0.6.12 pin and is unaffected. The
      window is as long as: CI on `main`, then the tag, then the three binary builds and
      `github-release`, then `trigger-publish`, then the launcher job. Options the workflows
      allow:
      1. **Merge, then tag, as this checklist is ordered.** The tag sits on the merge commit,
         after CI on `main` is green. The window above is open for that whole sequence; keep
         it short by tagging as soon as `main` is green. If `main` had not moved, that run
         repeats the pull request's on the same tree; keep the wait anyway, because the image
         job does not wait for a test (ledger row 61).
      2. **Tag the branch head before merging**, once the pull request's CI is green, and
         merge after `publish.yml` finishes. `release.yml` runs on any pushed `v*` tag,
         whatever branch the commit is on, so this works and closes the window: the registry
         has 0.7.0 before `main` names it. The costs:
         - The tag's green is the pull request's run, not a run on `main`.
         - The merge must be a true merge commit. A squash or a rebase-merge writes new
           commits, and the tagged commit is then never on `main`.
         - The branch is frozen from the tag to the merge. "Fix on the branch" ends at the
           tag: a commit pushed after it is code no registry carries, and the pull request
           must not be rebased if `main` moves.
         - `release.yml`'s `docker` job pushes the moving `:latest` image from the tagged
           commit, which is not yet on `main`.
         - The registries serve 0.7.0 for a while with `main` still describing 0.6.12.

      Dispatching `publish.yml` by hand from a branch is not a third option: the launcher it
      would publish downloads its binary from the `v0.7.0` GitHub Release, which only the tag
      creates.
- [ ] The next two steps are in option 1's order. Under option 2 the tag section below comes
      first, and the merge follows once `publish.yml` has finished.
- [ ] Merge. **Merging publishes the docs**: `pages.yml` deploys `docs/site/` on a push to
      `main` that touches `docs/site/**` or `docs/assets/**`, and this branch changes sixteen
      files under `docs/site`. If Pages is enabled (not verified from here), the site describes
      0.7 from that moment while every registry still serves 0.6.12. Tag soon after, or accept
      the window.
- [ ] Option 1: wait for CI on `main` to finish green. `release.yml`'s `docker` job needs no
      other job, so it pushes `:latest` without waiting for a binary or a test (ledger row
      61). The tag goes only on a commit already known green.

## The tag — nothing after this can be taken back

- [ ] If anything changed since the rehearsal, run it again first:
      `bash scripts/publish-rehearsal.sh`. It uploads nothing. Its last line names any step
      it skipped.
- [ ] **Confirm the publish credentials before the tag.** `publish.yml` reads one secret,
      `NPM_TOKEN`, in both npm jobs; check in the repository's settings that it exists and has
      not expired. crates.io and PyPI use trusted publishing and read no secret: each of the
      eight crates needs this repository's `publish.yml` as a trusted publisher, and PyPI needs
      it for the `pypi` environment. The registries publish side by side, so an expired npm
      token yields crates and wheels with no launcher.
- [ ] **Confirm no `v0.7` tag is on the remote**: `git ls-remote --tags origin 'v0.7*'` prints
      nothing. Nothing here ran it. A tag already there means `release.yml` has already run,
      or will not run again for a second push of the same name.
- [ ] Tag the commit the ordering you chose names, and push the tag:
      `git tag v0.7.0 <commit>` and `git push origin v0.7.0`.
      - Option 1: `<commit>` is the merge commit on `main`, after `git fetch origin` shows it
        is `origin/main`'s head and its CI is green.
      - Option 2: `<commit>` is the branch head the pull request's CI ran green on, with
        nothing pushed to the branch since.

What that starts. `release.yml` runs on the pushed tag; its `trigger-publish` job then
dispatches `publish.yml` on the same tag. Inside `publish.yml` the crates, PyPI and npm jobs
run side by side and none waits for another, so one registry can be published while another
has failed.

| What | Where | Can it be undone? |
|---|---|---|
| Three binaries, `SHA256SUMS`, the Homebrew formula | the GitHub Release | Deletable — but the npm launcher downloads its binary from it, and so does the formula |
| `:latest` and `:v0.7.0` | `ghcr.io/matthewsherlin/mushroomdb` | Overwritable; images already pulled are out |
| Eight crates, in dependency order, 30 s apart | crates.io | **Never.** Yank only; `0.7.0` cannot be published again |
| Three abi3 wheels | PyPI | **Never** for that version: a deleted file's name cannot be reused |
| `mushroomdb` and `mushroomdb-client` | npm | The number is burned once used |

- [ ] Watch `release.yml`: `binary-<target>` (three), `github-release`, `docker`,
      `trigger-publish`. The release is created as a draft and published by the job's last
      step. If `github-release` fails, a draft is left, `trigger-publish` does not run and no
      registry is touched — but `docker` has already pushed `:latest`.
- [ ] **Do not publish that draft by hand.** `publish.yml` also runs on a release a person
      publishes, and would start the registry publish on a release whose assets are
      incomplete. Re-run the failed job instead.
- [ ] Watch `publish.yml`: `crates.io`, `PyPI` (three builds) and `PyPI upload`,
      `npm (mushroomdb launcher)`, `npm (mushroomdb-client)`, `npx smoke test`.
- [ ] **If the crates job fails part-way, re-run the failed jobs of that `publish.yml` run.**
      The crates step skips a crate already on the index, and both npm jobs skip a version
      already published. `PyPI upload` has no such skip: re-run it only if it failed. Do not
      delete the tag and do not re-tag: a second tag cannot publish again the crates the first
      one landed.
- [ ] `npx smoke test` runs after the launcher is on npm. It detects a broken release; it
      cannot prevent one.
