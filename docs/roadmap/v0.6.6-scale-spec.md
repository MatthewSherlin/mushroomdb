# v0.6.6 — the scale release: design

**Date:** 2026-09-11
**Status:** draft for owner review
**Branches from:** `feat/v0.6.5-knowledge-base` (0.6.5 in flight; Tasks 1–4 landed as of `0e97c55`)
**Owner decision it implements (2026-09-11):** 0.6.5 fixed the blockers on the sidecar report that
were honesty and format work and named two items as deferred with their numbers
(`docs/roadmap/v0.6.5-knowledge-base-spec.md` §10 and §11). This release is those two, plus the
third ACL axis the same report asked for. Nothing here is new product surface; all three are the
engine failing to keep a promise it already makes.

## 1. Goal

Make the vector index something a store can afford, and give visibility a second axis so one store
can hold more than one tenant's graph. Three items. When it ships:

1. Building a vector index does not happen twice, does not happen on every open, and does not
   happen inside a write lock for minutes. A per-embedding write costs one insert into a graph,
   not one insert plus a scan of every other vector in it.
2. A `VectorSimilar` rule finds its candidates through that index instead of comparing every pair.
   The scores stay exact — only the candidate set becomes approximate, with a measured floor.
3. A namespace is a visibility axis beside roles and masks: a role may be bound to namespaces, a
   read under that role sees only those, a rule is either scoped to one namespace or global, and no
   edge crosses a namespace boundary unless a global rule put it there. An existing store is one
   implicit default namespace and nothing about it is rewritten.

No format bump. §3–§6 change the contents of one opaque blob that already exists inside the V9
snapshot; §7 adds a node property, an appended rule field and a `roles.json` version. The
`format-compat` contract — V5…V9 open, migrate and preserve data — is untouched, and V9 stays V9.

## 2. What we learned

The numbers below come from two places and the distinction matters.

**The deployment report** (the owner's team, running the engine as a sidecar graph beside a
document knowledge base) is **not** a committed measurement in this repository. No number from it
may appear in `README.md`, `docs/site/**`, `llms*.txt` or `CHANGELOG.md`. It is carried here so
0.6.6 starts from measurements rather than memory, exactly as `v0.6.5-knowledge-base-spec.md` §11
carried it.

| Finding | Reported | Item |
|---|---|---|
| HNSW build is superlinear and welded to rule creation | 23 s at 2,000 documents; 252 s at 10,000; 50,000 unfinished inside ten minutes | §3, §4 |
| Per-write cost once the index exists | about 111 ms per embedding write | §3 |
| So the sidecar runs brute-force vector search instead | about 5 ms at 2,000; 106 ms unmasked at 50,000 | §6 |
| The exact rule that would replace an external vector index is quadratic | about 41 s at 5,000 | §6 |
| Masks are key allow-lists; no namespaces | — | §7 |

**This repository's own committed measurement** corroborates the first line and may be quoted,
because it is a test that runs in CI. `.github/workflows/ci.yml:36-37` records, against
`crates/sim-harness/tests/oracle_equivalence.rs:1825` (`approximate_recall_5k_timing`, 5,000 nodes
× 1,536 dimensions, `approximate: true`):

> this test takes ~4.5 min (HNSW backfill 227 s + exact O(n²) ground truth ~43 s)

227 s to build a 5,000-vector index inside `create_rule`, and 43 s for the brute-force pass the
exact rule would do — the same two costs the deployment report hit, measured here, in CI, today.
Those are the two numbers 0.6.6 is allowed to quote as *before*, and the only ones.

## 3. Incremental HNSW: stop building indexes nobody keeps

### 3.1 What is true today (read, not assumed)

The index is **already incremental on the write path**. `SideIndex::insert`
(`crates/core-rules/src/index.rs:777-786`) calls `HnswIndex::insert` for one node, and
`SideIndex::remove` (`index.rs:837-845`) calls `HnswIndex::remove`. Nothing rebuilds on a normal
write. The cost is not in the shape of the write path; it is in four concrete places.

**(a) Every open builds an index and then throws it away.** `reindex_all_load_ivf`
(`crates/core-rules/src/engine.rs:2054-2106`) calls `init_hnsw` on both sides of every approximate
rule (`engine.rs:2069-2075`) *before* its node scan, so the scan inserts every vector into a fresh
HNSW graph — the full build. Its two callers then immediately discard the result:

```rust
// crates/core-rules/src/engine.rs:2233-2235  (consume_retained_state_eager)
self.reindex_all_load_ivf(ids, syms, labels, props, ivf);
// Override the incrementally-built HNSW with the persisted blob (better).
self.load_hnsw_state(hnsw);
```

and again at `engine.rs:2508-2509` (`ensure_indexes_populated`). The comment at `engine.rs:2089-2090`
states the intent plainly — *"HNSW was built incrementally; it will be replaced by
`load_hnsw_state`"* — and that is the defect: the replacement is correct and the build before it is
pure waste. A store with a 10,000-vector rule pays the whole build on every open, WAL-present or
clean, and then drops it. `reindex_all` (`engine.rs:1999-2043`) does the same `init_hnsw` at
`:2013-2020`, and there the build is genuinely needed — no blob exists.

**(b) A re-insert is O(N).** `HnswIndex::insert` removes an existing id before re-inserting
(`crates/core-rules/src/hnsw.rs:280-283`), and `HnswIndex::remove` ends with a scan of **every
remaining node** to strip back-references:

```rust
// crates/core-rules/src/hnsw.rs:427-431
for other_node in self.nodes.values_mut() {
    for layer in other_node.layers.iter_mut() {
        layer.retain(|&x| x != id);
    }
}
```

The file already names the fix and its cost (`hnsw.rs:421-426`): *"O(N·M) where N = live nodes and
M = max neighbors per layer … The fix (v0.3 candidate) is a reverse-adjacency map"*. At 50,000
nodes with M₀ = 128 that is 6.4 M vector retains per changed embedding, which is the reported
111 ms per embedding write, and it fires on **every** embedding update because an update is a
remove plus an insert.

**(c) The per-insert constant saturates as the graph fills, which is what "superlinear" is.** An
insert beam-searches with `EF_CONSTRUCTION = 400` (`hnsw.rs:42`) and links up to `M₀ = 128`
neighbours at layer 0 (`hnsw.rs:40`). For each of those neighbours that is now over-connected, the
prune block at `hnsw.rs:350-378` clones the neighbour's whole vector and re-scores its entire
adjacency list — `O(M₀² × dim)` ≈ 128 × 129 × 1,536 ≈ 25 M multiply-adds per insert, but **only
once the neighbourhood is saturated**. At 2,000 nodes most neighbours are under the cap and the
block rarely fires; at 10,000 nearly all of them are over it. That is the mechanism behind 11.5 ms
per insert at 2k becoming 25 ms at 10k. Every distance is also a `BTreeMap<u32, HnswNode>` lookup
(`hnsw.rs:167-171`), so each of the ~51,200 candidate evaluations per insert pays a B-tree descent
before it touches a float.

**(d) The prune is not the algorithm's.** `hnsw.rs:342-378` keeps the M nearest neighbours. The
paper's §3.5 diverse-neighbour heuristic keeps a *diverse* set instead, which is why the file
itself says so at `hnsw.rs:35-37`: *"it does NOT remove the structural pathology — the HNSW §3.5
diverse-neighbour heuristic is the true fix, ledgered for v0.4.3+"*. M₀ was raised 64 → 128 as a
workaround, and the prune cost is quadratic in M₀.

**Persistence today.** The blob is opaque to the container: `HnswSectionData { rules:
Vec<HnswRuleEntry> }` holds two `Vec<u8>` per rule (`crates/core-storage/src/v8/layout.rs:166-183`),
written as section 6 (`crates/core-storage/src/v8/mod.rs:73-74`, encoded at
`crates/core-storage/src/v8/encode.rs:190`, `:237`). `export_hnsw_blob` is `bincode::serialize`
(`index.rs:1243-1248`) and `load_hnsw_blob` is `bincode::deserialize` with a silent
failure-to-`None` (`index.rs:1255-1264`). **The snapshot container therefore does not need to know
anything changed inside the blob**, which settles the format question in §3.4.

### 3.2 New behaviour

Four changes, each answering one of (a)–(d).

**(a) Load before you build, and skip what the load already has.** `init_hnsw` grows a sibling:

```rust
// crates/core-rules/src/index.rs
/// Initialise the HNSW graph for this side, or adopt `blob` when one was
/// persisted. Returns the node ids the adopted graph already holds, so the
/// open-time scan can skip re-inserting them.
pub fn init_or_adopt_hnsw(&mut self, rule_name: &str, blob: &[u8]) -> BTreeSet<u32>;
```

`reindex_all_load_ivf` (`engine.rs:2054`) takes the HNSW blob map as a parameter instead of having
it applied afterwards, calls `init_or_adopt_hnsw` at `:2069-2075`, and its node scan passes the
adopted-id set down so `SideIndex::insert`'s Hnsw arm (`index.rs:777-786`) inserts into
`hnsw_tracked` but **not** into the graph for an id the graph already holds. The two call sites
that discarded the build (`engine.rs:2233-2235`, `:2508-2509`) lose their `load_hnsw_state` line
because the load now happens first. `load_hnsw_state` stays public and is unchanged for
`reindex_all`, which still builds when no blob exists.

A node written after the snapshot is not in the adopted set, so WAL replay inserts it — which is
what makes the load *incremental* rather than a rebuild: the persisted graph is the base, the WAL
frames are the delta, and nothing is built twice.

**(b) Reverse adjacency.** `HnswIndex` gains one field:

```rust
// crates/core-rules/src/hnsw.rs
/// node id → the ids that list it as a neighbour, on any layer.
/// Maintained in lockstep with `HnswNode::layers` by insert/remove/prune.
/// Turns removal from O(live nodes × M₀) into O(in-degree).
back_refs: BTreeMap<u32, BTreeSet<u32>>,
```

`remove` (`hnsw.rs:403-449`) replaces the whole-index scan at `:427-431` with a walk of
`back_refs[&id]`. The defensive scan is not weakened — it is *replaced* by the structure that makes
it unnecessary, and a debug-only `debug_assert!` in a test helper verifies the two agree.

**(c) Dense slot storage.** `nodes: BTreeMap<u32, HnswNode>` becomes a slot vector plus a map:

```rust
slots: Vec<HnswNode>,               // dense, contiguous; free slots reused
slot_of: BTreeMap<u32, u32>,        // node id → slot
id_of: Vec<u32>,                    // slot → node id
free: Vec<u32>,                     // reclaimed slots
```

`dist_to` becomes an index, not a descent. Adjacency lists hold **slots**, so a beam step is a
pointer offset. `node_ids()` (`index.rs:1261` depends on it) iterates `slot_of.keys()`.

**(d) The §3.5 heuristic, and smaller M.** The prune block at `hnsw.rs:342-378` is replaced by
`select_neighbors_heuristic(candidates, m)`: walk candidates nearest-first, keep one only when it
is closer to the query than to every already-kept neighbour. That is the paper's Algorithm 4, it
allocates nothing per candidate, and it is what lets M₀ come back down. See §5 for the parameters
and the recall gates that decide them.

### 3.3 Retraction and deletes

`SideIndex::remove` (`index.rs:837-845`) already fires on node delete and on an embedding change,
because the rule engine removes then re-inserts a changed node. With (b) that path stops being
O(N). No tombstones are introduced: with reverse adjacency an eager removal is cheap, and a
tombstone would make `len()` and the recall gates lie.

### 3.4 Implications

- **No snapshot format change, and no sidecar index file.** Section 6 already carries the index as
  two opaque `Vec<u8>` per rule; only the bytes inside change. A sidecar file would add a second
  durability object to back up, restore and keep consistent with the snapshot — exactly the
  operational surface `docs/site/service.md` was written to shrink — for no benefit the opaque
  section does not already give.
- **The blob gets its own version, inside itself.** `export_hnsw_blob` writes
  `HnswBlob { magic: b"MHNS", version: 2, index }`; `load_hnsw_blob` reads version 2, falls back to
  bincode-decoding today's bare `HnswIndex` as version 1, and up-converts in memory by rebuilding
  `back_refs` and the slot arrays from the decoded layers — no re-insert, no distance computed. An
  unrecognised version is ignored exactly as a corrupt blob is today (`index.rs:1259`), which leaves
  the rule on its `hnsw_tracked` full-scan fallback: **slower, never wrong**.
- **A 0.6.5 binary meeting a 0.6.6 blob** fails its `bincode::deserialize::<HnswIndex>` and falls
  back to the same full scan. No data loss, no format bump, no downgrade refusal needed.
- Memory: `back_refs` costs one `u32` per directed adjacency entry — at M₀ = 32 (§5) that is under
  half what the current M₀ = 128 adjacency itself costs, so the total is **lower** than today.
- Graph structure changes, so a 0.6.6 index is not byte-identical to a 0.6.5 one. Determinism
  within a version is preserved: levels still come from `gen_level` (`hnsw.rs:64-74`), the heuristic
  is order-deterministic, and replay of the same WAL against the same seed yields the same graph.
  The existing replay-identity tests are the gate.

### 3.5 Tests

- `crates/core-rules/src/hnsw.rs` unit tests: `back_refs_match_a_full_scan` — after 500 inserts, 100
  removes and 100 re-inserts of a fixed vector set, assert that for every node id `i`, the set of
  nodes listing `i` in any layer equals `back_refs[&i]`. `remove_is_not_a_full_scan` — build 5,000
  nodes, time 50 removals, assert the mean is under 5 ms (today's whole-index scan is ~100×
  that at this size; the assertion is a floor on the structure, not a wall-clock claim).
- `crates/core-api/tests/rules.rs`: `reopening_does_not_rebuild_the_vector_index` — build a store
  with an approximate rule over 400 vectors, snapshot, reopen, and assert through a counter gated on
  `#[cfg(test)]` (`HnswIndex::insert` call count, thread-local, in the style of `DELTA_COPY_COUNT`,
  `crates/core-api/src/db.rs:3322-3323`) that **zero** inserts ran during the open. This is the test
  that would have caught (a).
- `crates/core-api/tests/snapshot_rules.rs` case 6 (`VectorSimilar`, added by 0.6.5 Task 4) keeps
  passing unedited: derived edges survive a snapshot and a write after the reopen retracts exactly
  the right subset.
- The existing recall gates — `hnsw_5k_1536_recall` (`hnsw.rs:647`, min ≥ 0.90 / mean ≥ 0.95),
  `approximate_recall_above_floor_1536dim_1k` and `approximate_recall_5k_timing`
  (`crates/sim-harness/tests/oracle_equivalence.rs:1825`) — pass **unedited**. They are the
  acceptance criterion for (d) and for §5's parameters.

## 4. `create_rule` stops blocking writes

### 4.1 What is true today

`GraphDb::create_rule` (`crates/core-api/src/db.rs:5533`) WAL-logs and applies; the apply arm at
`db.rs:3300-3318` calls `RuleEngine::create_rule` (`engine.rs:2514`) under the write lock. That
function does the whole job inline: `ensure_indexes_populated` (`engine.rs:2524`), `init_hnsw`
(`:2540-2546`), a scan inserting every node into the new index (`:2548-2555`), an IVF fit
(`:2557-2563`), then the streaming backfill (`:2565` onward, `apply_streaming_create` at
`engine.rs:1268`). The 227 s in `.github/workflows/ci.yml:36` is that one call.

There is already a mechanism for "do more work in a second commit": `take_rebuild_needed`
(`engine.rs:1952`) drains rule names and `db.rs:4259-4275` issues `WalRecord::RebuildRule { name }`
as a follow-up commit after the triggering write. `rebuild_rule` is public (`db.rs:5641`).

### 4.2 New behaviour

`create_rule` keeps its synchronous shape whenever it can finish promptly, and hands off when it
cannot. One constant decides:

```rust
// crates/core-rules/src/index.rs
/// Vectors inserted into a rule's HNSW graph per build slice. A slice is the
/// unit of work `create_rule` does inline and `pump_index_build` does per call.
pub const HNSW_BUILD_BATCH: usize = 2_048;
```

- **Corpus ≤ `HNSW_BUILD_BATCH` vectors per side.** Everything happens exactly as today, in one
  commit, byte-identical results. Every existing test is in this regime and none of them change.
- **Larger.** `create_rule` indexes the non-vector legs (they are O(n) and cheap), inserts the first
  slice, installs the rule with **no derived edges**, and records the remainder:

```rust
// crates/core-rules/src/engine.rs
/// How far a rule's vector index has got, for rules whose build did not fit
/// in one commit. Never persisted: a reopen re-derives it from the adopted
/// graph and the node scan.
#[derive(Clone, Debug, PartialEq, Serialize)]
pub struct BuildProgress { pub rule: String, pub indexed: u64, pub total: u64 }

impl RuleEngine {
    /// Rules whose vector index is still being built, in name order.
    pub fn builds_in_progress(&self) -> Vec<BuildProgress>;
    /// Advance every pending build by one slice. Returns the rules that
    /// finished, which the caller must then `rebuild_rule`.
    pub fn pump_index_build(&mut self, g: &mut GraphMut<'_>) -> Vec<String>;
}
```

```rust
// crates/core-api/src/db.rs
/// Advance any vector index still building; backfill each rule that finishes.
///
/// Returns what is still outstanding. Safe to call on a store with nothing
/// pending (it is then a map lookup). Each call takes one write lock and does
/// at most `HNSW_BUILD_BATCH` inserts per pending rule, so a caller can drive a
/// large build to completion without holding the lock for more than a slice.
pub fn pump_index_build(&mut self) -> Result<Vec<BuildProgress>>;
```

A finished build issues `WalRecord::RebuildRule { name }` through the existing second-commit path
(`db.rs:4259-4275`), which runs the backfill exactly as `rebuild_rule` does today. So the derived
edges a large `create_rule` produces are produced by code that already exists and is already
tested; only *when* changes.

**Who pumps.**

1. Any write. The post-commit hook at `db.rs:4259-4275` already runs after every durable op; it
   gains one slice of build work beside the rebuild drain. A store being written to finishes its
   build on its own.
2. `mushroomdb serve`. `crates/cli/src/main.rs:554-581` already drives a `--snapshot-every` ticker;
   a second ticker at a fixed 1 s calls `pump_index_build` and logs one line per completion. A
   quiescent server still finishes.
3. Explicitly. `mushroomdb build-index <db> [--rule <name>]` pumps to completion with a progress
   line, for an operator who wants the build done before traffic arrives.

**What a caller sees while it builds.** `RuleStats` (`db.rs:288-300`) gains
`building: Option<BuildProgress>`; `stats` reports it on HTTP, MCP and Python. `POST /rules`
(`crates/server/src/http.rs:377`, `:1166`) returns `202 Accepted` with
`{"rule": "...", "building": {"indexed": N, "total": M}}` instead of its current success body when
the build did not fit in one commit, and `200` unchanged when it did. A rule that is still building
derives no edges and says so; it never derives a *partial* set, because the backfill is one commit
that happens after the index is whole.

### 4.3 Implications

- **Additive Rust API** (`pump_index_build`, `builds_in_progress`, `BuildProgress`), one additive
  field on `RuleStats`, one new HTTP status on an existing route, one new CLI command.
- **Behaviour change, named in the changelog:** `create_rule` on a corpus above the slice size
  returns before the edges exist. Anything that created a rule and immediately asserted its edge
  count now has to pump first — including, potentially, tests in this repository; Task 2's Step 4
  finds them by running the workspace.
- No format change, no WAL change (`RebuildRule` is discriminant 9 already,
  `crates/core-storage/src/wal.rs:399`).
- `BuildProgress` is never persisted. A store that is killed mid-build reopens with the rule present
  and its index partly built; the adopted blob covers what was snapshotted and the open-time scan
  covers the rest, so the reopen completes the build rather than restarting it.

### 4.4 Tests

`crates/core-api/tests/rules.rs`:
- `create_rule_under_the_slice_is_one_commit` — 100 vectors, assert the edges exist the moment
  `create_rule` returns and `builds_in_progress()` is empty. This is the compatibility half.
- `create_rule_over_the_slice_defers_the_backfill` — with `HNSW_BUILD_BATCH` overridden to 64 via
  the thread-local test hook that `with_ivf_drift_rebuild` (`index.rs:40`) already models, seed 300
  vectors, assert `create_rule` returns `Ok`, the rule is listed, its edge count is 0, and
  `builds_in_progress()` names it with `indexed == 64`.
- `pump_finishes_the_build_and_backfills` — pump in a loop until `builds_in_progress()` is empty,
  then assert the derived edge set is **exactly equal** to the set the same rule produces on the
  same seed when created under the one-commit path. Deferring must not change the answer.
- `a_write_pumps_the_build` — same store, no explicit pump; insert unrelated nodes until the build
  finishes; assert the same edge set.
- `an_interrupted_build_resumes_on_reopen` — pump one slice, snapshot, drop, reopen, pump to
  completion, assert the same edge set.

`crates/server/tests/http.rs`: `POST /rules` on a large store returns 202 with a `building` body and
`GET /stats` shows the progress; on a small store it returns its current 200 body unchanged.

## 5. Parameters, the benchmark, and the recall floor

### 5.1 What is true today

`crates/core-rules/src/hnsw.rs:26-44`: `MAX_LEVEL = 16`, `M = 32`, `M0 = 128`,
`EF_CONSTRUCTION = 400`, `EF_SEARCH = 400`. Search uses `ef = k.max(EF_SEARCH)` (`hnsw.rs:466`).
They are module constants with no override and no documentation outside that file — `docs/site/`
does not state them anywhere. The doc comment at `hnsw.rs:30-39` explains M₀ = 128 as a workaround
for the missing §3.5 heuristic and discloses its memory cost.

### 5.2 New behaviour

One struct, one default, one env override, and a page that says what they mean.

```rust
// crates/core-rules/src/hnsw.rs
/// Index shape. Store-wide, not per rule: nothing in the deployment report
/// asked to tune one rule differently from another, and a per-rule parameter
/// set would have to be persisted in `RuleDef` and versioned with it.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct HnswParams {
    /// Max connections per layer above layer 0.
    pub m: usize,
    /// Max connections at layer 0.
    pub m0: usize,
    /// Beam width during insertion.
    pub ef_construction: usize,
    /// Beam width during search; the floor under a query's own `k`.
    pub ef_search: usize,
}

impl Default for HnswParams {
    fn default() -> Self {
        Self { m: 16, m0: 32, ef_construction: 200, ef_search: 128 }
    }
}

/// Read once, from `MUSHROOMDB_HNSW_PARAMS` as `m,m0,ef_construction,ef_search`.
/// Unset or unparseable → `HnswParams::default()`. For benchmarks and for an
/// operator who has measured their own corpus; not a per-rule knob.
pub fn hnsw_params() -> HnswParams;
```

M₀ falls 128 → 32 because §3's §3.5 heuristic is the thing M₀ = 128 was standing in for, and the
prune cost is quadratic in M₀ — a 16× reduction in the per-insert constant that §3.1(c) identified.
`ef_construction` and `ef_search` fall with it because a diverse graph routes in fewer hops.

**These four numbers are decided by the gates, not by this document.** The plan's Task 3 sets them
to the defaults above, runs the three existing recall gates unedited, and — if any fails — raises
`ef_construction` in steps of 64 (then `m0` in steps of 16) until all three pass, and records the
values that passed in the commit message and in `docs/site/indexes.md`. A parameter set that cannot
pass `hnsw_5k_1536_recall`'s min ≥ 0.90 / mean ≥ 0.95 is not shipped.

**Documentation.** `docs/site/indexes.md` gains a section stating each parameter, its default, what
raising it buys and costs, the memory per indexed vector at the default (`m0 × 4` bytes of layer-0
adjacency plus `dim × 8` bytes of vector), and `MUSHROOMDB_HNSW_PARAMS`. It states the recall the
committed gates assert and names the test that asserts it.

### 5.3 The scale benchmark

New file `crates/core-rules/tests/hnsw_scale.rs`, at the index level so it measures the index and
not the rule engine. `#[ignore]` and additionally gated on an environment variable so it cannot run
by accident:

```rust
/// Insert cost at 2k / 10k / 50k, 1,536-D. Prints a table and asserts the
/// growth is sub-quadratic and the 50k case finishes.
///
/// Gated twice: `#[ignore]` keeps it out of `cargo test --workspace`, and
/// `MUSHROOMDB_BENCH_HNSW=1` keeps it out of an `--ignored` sweep that did not
/// mean to spend ten minutes. Run:
///   MUSHROOMDB_BENCH_HNSW=1 cargo test --release -p mushroomdb-rules \
///     --test hnsw_scale -- --ignored --nocapture
#[test]
#[ignore = "slow: builds a 50k-vector index; set MUSHROOMDB_BENCH_HNSW=1"]
fn hnsw_insert_cost_is_sublinear_per_vector() {
    if std::env::var("MUSHROOMDB_BENCH_HNSW").as_deref() != Ok("1") { return; }
    const DIM: usize = 1_536;
    let sizes = [2_000usize, 10_000, 50_000];
    let mut build = Vec::new();     // total build seconds per size
    let mut update = Vec::new();    // mean seconds per single re-insert at that size

    for &n in &sizes {
        let vecs = make_unit_vecs(n, DIM, 0xB0A7_5EED);
        let mut idx = HnswIndex::new(fnv1a_u64(b"bench"));
        let t0 = Instant::now();
        for (i, v) in vecs.iter().enumerate() { idx.insert(i as u32, v); }
        build.push(t0.elapsed());

        // Per-write cost once the index exists: re-insert 100 existing ids,
        // which is exactly what an embedding change costs.
        let t1 = Instant::now();
        for i in (0..n).step_by(n / 100).take(100) { idx.insert(i as u32, &vecs[i]); }
        update.push(t1.elapsed() / 100);

        println!("n={n:>6}  build {:>8.2?}  per-insert {:>8.3?}  update {:>8.3?}",
                 build[build.len()-1],
                 build[build.len()-1] / n as u32,
                 update[update.len()-1]);
    }

    // (1) Sub-quadratic build. Each step multiplies n by 5. Linear would cost
    //     5x; quadratic 25x. 8x is comfortably sub-quadratic and leaves room
    //     for the log(N) descent term and for CI noise.
    let r1 = build[1].as_secs_f64() / build[0].as_secs_f64();
    let r2 = build[2].as_secs_f64() / build[1].as_secs_f64();
    assert!(r1 < 8.0, "2k→10k build grew {r1:.2}x for 5x the vectors; must be < 8x");
    assert!(r2 < 8.0, "10k→50k build grew {r2:.2}x for 5x the vectors; must be < 8x");

    // (2) The case that did not finish in ten minutes must finish in five.
    assert!(build[2] < Duration::from_secs(300),
            "50k build took {:?}; must be under 5 minutes", build[2]);

    // (3) A changed embedding must not cost a scan of the index. Flat, not
    //     growing: the 50k update must be within 3x the 2k update.
    let u = update[2].as_secs_f64() / update[0].as_secs_f64();
    assert!(u < 3.0, "update cost grew {u:.2}x from 2k to 50k; removal is still O(N)");
    assert!(update[2] < Duration::from_millis(25),
            "a 50k embedding update took {:?}; must be under 25 ms", update[2]);
}
```

Assertion (3) is the one that fails today: the whole-index scan in `remove` makes the 50k update
roughly 25× the 2k update. Assertions (1) and (2) are the deployment report's two claims turned
into gates.

The printed table's numbers are the **only** vector-index numbers permitted into `CHANGELOG.md` and
`docs/site/indexes.md`, and they are quotable only alongside the 227 s already committed in
`.github/workflows/ci.yml:36`.

### 5.4 Recall versus brute force

Recall is already gated in CI and stays gated. `hnsw_5k_1536_recall` (`hnsw.rs:645-694`) asserts
min recall@10 ≥ 0.90 and mean ≥ 0.95 over 50 queries against 5,000 random 1,536-D vectors, with
exact brute-force k-NN as ground truth. `approximate_recall_5k_timing` asserts a floor on the whole
derived edge set against an O(n²) ground truth. **0.6.6 does not edit either test**; passing them
unchanged under the new parameters and the new prune is what makes §3(d) and §5.2 shippable.

One test is added, because the existing two cover the approximate path and §6 needs the exact one:
`exact_vector_rule_recall_5k` in `crates/sim-harness/tests/oracle_equivalence.rs`, a copy of
`approximate_recall_5k_timing` with `approximate: false`, asserting recall ≥ 0.98 against the same
O(n²) ground truth and printing the wall clock beside the 227 s the approximate one records.

## 6. `VectorSimilar` rules find candidates through the index

### 6.1 What is true today

`candidate_spec` maps `VectorSimilar` to `ScanAll` (`crates/core-rules/src/index.rs:422`);
`candidate_spec_approx_with_k` maps it to `Hnsw` (`index.rs:465`). `candidate_spec_for`
(`engine.rs:291-301`) picks between them on `def.approximate`. So an exact rule's candidate set is
every node in the `SCAN_ALL_SENTINEL` bucket (`index.rs:637`, populated at `index.rs:810-821`) —
every vector on the other side — and `compute_desired` (`engine.rs:356`) evaluates the predicate for
each. That is the quadratic: 41 s at 5,000 reported, 43 s for the equivalent ground-truth pass
measured in this repository (`.github/workflows/ci.yml:36`).

There is a real optimisation on that path — the Cauchy-Schwarz suffix-norm early exit
(`engine.rs:428-471`, gated on `!def.approximate`, backed by `vec_meta` / `vec_checkpoints` /
`vec_anchor`, `index.rs:810-821`). It prunes pairs, not the O(n) walk over candidates, so the pass
stays linear per source and quadratic per rule.

### 6.2 New behaviour

**Candidate generation moves to the index for every `VectorSimilar`-rooted rule; scoring does not
move at all.** `candidate_spec` keeps returning `ScanAll` (it is the honest description of the
predicate, and `spec_is_scan_all_universe` at `index.rs:1007` depends on it inside `Intersect`), and
`candidate_spec_for` (`engine.rs:291-301`) is the one place that changes:

```rust
fn candidate_spec_for(def: &RuleDef) -> CandidateSpec<'_> {
    // Both exact and approximate rules probe the index. The difference is the
    // beam: an approximate rule takes one pass at k; an exact rule widens the
    // beam until the beam's own worst hit falls below the rule's `min`, at
    // which point nothing outside it can qualify.
    let k = def.max_edges.map(|me| me.max(128)).unwrap_or(128) as usize;
    candidate_spec_approx_with_k(&def.predicate, k)
}
```

`CandidateSpec::Hnsw` gains the floor:

```rust
// crates/core-rules/src/index.rs
Hnsw {
    field: &'a str,
    k: usize,
    /// `Some(min)` for an exact rule: widen the beam until the worst hit the
    /// beam returns is below `min`, so a qualifying node cannot be sitting
    /// outside a truncated beam. `None` for an approximate rule: one pass at
    /// `k`, which is today's behaviour.
    floor: Option<f64>,
},
```

`hnsw_candidates` (`index.rs:1222-1238`) implements the widening:

> Search at `ef = max(k, ef_search)`. If `floor` is `Some(min)` and the **worst** similarity the
> search returned is still ≥ `min`, the beam was truncated at the floor and there may be more:
> double `ef` and search again, up to `EF_MAX = 4096` or until the index is exhausted
> (`ef >= index.len()`). Stop as soon as the worst returned similarity is below `min`, because
> every node the beam then rejected is farther than a node already known to fail the predicate.

The rule's `min` is therefore a stopping rule and not just a filter, which is why a rule with a
selective `min` — the case the deployment report is about, semantic edges between documents — is
both fast and complete in practice: the beam stops as soon as it has passed the floor.

**Scoring is untouched.** `compute_desired`'s per-pair evaluation (`engine.rs:472` onward) runs on
the candidates it is handed, exactly as it does now, with the same `evaluate()` and the same
`weight_prop`. Every score, every tie-break, every `filter_src_top_k` (`engine.rs:1338`) is the
code that runs today. Only the set fed into it is smaller.

**The early-exit metadata follows the vectors.** `vec_meta`, `vec_checkpoints` and `vec_anchor` are
maintained today only in the `ScanAll` arm (`index.rs:810-821`). Exact rules now take the `Hnsw` arm
(`index.rs:778-786`), so those three lines move into a shared helper both arms call, and the
Cauchy-Schwarz early exit keeps working for exact rules. Nothing about its correctness changes —
`fresh_ckpts_for` (`index.rs:929-956`) still refuses stale checkpoints.

**Retraction on an embedding change** is the existing remove/insert pair (`index.rs:837-845`), now
firing for exact rules too, and now O(in-degree) after §3(b).

**An escape hatch, for the equivalence test and for a caller who needs the guarantee.**
`MUSHROOMDB_VECTOR_SCAN=1` forces `candidate_spec_for` back to `candidate_spec`, in the shape
`vector_early_exit_enabled()` (`index.rs`, used at `engine.rs:448`) and
`vector_dim_reject_enabled()` (`index.rs:986`) already establish. It exists so the equivalence test
can compare the two paths in one process, and it is documented as the way to pay O(n²) for a
guarantee.

### 6.3 Implications

- **Behaviour change, named in the changelog and the docs.** An exact `VectorSimilar` rule's derived
  edge set is no longer provably every pair above `min`; it is every pair above `min` that the beam
  found, with a committed recall floor. The alternative — leaving it quadratic — is what made the
  sidecar keep its semantic edges on an external vector index, which is the thing this release is
  for. `docs/site/rules.md` and `docs/site/indexes.md` say it in one sentence each and name
  `MUSHROOMDB_VECTOR_SCAN`.
- `explain_association` is unaffected: provenance records which rule derived an edge, not how its
  candidates were found.
- No format change. `RuleDef` is not touched by this item at all.
- Rules with `approximate: true` behave exactly as today (`floor: None`, one pass at `k`).

## 7. Namespaces

### 7.1 What is true today, and what it rules out

A **key** is an opaque string. Nothing validates its shape: `check_insert_node`
(`crates/core-api/src/db.rs:10735-10741`) checks only for a duplicate. Keys are the currency of
almost every surface — `node_info`, `node_edges`, `neighborhood`, `was_linked`, `edges_at`,
`node_history`, `edge_history`, `rename_node`, every mask entry (`crates/core-api/src/mask.rs:53`),
every `RoleDef.keys` entry (`crates/core-api/src/roles.rs:81`), and Cypher's `key(n)`
(`db.rs:888-896`).

A **label** is one symbol per node: `self.labels[id]` is a single `u32` (the label leg of
`mask_for_role` scans it at `db.rs:6356-6364`). A node cannot carry a second label, so a namespace
cannot be one.

Three facts decide against the `<ns>/<key>` prefix:

1. **Shipped stores already put `/` in keys.** `ingest-git` keys a `File` node on its repository
   path (`crates/cli/src/ingest_git.rs:562-580` builds `id`/`path` from it,
   `:1608` ingests `File` rows on it), so keys like `crates/core-api/src/db.rs` exist in this
   repository's own store. `<ns>/<key>` cannot be parsed out of that without guessing, and the
   implicit default namespace would have to be the empty prefix, which is the ambiguity again.
2. **`KeyMatch` joins a property value to a key.** `compute_desired` resolves the FK field's string
   value through `g.ids.get(target_key)` (`engine.rs:389-407`). Prefixing keys means prefixing every
   FK property value in lockstep, across a live store, or the rule finds nothing and retracts every
   edge it owns — the v0.5.x data-loss shape, reintroduced by a migration.
3. **Every key on every wire would change value.** `key(n)`, every history body, every mask, every
   role's `keys` list. That is a breaking change to roughly every surface in the product, to express
   something that does not need to live in the key at all.

### 7.2 New behaviour: a namespace is a reserved, immutable node property

```rust
// crates/core-api/src/db.rs
/// The reserved property that names a node's namespace.
///
/// Absent means the default namespace. Writing `NS_DEFAULT` explicitly stores
/// nothing, so a store that never leaves the default namespace carries no `ns`
/// column and pays nothing for the feature.
pub const NS_PROP: &str = "ns";
/// The namespace a node with no `ns` property is in.
pub const NS_DEFAULT: &str = "default";

/// Valid namespace name: 1–64 of `[A-Za-z0-9_.-]`.
pub fn valid_namespace(name: &str) -> bool;
```

**Set at insert, immutable after.** `insert_node` and `ingest` accept `ns` like any other property
and validate it. `set_prop`, Cypher `SET`, `MERGE`'s property merge and `upsert_node`'s merge refuse
to change it:

```rust
GraphError::NamespaceImmutable { key: String, from: String, to: String }
// "node {key} is in namespace {from}; a namespace is set at insert and cannot
//  be changed to {to} — delete and re-insert the node instead"
```

`rename_node` preserves it (it changes the key, not the props). Deleting and re-inserting is the
documented way to move a node, and it is honest: moving a node between tenants is a deletion from
one and a creation in the other.

**A derived dense array, never persisted.**

```rust
// crates/core-api/src/db.rs, beside `labels: Vec<u32>`
/// Interned namespace symbol per dense node id; `ns_default_sym` for a node
/// with no `ns` property. Derived: built by one pass over the `ns` column at
/// open, maintained at insert and delete. Never written to a snapshot or the
/// WAL, because the property it mirrors already is.
node_ns: Vec<u32>,
```

The open-time pass is one column read, beside the node scan `reindex_all` already does
(`engine.rs:2022-2032`); on a store with no `ns` column it reads nothing and fills the vector with
one constant.

### 7.3 Roles bind to namespaces — `roles.json` version 4

```rust
// crates/core-api/src/roles.rs
pub struct RoleDef {
    pub name: String,
    pub keys: Vec<String>,
    pub labels: Vec<String>,
    pub visible_where: Option<PropPredicate>,   // 0.6.5 §7
    /// Namespaces this role may read. Absent = unscoped, which is exactly
    /// today's behaviour, so no existing role changes meaning. `Some(list)`
    /// restricts. `Some([])` is rejected at apply time: a role that sees
    /// nothing is written by omitting `keys` and `labels`, not by this.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub namespaces: Option<Vec<String>>,
    pub write: Option<WriteScope>,
}
```

**Resolution, stated once.** With 0.6.5's predicate masks composed in:

```
visible = ( keys ∪ { n : label(n) ∈ labels ∧ visible_where(n) } ) ∩ { n : ns(n) ∈ namespaces }
```

The namespace leg **intersects, and it intersects `keys` too** — unlike `visible_where`, which
narrows only the label leg (0.6.5 §7.2, decision 7 there). A namespace is a tenancy boundary, and an
explicitly named key in another tenant's namespace is a mistake rather than an administrative grant.
`apply_schema` makes the mistake loud: a role whose `keys` name a node that **exists** and is
outside the role's `namespaces` is rejected with both names in the message. A key naming no live
node is still silently ignored, as it is today.

`RolesFile::new_versioned` (`roles.rs:110-117`) picks 4 > 3 > 2 > 1: version 4 is written only when
some role carries `namespaces`. `load_roles_from_fs` (`db.rs:6316-6320`) accepts `1 | 2 | 3 | 4`; 5
and up still poison the roles state, which denies every role — the never-widen direction.

**The memo covers it.** 0.6.5's `RoleMaskCache` is keyed by `commit_seq()`, so the namespace leg
costs one scan per write, not one per call, with no new machinery.

### 7.4 Rules are scoped or global

```rust
// crates/core-rules/src/def.rs, appended after `via_dir`
/// The namespace this rule operates in. `None` = global: it sees every node
/// and its derived edges may cross namespaces. `Some(ns)` = scoped: it sees
/// only nodes in `ns`, so every edge it derives is intra-namespace by
/// construction.
///
/// APPENDED field — the same pre-alpha no-migration ruling as `max_edges`,
/// `approximate` and `via_dir` (def.rs:33, :51): a rule bincoded before this
/// field decodes with `None`, which is the behaviour it had.
#[serde(default)]
pub namespace: Option<String>,
```

Enforcement is **one check in one function**. `index_node_for_rule` (`engine.rs:1580-1597`) is the
sole place a node enters a rule's candidate index; it returns early when `def.namespace` is `Some`
and does not match the node's namespace. Both sides are then namespace-pure, so every derived edge
is intra-namespace without any pair-level check, and a global rule is unchanged code.

Via-hop rules are scoped the same way: the via node is a node, and it is filtered by the same check.

### 7.5 No cross-namespace edges

A user-written edge is refused across a boundary. `prepare_insert_edge`
(`db.rs:10751-10762`) — the single choke-point every insert-edge path goes through — gains:

```rust
GraphError::CrossNamespace { src: String, src_ns: String, dst: String, dst_ns: String }
// "edge {src} → {dst} crosses a namespace boundary ({src_ns} → {dst_ns});
//  only a global rule may derive one"
```

On an existing store every node is in `default`, so nothing that works today stops working.

### 7.6 Time travel

0.6.5's `AsOfScope` gains one variant:

```rust
// crates/core-api/src/db.rs
pub enum AsOfScope<'a> { Role(&'a str), Keys(&'a [String]), Namespace(&'a str) }
```

`AsOfScope::Role` needs no change: `open_at_with` already loads the roles sidecar into the temporal
handle (`db.rs:2700-2701`) and `mask_for_role` resolves against *that handle's* state, so a role's
namespaces resolve against the commit-`c` graph exactly as its labels do. `node_ns` on the temporal
handle is built by the same open-time pass. The semantic that a reader can get wrong is the same one
0.6.5 already documents and is documented again for namespaces in one sentence: **the graph is
historical, the role definition is current.** A node's namespace, unlike its label, cannot have
changed — it is immutable — so there is no second case to explain.

### 7.7 Migration

None. An existing store has no `ns` property on any node, so every node is in `default`; every
existing role has no `namespaces`, so every role is unscoped; every existing rule decodes with
`namespace: None`, so every rule is global; every existing edge is `default → default`. The first
node written with an `ns` is the first moment anything changes. **No snapshot is rewritten, no WAL
record changes shape, and `roles.json` stays at the version it was.**

### 7.8 Implications

- **No format change.** `ns` is an ordinary string property in the columns section (and, after
  0.6.5's shared string table, one entry per distinct namespace name in the whole snapshot).
  `RuleDef.namespace` rides the positional-append ruling the repository has already applied twice.
  `roles.json` is a JSON sidecar with its own version field. V9 stays V9 and `format-compat` is
  untouched.
- **Additive Rust API**: one `RoleDef` field, one `RuleDef` field, one `AsOfScope` variant, two
  error variants, `GraphDb::namespaces()`, `GraphDb::namespace_of(key)`.
- **A new refusal**: `SET n.ns = …` and a cross-namespace `insert_edge`. Both are impossible to hit
  on a store that never used a namespace.
- **`roles.json` version 4 is forward-incompatible by design**: a 0.6.5 binary meeting one poisons
  its roles state and denies every role.
- Memory: one `u32` per node, plus one string column that is empty on a single-tenant store.

## 9. Non-goals

- **Larger-than-RAM.** The graph is in memory; that is the design. A vector index that fits on disk
  is a different product.
- **Distributed anything.** One writer per store directory, enforced by `LOCK`, as
  `docs/site/service.md` says.
- **Removing the code door.** Deprecated in 0.6.4, removed in 0.7. Nothing here touches it.
- **Per-rule index parameters.** §5 makes them store-wide with an env override. A per-rule set has
  to be persisted in `RuleDef` and versioned with it, and nothing asked for it.
- **A second index kind.** IVF stays exactly where it is — legacy, still loaded, still exported, not
  the default (`index.rs:362-371`).
- **Renaming a namespace, or moving a node between namespaces in place.** Delete and re-insert. A
  rename is a mass mutation of an ACL boundary and needs its own design.
- **Namespace-scoped write tokens.** `WriteScope` (`roles.rs:40-59`) is unchanged; a role's writes
  are still bounded by labels and edge types. Namespaces bound reads in 0.6.6.
- **Making the exact `VectorSimilar` rule exact again at scale.** §6 trades a proof for a measured
  floor and says so. `MUSHROOMDB_VECTOR_SCAN=1` is the way back and it costs O(n²).
- **Quantisation, SIMD, or a `f32` vector representation.** All three are real wins and none of them
  are this release; §3 and §5 are about not doing work twice, not about the inner loop.

## 10. Decisions taken on the owner's behalf (revisit if wrong)

1. **No format bump, and no sidecar index file.** Section 6 already carries the index as opaque
   bytes (`v8/layout.rs:166-183`), so the container does not need to know its contents changed. A
   sidecar file would add a second durability object to the runbook 0.6.5 just wrote. The blob
   carries its own magic and version, and an unreadable blob degrades to the existing full-scan
   fallback (`index.rs:1259`) — slower, never wrong, in both directions.
2. **Load the persisted index before the node scan, rather than after it.** Today the scan builds a
   whole index and `load_hnsw_state` throws it away (`engine.rs:2233-2235`, `:2508-2509`). This is
   the single largest win in the release and it deletes code rather than adding it.
3. **Reverse adjacency rather than tombstones.** The file already names reverse adjacency as the fix
   (`hnsw.rs:421-426`). Tombstones would make `len()`, `node_ids()` and every recall gate report a
   graph that is not the one being searched.
4. **The §3.5 diverse-neighbour heuristic ships, and M₀ comes back down to 32.** The heuristic is
   already ledgered in the file as "the true fix" (`hnsw.rs:35-37`), the prune cost is quadratic in
   M₀, and the three recall gates already in CI decide whether the parameters are acceptable. If
   they do not pass at the proposed defaults, the plan raises `ef_construction` until they do and
   records what passed — it does not weaken a gate.
5. **`create_rule` finishes in one commit below `HNSW_BUILD_BATCH` and defers above it.** Every
   existing test is below the threshold and none of them change. The deferred path reuses
   `RebuildRule` and the second-commit machinery that already exists (`db.rs:4259-4275`), so the
   backfill itself is code that already ships.
6. **A background build is pumped, not threaded.** `pump_index_build` takes the write lock for one
   slice and returns. A write pumps it, `serve` pumps it on a ticker, and an operator can pump it
   explicitly. A thread inside `core-api` would own a lock the embedding caller does not know about,
   and `GraphDb` is a single-writer handle by design.
7. **Exact `VectorSimilar` rules get an index-backed candidate set with the rule's `min` as the
   stopping rule.** Widening the beam until its worst hit falls below `min` is what makes a
   selective rule both fast and complete in practice, and it is a better use of `min` than a filter.
   The trade — a proof becomes a measured floor — is stated in the changelog and in two doc pages,
   and `MUSHROOMDB_VECTOR_SCAN=1` buys the proof back.
8. **A namespace is a reserved node property, not a key prefix.** Keys already contain `/` in
   shipped stores (`ingest_git.rs:562-580`), `KeyMatch` joins a property value to a key
   (`engine.rs:389-407`) so prefixing keys means migrating FK values in lockstep, and every key on
   every wire would change value. The property costs one string column and one derived `u32` array.
9. **The namespace is immutable after insert.** A mutable ACL boundary is not one. It also removes
   the only case where time travel would have to explain a namespace that changed.
10. **The namespace leg intersects `keys`, where `visible_where` does not.** 0.6.5 decided an
    explicitly named key is an administrative grant that a property change must not withdraw. A
    tenancy boundary is different in kind, and `apply_schema` rejects the mistake by name rather
    than silently honouring it.
11. **`namespaces: None` means unscoped, not "default only".** Every role that exists today has no
    `namespaces` field, and none of them may change meaning on upgrade. `Some([])` is rejected so
    the ambiguous case cannot be written by accident.
12. **Rule scoping is enforced at `index_node_for_rule` and nowhere else.** One early return makes
    both candidate sides namespace-pure, so no pair-level check is needed and a global rule runs
    exactly the code it runs today.
13. **`AsOfScope` gains `Namespace` rather than a second parameter.** It is one arm on an enum
    0.6.5 is adding this week, and `Role` needs no change at all.
14. **Key-taking tools take no namespace argument.** A key is globally unique; the role already
    hides what it must, and a second way to say the same thing is a second way to get it wrong.
15. **Version 0.6.6, not 0.7.** No format bump, no tool added or removed, no MCP listing moved. Two
    behaviour changes (`create_rule` may defer; exact vector rules use the index) and one new
    refusal, all named in the changelog.

## 11. Sequencing

**§3, §4 and §5 first, and they can start in a worktree while 0.6.5 finishes.** They touch
`crates/core-rules/src/{hnsw.rs,index.rs,engine.rs}`, `crates/core-api/src/db.rs`'s rule-apply and
stats paths, and no file 0.6.5's remaining tasks (5, 6, 7, 8) are editing — those are
`db.rs`'s mask and as-of paths, `roles.rs`, `mask.rs`, `reader.rs`, `http.rs`, `mcp.rs` and

`create_rule`; the benchmark itself is index-level and independent.

**§6 after §3 and §5**, because it depends on the widening beam and on parameters that have passed
their recall gates.

same `mask_for_role` that Task 6 is rewriting and a fourth variant on the `roles.json` version
ladder Task 6 extends to 3, and §7.6 adds a variant to the `AsOfScope` Task 5 introduces. Starting
§7 before those land means writing the same function twice and resolving a merge in the one place in
the codebase where a mistake silently widens access.

**§8 after §7**, and the release commit last.
