# W4 — Self-Hosting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a production-ready self-host story: TLS in the Docker image, `/ready`, CORS, write-tier access keys, Prometheus metrics, JSON logs, continuous S3 WAL-segment backup with restore, PITR, restore-on-boot, a bucket lease, deploy templates for Fly/Render/Railway/Docker Compose/K8s, and CI validation of templates against MinIO.

**Architecture:** A new `crates/backup/` crate owns the `BackupWorker` Tokio task, the `object_store` integration, manifest schema, bucket lease, and the restore download logic. The `mushroomdb-cli` crate spawns `BackupWorker` alongside the serve loop and extends the shutdown sequence to flush uploads and delete the lease. The server crate gains `/ready` (AtomicBool in AppState), CORS (tower-http cors feature flag), a Write tier on `AuthIdentity`, and Prometheus text output on `GET /metrics`.

**Tech Stack:** `object_store` 0.11.x (aws feature, owner-approved §9.1); `tower-http` cors feature (already a dep); `tracing-subscriber` json feature (already a dep); `axum`, `tokio`, existing `mushroomdb` + `mushroomdb-server` + `mushroomdb-cli` crates; flyctl, kubectl, docker for template linting in CI.

**Spec:** `docs/roadmap/v0.10-spec.md` §4.4 and `docs/roadmap/v0.10/W4-hosting.md`

## Review Focus

1. **Partial-frame upload**: if the worker reads wal.bin at a byte boundary that falls inside a WAL frame, the segment is malformed and restore will silently truncate or error — every restore round-trip test must verify the segment count and that `open()` on the restored store produces the same node/edge count as the source.
2. **Generation rollover on truncating snapshot**: a new snapshot replaces `wal.bin`; if the worker does not increment `wal_generation` before uploading the next segment, segment offsets collide with a prior generation — the PITR test must write across at least two snapshot boundaries and verify both generations appear in the manifest.
3. **Restore-on-boot with an active foreign lease**: if a second instance starts, finds a fresh foreign lease, but still restores (race between lease check and restore start), it may write over the primary — the dual-instance test must assert that only one instance proceeds to serve after lease check.
4. **SIGHUP key reload races**: the `keys.json` reload on SIGHUP must be atomic (swap the whole map under a lock); a test must verify that a request in flight during reload gets exactly one key set, not a mix of old and new.
5. **Segment continuity gap on restart**: if the server crashes between two segments, the next boot uploads from where the last successful segment ended — the crash-then-restart test must verify no gap in the uploaded segment sequence and that restore of "latest" includes all committed frames.
