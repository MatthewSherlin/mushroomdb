# v0.6.3 — the association release: design

> **Closed 2026-09-11 (v0.6.4).** Closed with its plan. Its gate failed on the cost interval alone
> after the fixes (0.967 vs 0.974, $0.0923 vs $0.1158); the suite it specified is the one 0.6.4
> keeps.

**Date:** 2026-09-10
**Status:** draft for owner review
**Owner decision it implements (2026-09-10):** the 0.6.2 harness measured grep-shaped questions on a
small repository and found no agent-facing edge for the code graph. This release measures the engine
on the questions it exists for — associations, retraction, time travel, visibility — against the
honest baselines (files + grep, SQLite), and runs the three "no choice required" code-door arms
alongside.

## 1. Goal and the gate

Show whether an agent with the graph answers relationship questions over an entity dataset better
or cheaper than an agent with the same data as files or as SQLite. Pre-registered gate, evaluated
on the association suite (§3), three reps:

1. correctness: the graph arm's paired mean score is at or above EVERY other arm's (a tie passes);
2. cost: the graph arm's mean cost per cell is at or below the SQLite arm's, with the 95% bootstrap
   interval of the paired cost difference excluding zero;
3. no cell fails on max-turns where the SQLite arm succeeded.

Amended 2026-09-11 before the run: the SQLite pilot scored 1.00 on all twenty tasks, so correctness
is saturated and cost is the discriminator. The original wording (correctness must exceed both
baselines with its interval excluding zero) could not be passed by any arm.

Adoption is not a gate criterion here: in the graph arm the store is the agent's only data path.
It is still recorded. If the SQLite arm matches the graph on both correctness and cost, the engine
has no agent-facing edge on this dataset and the changelog says so.

The code-door arms (§6) carry the 0.6.2 gate unchanged and are diagnostics, not gates for this
release.

## 2. What we learned

- Grep answers every question in the 0.6.2 suite in one turn; a graph competes with a good search
  engine on its home turf and loses on cost. Relationship questions were the only tasks where the
  agent reached for the graph at all.
- The engine's differentiators — rules that derive and retract relationships, explain, time travel,
  role-scoped visibility, memory across sessions — never appeared in any task.
- Agents do not choose unfamiliar tools (0 of 120 unprompted sessions; independent pilots 0–6%).
  Any arm that offers the graph as an option repeats that failure; the graph must be the data path.
- The memory-store default MCP listing today is the code door's eight task tools plus
  `query`/`ingest_json`/`stats` — meaningless on an entity graph. The association surface is a
  product fix, not just a benchmark convenience.

## 3. The association suite

### 3.1 Dataset

One deterministic generator (seed fixed in the suite file) produces the same world in three forms:

- **Entities:** the existing `dogfood/synthesize.py` shapes — Talent, Company, Job with industry,
  specialties, design styles, size bucket, location, years of experience, status — at 2,000 nodes
  (1,400 / 400 / 200, `split_scale`).
- **Rules:** the ten `dogfood/rules.py` definitions (industry alignment, specialty match, location
  fit, similar size, design style, semantic match) as the derived relationships.
- **History:** a scripted changelog of 300 mutations with timestamps over a 90-day window: status
  flips, specialty edits, industry changes, relocations, deletions. Applied in order as commits so
  the graph has real node/edge history; written as a `changes.jsonl` for the file and SQLite forms.
- **Visibility:** two roles in the schema: `recruiter` sees Talent and Job; `client` sees Company and
  Job. Written as `roles.json` for the file form and a `roles` table for SQLite.

Forms:

| Arm | Data path | What the agent gets |
|---|---|---|
| P files | `entities/*.json`, `changes.jsonl`, `roles.json`, a one-page `README.md` describing fields and the rule definitions in prose | Read, Grep, Glob, Bash (python3 available) |
| Q sqlite | `world.sqlite` with `talent`, `company`, `job` (JSON columns for lists), `changes`, `roles`; the same `README.md` plus the schema | Read, Bash (`sqlite3` on PATH), Grep, Glob |
| R graph | a mushroomdb store with the rules loaded, the changelog applied as commits, roles in `schema.json`; MCP server on the association surface (§4); the memory skill | Read, Grep, Glob, Bash, `mcp__mushroomdb` (no entity files exist in the cwd) |

Every form carries exactly the same base facts. Derived relationships are never written to the
file or SQLite forms — computing them is the work.

### 3.2 Task kinds (20 tasks, 4 per kind)

| Kind | Question shape | Ground truth |
|---|---|---|
| Why | "Why is talent T associated with company C? Name every relationship and the evidence for each." | brute-force rule evaluation over base facts |
| Multi-hop | "Which companies in industry X are matched on industry, specialty and location to ≥ 3 published talents with ≥ 10 years?" | brute force |
| Retraction | "If company C's industry changed to Y, which of its current matches would no longer hold?" | rules re-evaluated on the counterfactual |
| Time travel | "What were talent T's matches on day D, before its specialty changed?" | brute force over the changelog replayed to D |
| Visibility | "As the `client` role, what can you see about talent T, and which of C's matches are visible to a `recruiter`?" | roles applied to the brute-force answer |

Rules: truth is computed by an engine-independent Python script AND by the engine; a task whose two
truths disagree is dropped and the disagreement filed as an engine bug. Answers are graded as sets
(entity keys, relationship types) with the existing `any_of` / `text` checks. Prompts never mention
mushroomdb; the README in every form describes the rules identically. Pilot rule: a task the
SQLite arm answers in ≤ 4 turns is replaced.

### 3.3 Harness

`benchmarks/agent-tasks/` gains a suite switch: `run.py --suite association` reads
`association/tasks.json`, provisions the three subject directories from `association/build.py`
(generator → files, SQLite, store), and runs arms P/Q/R with per-arm tool lists. Cells for P/Q run
in a fresh copy of the subject directory (the agent may write scratch files); R runs against a copy
of the store. Metrics, summary, gate and bootstrap intervals are reused; the gate function takes the
baseline arm as a parameter (A for the code suite, Q for the association suite).

## 4. The association surface

`Surface::Memory` lists: `query`, `explain_association`, `neighborhood`, `node_info`, `node_edges`,
`was_linked`, `node_history`, `edge_history`, `find_similar`, `hybrid_search`, `remember`,
`recall`, `stats` (13). The code task tools stay behind `--all-tools` on a memory store, as the
association tools stay behind it on a code store. The memory skill's task rules are rewritten around
these tools (why → `explain_association`; when → `node_history`/`was_linked`; who → `query` with
`mask`); ≤ 6,000 bytes. `explain_association`'s reply is text-first like the task tools.

## 5. Making the graph the data path

For arm R the install is `install --delivery mcp` into an otherwise empty directory; the store is
the only source of facts. This is not an adoption test; it is the shape a product would ship for an
entity workload: the agent gets the graph or nothing.

## 6. Code-door arms, run alongside

On the existing 20-task code suite, three reps each, using `--tools`/`--disallowedTools` (the
0.6.2 harness passed the tool list to `--allowedTools`, which is permissions-only — fixed here):

- **L impact-before-edit:** a `PreToolUse` hook on `Edit|Write|MultiEdit` runs
  `mushroomdb impact --auto <file>` and injects ≤ 600 bytes of blast radius (callers, co-change
  partners, tests) as `additionalContext` before the edit lands. No tool to discover.
- **J grep enrichment:** a `PostToolUse` hook on `Grep` appends ≤ 800 bytes of graph facts about
  the symbols the matches name (definition, callers, owner) to the tool result via
  `updatedToolOutput`. Adoption is 100% by construction.
- **H alwaysLoad:** the 0.6.2 installed arm with `alwaysLoad: true` on the MCP server. Tests whether
  the 0% was deferral.

L and J are new `install` flags (`--impact-before-edit`, `--enrich-grep`), off by default, through
the manifest like `--intercept-grep`. The 0.6.2 gate applies. If none passes, the code door is
recorded as a niche for large multi-repository trees and the linkt scale test is the only remaining
code-door experiment.

## 7. Non-goals

Embeddings beyond the synthetic ones the generator already produces; new rule kinds; the CTL
wrapper; the linkt scale test (its own plan after this release); any on-disk format change.

## 8. Testing and verification

TDD per crate convention. Harness tests cover the suite switch, the three builders' equivalence
(the same base facts in every form, asserted by loading all three and comparing), the parameterised
gate, and the truth cross-check. The MCP surface change and the two hooks get server/CLI tests.
Acceptance gains a memory-store listing check. All numbers in docs come from committed summaries.

## 9. Sequencing

Association surface (§4) → generator and three forms → truth script + cross-check → tasks + pilot
→ association run (P/Q/R × 3) → code-door flags → code-door run (A/L/J/H × 3) → release 0.6.3
with both gate tables.

## 10. Decisions taken on the owner's behalf

- Dataset scale 2,000 nodes: large enough that brute force in the agent is real work, small enough
  that a cell finishes inside 30 turns.
- SQLite is the primary baseline; files + grep is kept as the stock reference.
- The association surface replaces the memory-store default listing (breaking for programmatic
  callers relying on the old listing; called out in the changelog).
- Version 0.6.3, not 0.7.
