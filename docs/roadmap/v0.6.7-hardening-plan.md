# v0.6.7 — the hardening patch: implementation plan

**Goal:** close the Known-limits lines the v0.6.6 CHANGELOG had to print, without any format,
API-shape or positioning change.

**For the executing agent:** you have zero prior context. Everything you need is in this file,
the files it names, and `CHANGELOG.md` (read the `## v0.6.6` entry first: its BREAKING, Fixed and
Known limits sections are the ground truth for the behaviour you are changing). Work task by task,
in order, one commit per step that says "commit". Do not skip the verification steps.

**Architecture:** mushroomdb is a Rust workspace. `crates/core-api` (`mushroomdb`) holds the
engine (`src/engine.rs`: rules, HNSW build slices, `pending_builds`; `src/db.rs`: `GraphDb`, open,
snapshot, `pump_index_build`); `crates/core-rules` holds the HNSW index (`src/hnsw.rs`, blob
`MHNS` v3 with a `complete` flag); `crates/core-query` holds Cypher (`MERGE` lives there);
`crates/server` serves MCP (`src/mcp*.rs`: `upsert_entity`, `find_similar`) and HTTP
(`src/http.rs`); `crates/cli` is the `mushroomdb` binary (`serve`, `build-index`, `doctor`);
`bindings/python` is a PyO3 binding with tests in `bindings/python/tests`; docs in `docs/site/*.md`
are concatenated into `llms-full.txt` by `scripts/gen-llms-full.sh` (regenerate after any doc edit;
CI fails on drift). Benchmarks: `benchmarks/ci/run.sh` + `benchmarks/baselines/ci.json`.

**Base:** `main` at tag `v0.6.6` (`5993ad7`). Branch: `feat/v0.6.7-hardening`.

## Global constraints (every task)

- Version stays `0.6.6` until Task 8 bumps to `0.6.7` everywhere except CHANGELOG headings
  (which keep the `v`).
- Snapshot format stays `VERSION_9`; HNSW blob stays `MHNS` v3; `roles.json` stays v4. No new
  persisted fields. If a task seems to need one, stop and write down why instead.
- No recall floor in `crates/sim-harness` may be lowered.
- Every commit: `git add <explicit paths>` (never `-A`, `-a`, `.`); commit with
  `git -c commit.gpgsign=false commit -m "<subject>"`; **no trailers of any kind** in the message
  (no Co-Authored-By, no tool attribution). Untracked files you did not create stay untracked.
- Nothing committed may name a competitor database product.
- Every behaviour change has a test that fails without the change (revert the fix, run the test,
  see it fail, restore the fix). Say so in the commit body only if the test name does not already.
- Build with an isolated `CARGO_TARGET_DIR` (for example `target-067`); debug builds for tests;
  `--release` only for `scripts/acceptance-0.6.sh` and the recall gates.
- Verification commands (run before every commit that touches Rust):
  `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo test -p <crate you touched>`; before the release commit: `cargo test --workspace`,
  `cd bindings/python && .venv/bin/maturin develop && .venv/bin/pytest tests -q` (confirm
  `.venv/bin/pip show mushroomdb` reports the workspace version first; if it reports an older
  one, `pip uninstall -y mushroomdb` and re-run `maturin develop`), `scripts/check-claims.sh`,
  `scripts/render-plugin.sh --check`, `scripts/gen-llms-full.sh` then `git diff --exit-code
  llms-full.txt`.

### Task 1: `serve` registers an outstanding index build at open

**Symptom (CHANGELOG v0.6.6, BREAKING, `create_rule` bullet):** "After a restart the first
write or `mushroomdb build-index` is what registers an outstanding build — a freshly opened
`serve` has nothing to advance until then."

**Files:** `crates/core-api/src/engine.rs` (search `pending_builds`, `cut_short`,
`builds_awaiting_backfill`), `crates/core-api/src/db.rs` (search `pump_index_build`,
`mark_indexes_populated`, `adopt_hnsw`), `crates/core-rules/src/hnsw.rs` (search `complete`,
`can_answer`), tests in `crates/core-api/tests/` (find the file that holds
`an_interrupted_build_resumes_on_reopen` and `a_reader_over_a_mid_build_snapshot_answers_exactly`;
add beside them).

- [ ] Step 1: Write the failing test `a_reopened_store_pumps_its_outstanding_build_without_a_write`:
  build a store with a `VectorSimilar` rule over more vectors than `HNSW_BUILD_BATCH` (the constant
  is in `engine.rs`; the existing interrupted-build test shows how to stop after the first slice),
  snapshot, drop, reopen, then call `pump_index_build()` **without any write** and assert it
  reports progress (`indexed` grows) and, after enough pumps, `stats().building` is empty and
  the rule's edges exist. Run it: it must fail because the reopened handle's `pending_builds` is
  empty.
- [ ] Step 2: At open (the path that adopts the persisted HNSW blob), when a blob decodes with
  `complete == false`, register that rule in `pending_builds` with the correct `indexed`/`total`
  (total = retained vectors with that embedding property; indexed = graph size). Reuse whatever
  `cut_short` builds so there is one representation.
- [ ] Step 3: Run the test from Step 1; run `cargo test -p mushroomdb`. Confirm
  `an_interrupted_build_resumes_on_reopen` still passes (its assertion about inline finishing is
  changed by Task 2, not here).
- [ ] Step 4: Docs: `docs/site/rules.md` ("A store killed mid-build" paragraph), `docs/site/api.md`
  (the `create_rule` 202 contract), README and `docs/site/mcp.md` if they repeat the restart
  sentence, and the CHANGELOG (new `## v0.6.7` entry, `#### Fixed`): "`serve` advances an
  outstanding build after a restart without waiting for a write". Regenerate `llms-full.txt`.
- [ ] Step 5: Commit: `fix(rules): a reopened store registers its unfinished index build`.

### Task 2: Reopen after a mid-build kill is sliced, not inline

**Symptom (CHANGELOG v0.6.6, Known limits / "Not in this release"):** the open-time scan inserts
the whole remainder in one pass under the write lock (~1,000 s at 50,000 vectors).

**Files:** `crates/core-api/src/engine.rs` (the open-time scan that re-offers vectors the
persisted graph lacks; search `reindex_all_load_state` and `populate_indexes_before_write`),
`crates/core-api/src/db.rs`, same test file as Task 1.

- [ ] Step 1: Change `an_interrupted_build_resumes_on_reopen`: it currently asserts the first pump
  after reopen inserts more than one batch (pinning the inline finish). Invert it: the open must
  insert **at most `HNSW_BUILD_BATCH`** vectors before returning, `stats().building` must be
  non-empty right after open, and repeated `pump_index_build()` calls finish it. Run: fails.
- [ ] Step 2: In the open-time scan, when the persisted graph is incomplete (Task 1's registration
  fired), do not insert the remainder inline: leave the vectors to the slice loop that
  `pump_index_build` drives. Keep the inline path for the *complete* case (a handful of vectors
  written after the snapshot) — that is the fast path 0.6.5 fixed and must stay.
- [ ] Step 3: Add `a_search_after_a_mid_build_reopen_is_exact`: reopen mid-build, run
  `find_similar` on a vector whose true nearest neighbour is outside the built slice, assert the
  exact answer (the live gate from 0.6.6 must cover the registered build).
- [ ] Step 4: Run `cargo test -p mushroomdb` and the recall gates
  (`cargo test --release -p mushroomdb-sim-harness` — names in `crates/sim-harness/tests`).
- [ ] Step 5: Docs: `rules.md` mid-build paragraph now describes slicing; CHANGELOG `#### Fixed`;
  move the "Not in this release" sentence about the inline finish out. Regenerate `llms-full.txt`.
- [ ] Step 6: Commit: `fix(rules): the open after a killed build slices the remainder`.

### Task 3: `upsert_entity` validates everything before it writes anything

**Symptom (CHANGELOG v0.6.6, Known limits):** the update path sets one property at a time; a
refusal partway (a different `ns`, a reserved name, a type the role may not write) leaves the node
half-updated.

**Files:** `crates/server/src/` (search `fn upsert_entity` — the MCP tool), the engine write API
it calls (`set_prop`, or a batch form if one exists; search `set_props` in `crates/core-api`),
tests: `crates/server/tests/` (find `upsert_entity_never_takes_id_from_props` and add beside it).

- [ ] Step 1: Failing test `upsert_entity_update_is_all_or_nothing`: create a node with props
  `a=1`; call `upsert_entity` on it with `{b: 2, ns: "other"}` (the `ns` change is refused); assert
  the result is the refusal, `b` is **absent**, `commit_seq` did not move, and `updated_fields`
  is not reported. Second case: a role token whose write is refused for one property refuses the
  whole call. Run: fails (today `b` is written before `ns` is refused, or vice versa depending
  on map order — the test must not depend on order; assert on the final state).
- [ ] Step 2: Implement: run every per-property check (reserved names, `ns` rule, role write
  permission, type) first, collecting the first refusal; only then apply all sets in one engine
  commit (use the existing batch write if the engine has one; otherwise add
  `set_props(key, Vec<(name, value)>) -> Result<…>` to `GraphDb` that applies in a single WAL
  commit — that is not a persisted-format change, it is one commit with several entries).
- [ ] Step 3: Tests green; `cargo test -p mushroomdb-server`. Python binding: if the binding
  exposes `upsert`, add the same all-or-nothing test in `bindings/python/tests`.
- [ ] Step 4: Docs: the `upsert_entity` tool description string (in the server) says the update is
  atomic; `docs/site/api.md`/`mcp.md` wherever the tool is described; CHANGELOG `#### Fixed`;
  delete the Known-limits bullet from the v0.6.6 entry? **No** — never edit a released entry;
  say in v0.6.7 that the limit is closed. Regenerate `llms-full.txt`.
- [ ] Step 5: Commit: `fix(mcp): upsert_entity refuses the whole update or applies all of it`.

### Task 4: `MERGE` creates into a single-namespace role's namespace

**Symptom (CHANGELOG v0.6.6, BREAKING):** a MERGE create arm always lands in the default
namespace, so a role bound to namespaces cannot MERGE-create at all.

**Files:** `crates/core-query/src/` (search `Merge` in the executor; the create arm), the
authorization path that refuses cross-namespace writes (`crates/core-api`, search
`CrossNamespace`, `RoleWriteDenied`), tests: `crates/core-api/tests/namespaces.rs` (numbered
sections; add the next number) and the HTTP/MCP surface tests that pin the refusal text
(search `the_namespace_write_refusals_reach_the_surface`).

- [ ] Step 1: Failing tests: (a) a role bound to exactly one namespace runs `MERGE (n:Doc
  {id: "x"})` for a missing node → node exists with `ns` = that namespace; a second MERGE matches
  it (no duplicate). (b) A role bound to two namespaces → the existing refusal, with a message
  that says the role must name one namespace (the message is a documented string: put it in one
  `const` and pin it). (c) A global (no-role) MERGE is unchanged: default namespace.
  (d) `MERGE (n {id: "x", ns: "other"})` under a single-namespace role → cross-namespace refusal.
- [ ] Step 2: Implement: when the executing scope carries exactly one namespace and the pattern
  does not name `ns`, stamp `ns` on the create arm. Do it in the executor's create path, not in
  the authorizer (the authorizer must still refuse a mismatch).
- [ ] Step 3: `cargo test -p mushroomdb-query -p mushroomdb -p mushroomdb-server`.
- [ ] Step 4: Docs: `docs/site/masks.md` and `api.md` (search "MERGE" in both), CHANGELOG
  `#### Fixed` + a one-line note under a `#### Changed` heading that the single-namespace case is
  new behaviour. Regenerate `llms-full.txt`.
- [ ] Step 5: Commit: `fix(query): MERGE creates inside a single-namespace role's namespace`.

### Task 5: Masked approximate search widens until it has k

**Symptom (CHANGELOG v0.6.6, Known limits):** `find_similar_vector_masked` and the masked MCP
`find_similar` can return fewer than `k` when the mask filters index candidates.

**Files:** `crates/core-api/src/engine.rs` (search `find_similar_vector_masked`, and the widening
beam / `BEAM_FLOOR_SLACK` logic that `VectorSimilar` rules already use — reuse it),
`crates/core-rules/src/hnsw.rs` (search the `ef`/beam parameter of `search`), tests: the file
holding `find_similar` masked tests (search `masked` in `crates/core-api/tests`).

- [ ] Step 1: Failing test: 500 vectors, a role mask that admits 20 of them, ask `k = 10` with a
  query whose 10 nearest overall are all outside the mask; assert 10 results, all inside the mask,
  in the same order as the brute-force masked answer. Today this returns fewer than 10.
- [ ] Step 2: Implement: over-fetch by the mask's selectivity when known, otherwise widen the beam
  geometrically (×2) until `k` admitted candidates are found or the beam reaches the existing cap;
  at the cap fall back to the exhaustive masked scan. Same cap constant as the rule path.
- [ ] Step 3: `cargo test -p mushroomdb`; recall gates unchanged.
- [ ] Step 4: Docs: `api.md`/`mcp.md` `find_similar` (remove the under-k caveat, describe the
  fallback), CHANGELOG. Regenerate `llms-full.txt`.
- [ ] Step 5: Commit: `fix(vector): a masked search widens its beam until it has k`.
