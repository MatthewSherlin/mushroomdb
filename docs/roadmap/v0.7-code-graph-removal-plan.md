# v0.7 Removing the Code-Graph Door — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Delete the code-graph door — seven MCP tools, four install hooks, ten CLI subcommands, the `repograph` module and the CI job that gated it — after moving the three things the memory surface still depends on out of it, and without the memory product losing an answer it has today.

**Architecture:** The deletion is last, not first. `repograph` holds three things that are not about code graphs at all: the digest primitives every association tool renders through, the memory half of the session brief, and the `about_*` rule definitions `ingest-git` writes. Those move out first, each as a pure relocation with the existing tests following them, so that at no point are there two implementations of anything. Then the surface narrows: one MCP listing instead of two, two hooks instead of six, and the prompt hook stops demanding a code-shaped identifier before it will say anything. Only then does the module go, behind a gate that fails if it comes back.

**Tech Stack:** Rust 1.92.0 (edition 2021), cargo workspace of 10 crates; `serde_json` for MCP payloads and hook payloads; `bash` for the release gates; GitHub Actions for CI. Tests are `#[test]` in `crates/*/tests/`, driven either in-process through `server::run_mcp_stdio_with` over `std::io::Cursor` or by spawning the real binary via `CARGO_BIN_EXE_mushroomdb`.

**Spec:** `docs/roadmap/v0.7-memory-write-path-spec.md` (§1.4, §4.1, §5.1, §7.2, §7.4, §11 task 8)

**Predecessor:** `docs/roadmap/v0.7-memory-write-path-plan.md` (plan 1, tasks 1–7) and its handoff `docs/roadmap/v0.7-plan-1-handoff.md`. Read §6 and §7 of the handoff before Task 1: four of this plan's tasks exist because that document named them.

## Corrections to the spec, made by this plan

Every one was verified against the tree at `dec698e`, not inferred. The spec is closed for planning, so these are recorded here and Task 10 Step 8 amends the spec itself.

### C1 — `code-extract` and `structure.rs` must **stay**. Spec §11 task 8 is internally contradictory.

Spec §11 task 8 lists `code-extract` for deletion; spec §5.1 says "**`ingest-git` stays**, positioned as a data source". Both cannot hold:

- `code_extract` has exactly one consumer in the workspace: `crates/cli/src/structure.rs:54`. Verified: `git grep -n code_extract -- crates/cli/src crates/core-api/src` returns that line and one doc comment at `structure.rs:327`. One `Cargo.toml` depends on it (`crates/cli/Cargo.toml:37`).
- `structure.rs` is `ingest-git`'s **write path**, not a reader: `crates/cli/src/ingest_git.rs` calls `structure::refresh_all`, `structure::refresh_files`, `structure::importers_of` and `structure::ensure_rules_and_fulltext`.

So deleting either one deletes `ingest-git`. Both stay. What this costs: `mushroomdb-extract` stays in the 0.7 publish set, and `crates/code-extract/tests/extract.rs` (2,085 lines) keeps running. What it saves: `ingest-git` still works, which is what §5.1 promised.

> **If the owner intends to narrow `ingest-git` to git metadata only** — commits, pull requests, files, authors, which is exactly how `SKILL.md:51` describes it, with no symbols — then `code-extract` does come out and `structure.rs` loses its extraction half. That is a different and larger task and is **not** in this plan. See "One decision for the owner" at the end.

### C2 — there are **four** hooks to remove, not three. The spec names only the three flagged ones.

Spec §5.1 lists `--intercept-grep`, `--impact-before-edit`, `--enrich-grep`. It misses the one written **unconditionally**: `TOUCH_EVENT` (`crates/cli/src/install.rs:1130`), a `PostToolUse` hook matched to `Edit|Write|MultiEdit` (`install.rs:1132`) that runs `mushroomdb touch` to re-extract an edited file into the code graph. It is code-graph work on every edit of every install.

The consequence is a migration requirement the spec does not carry: `remove_stale_hooks` (`install.rs:1387`) only prunes hooks for an event/subcommand pair the installer is *still writing*. Stop writing `touch` and every already-installed user keeps a `PostToolUse` hook invoking a subcommand that no longer exists, firing on every edit. Task 7 Step 6 prunes retired hooks explicitly.

### C3 — deleting `why` deletes the CLI's only answer to the product's headline question.

`crates/cli/skills/mushroom/SKILL.md:44` ships this row:

```
| why are these two related | `{{BIN}} why '{{DB_PATH}}' <a> <b>` — what links two keys, with the evidence |
```

and `docs/site/skill.md:140` names `mushroomdb why <store> <a> <b>` as one of the three shell forms an `install --delivery cli` teaches. `explain_association` has **no CLI subcommand** (`crates/cli/src/lib.rs:2171` says so in a doc comment). So deleting the code-graph `why` leaves `--delivery cli` unable to answer the question the README leads with — worsening the exact friction spec §6.1 already flags.

`GraphDb::explain(&self, key_a: &str, key_b: &str) -> Result<Vec<Explanation>>` exists at `crates/core-api/src/db.rs:11403` and is what the MCP `explain_association` tool calls. Task 5 rebinds `mushroomdb why` to it. This is a small addition that prevents a headline regression; it is the one place this plan adds rather than subtracts, and it is the task to cut first if the plan has to shrink.

### C4 — `install` cannot apply the memory schema, because it never opens a store

The handoff assigns "the memory schema is not wired into `install`" to this plan. Verified: **`crates/cli/src/install.rs` contains zero references to `core_api`, `SharedDb`, `apply_schema`, `GraphDb` or `holds_a_store`.** It writes config only — a skill file, an `.mcp.json` entry, settings hooks, a `.gitignore` line, git hook blocks, a manifest. **After `mushroomdb install`, no store exists.** It is created lazily by whichever process opens it first:

| First opener | Site | Creates? | Schema? |
|---|---|---|---|
| `mcp` | `main.rs:911-919` | yes | **yes**, gated on `!holds_a_store` |
| `serve` | `main.rs:654-662` | yes | **yes**, same gate |
| `demo` | `lib.rs:2692`, `:2700` | yes | yes, unconditional |
| `ingest-git` | `ingest_git.rs:1142` | yes | **no** ← the one real offender |
| `sync`, `touch` | `ingest_git.rs:1740` (`open_existing`) | never | n/a |
| any hook body | `hook.rs:25` (`open_for_hook`, read-only, existence-checked) | never | n/a |

So "wire the schema into `install`" is not a one-line addition — it is giving `install` a store-creating responsibility it does not have, and one that `--auto` exists to defer to run time (`install.rs:557-573`). Task 8 closes the gap where the store actually appears: **`ingest_git.rs:1142`, the single creator without the gate.**

**One genuine residue.** A `--delivery cli` install registers no MCP server, so `mcp` may never run and the store may never be created by a path that declares a schema — the user's first store could arrive from `ingest-git` or not at all. That is the only case where `install` itself is the gap, and it is decision D2.

### C5 — `ingest-git` depends on `repograph::impact`, which is one of the seven

`crates/cli/src/ingest_git.rs:45` does `pub use core_api::repograph::DEFAULT_EXCLUDES;` and `:177` calls `core_api::repograph::path_excluded`. Both are defined in `crates/core-api/src/repograph/impact.rs` (`:52` and `:69`) — the file behind the `impact` tool. They are path-glob matching, not code-graph logic, and `ingest-git` uses them for its own exclude list.

After the seven handlers go, their only surviving caller is `ingest_git.rs` (`mcp_tasks.rs:501,519` are inside `tool_impact`/`tool_owners` and die; `cli/src/recall.rs:224,237` are inside the nudge and die). So they move into `ingest_git.rs`, alongside the exclude list they serve. Task 1 Step 2b.

### C6 — only **one** `ingest-git` store-creation site, not two

The handoff names `ingest_git.rs:1142` and `:1747`. Verified: `:1142` creates; the second site is at **`:1740`**, is `open_existing`, and **deliberately refuses to create**. Task 8 has one site to change, not two.

## Global Constraints

Copied from plan 1 and the spec; every task's requirements implicitly include these.

- **Rust 1.92.0** (`rust-toolchain.toml`, `workspace.package.rust-version`). Do not raise it.
- **No new WAL discriminant.** Snapshot versions 5–10 stay readable. A 0.6.x store must open in 0.7.
- **No storage format change.** This plan writes no new node, edge or property kind.
- **`enable_fulltext` is not idempotent** — `Err(RuleInvalid)` on an already-enabled pair, `Err(RuleNotFound)` from `disable_fulltext` on a disabled one. Always go through `apply_schema`, which applies full-text idempotently (`crates/core-api/src/schema.rs:272-281`).
- **Existing stores are never silently schema-upgraded.** Declaring full-text rebuilds the index at open — 227 ms against 3.8 ms with none, live ledger row 36 (`docs/roadmap/v0.6.10-defects.md:51`). New stores get a schema at creation; existing ones only through an explicit `schema apply`.
- **A pure relocation is byte-identical output.** Tasks 1, 2 and 9 move code. Where a moved function rendered a string, the string it renders after the move must be identical, and the test that proves it moves with it.
- **Determinism.** Collections sorted, ties on the key ascending, floats at fixed precision.
- **Verification bar, per commit:** `cargo fmt --check`; `cargo clippy --workspace --all-targets -- -D warnings` on both feature sets; `cargo test --workspace --no-fail-fast`. **`--no-fail-fast` is not optional** — plain `cargo test` stops at the first failing target, and plan 1 found three real regressions that three truncated runs had hidden (handoff §2, decision 7). Never pipe a test run through `tail` and read the exit code: that reads `tail`'s (handoff §2, "What I got wrong", item 1).
- **Commit style:** conventional, lowercase, short (`fix:`, `feat:`, `chore:`, `test:`, `docs:`, `refactor:`). **No `Co-Authored-By` and no session trailers, ever.**
- **Never run git actions beyond the commits this plan specifies.** No pushing, no tagging, no branch creation.
- **Verify every signature before you use it.** Fourteen defects in plan 1 came from task briefs citing APIs that did not have the shape claimed (handoff §6). Every `file:line` in this plan was read at `dec698e`; re-read it before editing, because this plan's own earlier tasks move some of them.

**Why:** The handoff's "Not fixed here — settle before Plan 2 points the prompt hook at `memory::recall`" is this. Two defects, and one of them is in the product's central shape.

**The floor drops the subject of the query.** `recall.rs:324` reads `present * 2 > terms.len()` — a *strict* majority. Verified arithmetic on the canonical example: `recall{topic:"What does Matthew prefer?"}` tokenizes to `["matthew","prefer"]` (`what` and `does` are both in `STOPWORDS`; `prefer` and `matthew` are not — checked against the 146-word list). The `Note` holding "Matthew prefers concise summaries" stems to contain both, so it scores 2/2 and survives. The `Person` node `matthew`, whose `name` is "Matthew Sherlin", holds one of the two, so `1 * 2 > 2` is **false and the Person is dropped**. The product's whole shape is an entity node holding the name and a note holding the fact — exactly where the two terms do not co-occur. Every existing "recall preserved" test uses a topic whose terms all sit in one node, so the suite structurally cannot see this.

**And there is no term cap.** `repograph::recall` has `MAX_QUERY_TERMS = 24`; `memory::recall` has none, and `search_terms` is unbounded (`recall.rs:189`). The query handed to the index is `terms.join(" OR ")` (`:248`). Today the prompt hook still calls `repograph::recall_digest`, so nobody has fed a whole prompt through this path. Task 4 does exactly that, and a two-hundred-word prompt becomes a two-hundred-clause OR query on every turn.

**The fix is one character on the floor plus a rendered number, not the floor's removal.** `present * 2 >= terms.len()` — coverage at half rather than above it:

| Topic | Candidate | Coverage | `>` (today) | `>=` (this task) |
|---|---|---|---|---|
| `What does Matthew prefer?` | `matthew` (Person) | 1/2 | dropped | **kept** |
| `What does Matthew prefer?` | `note-1` | 2/2 | kept | kept |
| `banana republic economic collapse history` | `banana-note` | 1/5 | dropped | dropped |
| `apple banana cherry`, one word per node | each | 1/3 | dropped | dropped |
| `apple banana`, one word per node | each | 1/2 | dropped | **kept** |

Only the last row flips an existing test (`terms_scattered_across_two_nodes_do_not_clear_the_majority`, `memory_recall.rs:131`), and its expectation is the defensible-either-way one: a store asked for "apple banana" that holds an apple note and a banana note has two honest answers, and returning nothing is the worse of the two. The two tests that guard against real false positives — 1-of-5 and 1-of-3 — keep passing unchanged.

**The handoff proposed dropping the floor entirely** and letting the rendered coverage carry all the precision. This plan does not, and the reason is Task 4: the moment the prompt hook runs on natural language, a floor of "one term anywhere" puts low-coverage hits into *every* prompt of *every* session. Half is the weakest floor that still refuses a minority of the topic's words, and the rendered number gives the informative half of the handoff's argument without the cost.

```rust

    //
    // (The paragraphs above this in the source explain why an absolute BM25
    // score cannot do this job and why coverage has to be asked per candidate
    // node rather than per corpus. Both still hold; keep them.)
    //
    // The bar is *half* the topic's terms, not more than half. A strict
    // majority reads well and refuses the shape this product is made of: an
    // entity node holds a name and a note holds the fact, so a two-word topic
    // naming a person and an action has one word in each, and the entity the

    // Half still refuses a *minority* — one word of three, one of five — which
    // is what the false-positive cases actually are.
    //
    // And the count survives the filter, because a digest that shows it does
    // not have to be believed: `reid — reid (1/3 terms)` is a hit a reader can
    // discount, where an unannotated line cannot be told from a full match.
    // RRF flattens every field's top hit to 1/(60+1), so the fused score
    // carries almost no ranking information; coverage carries it instead.
    let mut covered: BTreeMap<String, usize> = BTreeMap::new();
    if !terms.is_empty() {
        let stemmed_terms: Vec<String> = terms.iter().map(|t| stem(t)).collect();
        best.retain(|key, _| {
            let mut candidate_tokens: HashSet<String> = HashSet::new();
            for field in &fields {
                if let Some(value) = db.get_prop(key, field) {
                    candidate_tokens.extend(
                        value_tokens_stemmed_with_positions(&value)
                            .into_iter()
                            .map(|(tok, _)| tok),
                    );
                }
            }
            let present = stemmed_terms
                .iter()
                .filter(|t| candidate_tokens.contains(*t))
                .count();
            if present * 2 >= terms.len() {
                covered.insert(key.clone(), present);
                true
            } else {
                false
            }
        });
    }

        let cover = if total == 0 {
            String::new()
        } else {
            format!(" ({present}/{total} terms)")
        };
        let line = match db.node_summary_line(key) {
            Some(summary) => format!("  {key} — {summary}{cover}\n"),
            None => format!("  {key}{cover}\n"),
        };
        if out.len() + line.len() > max_bytes {
            break;
        }
        out.push_str(&line);
    }
    RecallOutcome::Hits(out)
```

/// Extract the prompt text from a hook payload. Accepts `prompt`,
/// `user_prompt`, and `user_input` (the docs disagree on the field name).
fn prompt_from_payload(raw: &str) -> Option<String> {
    let v: serde_json::Value = serde_json::from_str(raw).ok()?;
    for k in ["prompt", "user_prompt", "user_input"] {
        if let Some(s) = v.get(k).and_then(|x| x.as_str()) {
            let s = s.trim();
            if !s.is_empty() {
                return Some(s.to_string());
            }
        }
    }
    None
}

/// The hook's whole output. Never an error, never a panic: an empty string is
/// how this hook says "nothing to add", and every failure path says that.
#[must_use]
pub fn run_recall(db_dir: &Path, hook_stdin: &str) -> String {
    let Some(prompt) = prompt_from_payload(hook_stdin) else {
        return String::new();
    };
    let Some(db) = open_for_hook(db_dir) else {
        return String::new();
    };
    match recall_digest(&db, &prompt, &db_dir.display().to_string(), MAX_OUTPUT_BYTES) {
        RecallOutcome::Hits(d) => cut_to(&d, MAX_OUTPUT_BYTES),
        // Not the same answer as "no match": nothing in this store can ever
        // match, and the caller can fix that. The same wording the MCP tool
        // gives, for the same reason.
        RecallOutcome::NoIndex => format!(
            "mushroomdb recall — this store has no text index, so no topic can match. \
             Run `mushroomdb schema apply {} --memory-defaults`.\n",
            db_dir.display()
        ),
        RecallOutcome::NoMatch => String::new(),
    }
}

    let roots = ["crates/cli/src/main.rs", "crates/cli/src/lib.rs",
                 "crates/cli/src/install.rs", "crates/cli/src/ingest_git.rs",
                 "crates/cli/src/structure.rs", "crates/cli/src/hook.rs"];

        .parent().unwrap().parent().unwrap().to_path_buf();
    let mut offenders = Vec::new();
    for rel in roots {
        let src = std::fs::read_to_string(repo.join(rel)).expect(rel);
        let lines: Vec<&str> = src.lines().collect();
        for (i, line) in lines.iter().enumerate() {
            if !OPENS.iter().any(|o| line.contains(o)) || line.trim_start().starts_with("//") {
                continue;

                || window.contains("open_existing")

            }
        }

}
