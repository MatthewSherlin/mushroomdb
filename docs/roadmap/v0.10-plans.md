## Cross-plan contract

The plans were written in parallel. Where two plans name the same interface differently, this
contract is the one to build; each affected plan points here.

**C1 — Procedures (W1 QL-12, W3 TX-15).** Built-in procedures are pure functions over a catalog,
so they work over HTTP, embedded and Bolt alike, and nothing in `crates/core-query` or
`crates/core-api` depends on `crates/bolt`.

```rust
// crates/core-query/src/cypher/proc.rs — created by QL-12
pub struct ProcResult { pub columns: Vec<String>, pub rows: Vec<Vec<Value>> }
pub trait ProcCatalog {
    fn labels(&self) -> Vec<String>;              // visible to this view's mask
    fn relationship_types(&self) -> Vec<String>;
    fn property_keys(&self) -> Vec<String>;
    fn indexes(&self) -> Vec<SchemaRow>;          // same rows as SHOW INDEXES (W2 TY-9)
    fn constraints(&self) -> Vec<SchemaRow>;      // same rows as SHOW CONSTRAINTS (W2 TY-9)
}
pub fn call_procedure(cat: &dyn ProcCatalog, ns: &str, name: &str, args: &[Value])
    -> Result<ProcResult, String>;   // unknown → Err("unknown procedure: {ns}.{name}")
```

QL-12 creates the module with `db.ping` and the unknown-procedure error, parses `CALL ns.name(args)
[YIELD …]`, executes it on the **read** path, and implements `ProcCatalog` for the executor's
views in `crates/core-api` (masked views list only what the principal sees). TX-15 adds
`db.labels`, `db.relationshipTypes`, `db.propertyKeys`, `dbms.components` and
`db.schema.visualization` inside `call_procedure`, and `db.indexes` / `db.constraints` once TY-9
has landed. There is no registry object, no `set_procedure_registry`, and no procedure code in
`crates/bolt`. `SchemaRow` is the row type TY-9 defines for `SHOW INDEXES` / `SHOW CONSTRAINTS`.

**C2 — Constraints at commit (W2 TY-5/7, W3 TX-21).** W2 enforces unique constraints inside
`commit_logged_batch`, which every write path reaches, so there is no `check_constraints`
function. The violation error is `GraphError::ConstraintViolation`. TX-21 adds no call; it adds
two tests — a transaction whose commit would violate a constraint fails with that error and leaves
no WAL record; two concurrent transactions inserting the same unique value produce exactly one
success — and maps the error to Bolt's constraint-validation code.

**C3 — Temporal types (W1 QL-13, W2 TY-1).** 0.10 has exactly the five new types W2 defines:
`Value::Date(i32)`, `Value::LocalDateTime(i64)`, `Value::DateTime { micros_utc: i64,
offset_seconds: i16 }`, `Value::Duration { months: i32, days: i32, nanos: i64 }`,
`Value::Binary(Vec<u8>)`. There is no Time or LocalTime type: `time()` and `localtime()` fail with
`not supported in mushroomdb 0.10: time types`.

**C4 — TLS configuration (W3 TX-16, W4).** One helper in `crates/server/src/tls.rs`:
`pub fn load_server_config(cert: &Path, key: &Path) -> Result<Arc<rustls::ServerConfig>, String>`,
built from the existing `--tls-cert` / `--tls-key` flags (`MUSHROOMDB_TLS_CERT` /
`MUSHROOMDB_TLS_KEY`). The first of TX-16 or the W4 task that touches TLS creates it; the other
reuses it. HTTP and Bolt share it unless `--bolt-tls-cert` / `--bolt-tls-key` are given.

**C5 — Cypher function table (W1 QL-10, W6 PS-6).** `cargo run -p tck-runner -- --function-table
<path>` writes a markdown table — function, supported (yes/no), TCK scenarios passed / total —
that PS-6 renders and CI holds to the TCK results.

**C6 — Bolt listener configuration (W3 TX-16, W4 HO-15).** `--bolt-port <u16>` /
`MUSHROOMDB_BOLT_PORT`; unset means no Bolt listener; templates use 7687. `--bolt-tls` /
`MUSHROOMDB_BOLT_TLS`.

**C7 — Readiness (W4 HO-02).** `AppState.ready` defaults to `true` everywhere except `run_serve`,
which starts it `false` and sets it after `open()` returns. Every other entry point opens the store
before serving, so it is ready when it binds.

**C8 — Ledger row 46.** Closed in 0.8.1. PF-08 extends the ignored-test census to the new W5 scale
tests and changes no ledger row. The deferred rows owed to 0.10 are the seventeen in spec §8.

**C9 — V11 is sticky (W2 TY-12).** A store becomes V11 at its first V11-only record of any kind and
stays V11 — dropping the last constraint or range index does not move it back, because its WAL and
archives still hold V11 records. The released 0.9.x binary refuses a V11 store with its existing
text, `snapshot: unsupported version 11`; the format-compat test asserts that text and a
byte-identical WAL. 0.10's own refusal text applies to versions 12 and up.
