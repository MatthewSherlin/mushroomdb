# v0.7 — memory that fills itself

**Written 2026-09-29.** Surveyed against `main` @ `fab9bdc` (tag `v0.6.12`, published to
crates.io, npm, PyPI and GHCR). Every `file:line` below was read at that commit, and every
runtime claim marked **[probed]** was reproduced against the release binary built from it.
Claims resting on inference are marked **[inferred]** and must be confirmed before the
implementing task starts.

---

## 1. Why this release exists

v0.6.12 ships a graph engine whose pre-registered association gate passes for the first time —
arm R at 1.000 on all sixty cells against sqlite's 0.990, cost −45.6% with every interval
excluding zero. The engine is good.

The memory product on top of it does not work.

**[probed]** On the shipped 0.6.12 binary, default memory surface, the exact flow
`crates/cli/skills/mushroom/SKILL.md` prescribes:

```
upsert_entity {key:"matthew", label:"Person", props:{...}}   → {"created":true,"ok":true}
remember      {text:"Matthew prefers concise summaries",
               about:["matthew"]}                             → remembered note:b11d1be5f6fb608d
recall        {topic:"matthew"}                               → "nothing indexed matches matthew"
recall        {topic:"What does Matthew prefer?"}             → "nothing indexed matches …"
```

`MATCH (n:Note) RETURN n.text` returns the note. The write succeeded; the product's own recall
tool cannot reach it.

On an empty store it is worse. **[probed]** `remember{about:["matthew"]}` before the entity
exists returns `isError: true`, `unknown about key: matthew`. The fallback — `remember` with no
`about` — succeeds and writes an orphan node connected to nothing. `recall{query:...}` returns
`missing topic`, naming neither the correct argument nor the fact that one exists.

### 1.1 Cause

Three independent defects. The first is the dominant one, and it is not the one it looks like.

**(a) `recall` refuses to search for anything not shaped like code.**
`repograph::recall_digest` (`crates/core-api/src/repograph/recall.rs:370-373`) begins with
`identifier_terms(prompt)` and returns empty when it yields nothing. That extractor matches
only code-shaped tokens: paths, `mod::name`, snake_case words, backticked words.

**[probed]** This is provable in isolation, on one store, with one note:

```
remember {text:"Matthew prefers concise summaries in the graph_db project"}
recall {topic:"graph_db"}   → HIT   — returns the note
recall {topic:"`concise`"}  → HIT   — returns the note
recall {topic:"Matthew"}    → MISS  — "nothing indexed matches Matthew"
```

The note is indexed. The word is in it. `recall` will find `graph_db` and a backticked
`concise` and will not find `Matthew`, because a capitalised English word is not an identifier.
**A human name — the single most common subject in a memory store — is unreachable by
design.** The tool's own description advertises results "across notes, concepts, files, symbols
and people."

**(b) Only `Note.text` is ever indexed, so `recall` can only ever return notes.**
`recall_digest` searches `db.fulltext_pairs()` (`recall.rs:376-381`). `remember` self-declares
one pair — it calls `enable_fulltext("Note","text")` when absent
(`crates/core-api/src/repograph/remember.rs:100-105`), which is why (a) is reproducible at all.
Nothing ever declares a text index on an entity property. So `recall` cannot find a `Person` by
their name even with a code-shaped query, and the memory surface has no index-declaring tool to
fix it with — `enable_fulltext` (`crates/core-api/src/db.rs:7324`) is reachable only from
`apply_schema` and from two callers in `crates/cli/src/ingest_git.rs` and
`crates/cli/src/structure.rs`, both code-graph code.

**(c) `remember` requires scaffolding it cannot create.** `tool_remember`
(`crates/server/src/mcp_tasks.rs:2477`) rejects any `about` key not already present, so the
first natural call on a new store errors by construction.

> **Correction, 2026-09-29.** An earlier draft of this spec attributed the §1 failure to a
> missing full-text index. That was wrong: `remember` declares its own. The probe above
> separates the two gates and puts the weight on `identifier_terms`. Recorded because the wrong
> diagnosis would have produced the wrong fix — declaring an index changes nothing for a query
> like "Matthew".

### 1.2 Why no gate caught it

The association benchmark's world is generated and pre-loaded, so the write path is never the
thing under test. `remember` and `recall` have no round-trip test at the MCP layer at all.

This is the fifth instance of one failure shape in this project: **a real defect present for
releases, invisible because nothing was positioned to report it.** The four prior instances are
catalogued at `docs/roadmap/road-to-0.7-plan.md:451-472`. §8 of this spec is written to close
the shape, not just this instance.

### 1.3 The structural gap underneath

`create_rule` derives **edges**. Nothing derives **nodes**. The write path is manual
`upsert_entity` / `ingest_json`, plus `ingest-git` — and the code-graph door is removed in 0.7.
"The graph that builds itself" builds edges, not entities.

### 1.4 The removal and the feature are one task

**Three things the memory surface depends on live inside `repograph`, the module 0.7 deletes:**

| In `repograph` | Reached by | Consequence |
|---|---|---|
| `remember` (`remember.rs:71`) | MCP `remember` | must be reimplemented |
| `recall_digest` (`recall.rs:364`) | MCP `recall`, the `UserPromptSubmit` hook | must be reimplemented |
| `brief` / `SchemaBrief` (`brief.rs:239`, `:170`) | the `SessionStart` brief, CLI `brief` | must be reimplemented — and it is the only schema introspection that exists (§4.2) |

The code-graph removal cannot land without reimplementing all three, and reimplementing them
*is* the memory write path. These are not two competing work items.

Related trap: `crates/cli/src/structure.rs` is one of only two non-`apply_schema` callers of
`enable_fulltext`. Deleting it carelessly removes a working example of index declaration at the
moment `recall` starts depending on one.

## 2. Non-goals

Stated so they are refused once rather than re-argued per task.

| Non-goal | Why |
|---|---|
| **MushroomDB calls a model** | `docs/design.md:55` already rules this out: *"LLM extraction is a possible later optional plugin, never core."* Extraction is the host agent's job; this release makes its output cheap to store. The local-first claim depends on it. |
| **Destructive entity merge** | §3.3. Merge is terminal — node ids are never reused after delete (`IdMap` tombstones). Link is recoverable and can gain canonicalisation later; merge cannot gain reversibility later. |
| **A storage format bump** | The memory schema needs no new WAL discriminant (§5.2). Snapshot versions 5–10 stay readable. A 0.6.x store opens in 0.7. |
| **True redaction / right-to-be-forgotten** | `forget` tombstones and says so plainly (§4.2). Removing a fact from history requires snapshot-and-truncate-and-rebuild — its own subsystem. Candidate for 0.8. |
| **Scale, HNSW ceiling, the 10M-node target** | Release-sized alone. 0.7 restates the target to what is measured (§6.4) and does no engine work on it. |
| **LongMemEval** | Ruled out by the owner 2026-09-03. It would also score the retrieval path this release replaces. |
| **Rules running post-resolution** | Requires a derived-node primitive. Gated behind the measurement in §8.2 — deliberately not committed here. |
| **Hosted service, multi-writer, larger-than-RAM** | Unchanged non-goals from `docs/design.md:68-70`. |

## 3. Design

### 3.1 Layer 1 — a store that can find what it was told

Two changes, matching the two causes in §1.1:

- **Delete the `identifier_terms()` gate — do not relax it.** A code-identifier extractor has
  no place on an entity surface. `recall` passes the topic to `search_hybrid` / BM25 over the
  declared text fields, which is the path it already uses *after* the gate
  (`recall.rs:414-423`). This is the fix for §1.1(a) and it is subtraction, not addition.
- **A memory store declares text indexes on entity properties, not just `Note.text`.** A new
  store created through `install` or `demo` applies the memory schema (§3.5). This is the fix
  for §1.1(b) — without it `recall` can only ever return notes, never the entities they are
  about.

Zero hits must also be distinguishable from a store that cannot search: today both print
"nothing indexed matches". They are different conditions and get different answers — *no
match* versus *this store has no text index on that label — run `schema apply`*.

**Existing stores are not silently upgraded.** Declaring full-text on an existing store
rebuilds the index at open, and that cost is already a known live defect: row 36 of the ledger
(`docs/roadmap/v0.6.10-defects.md:2005`) measures open at **456 ms with three indexed text
fields against 3.8 ms with none — 120×, attributable entirely to full-text**, halved to 227 ms
in 0.6.11 and not solved. Creating the `SAME_AS` rule on an existing store additionally fires a
backfill across every node. So: new stores get the schema at creation; existing stores get an
explicit `mushroomdb schema apply --memory-defaults` that states what it will cost before
doing it.

### 3.2 Layer 2 — a fact can arrive before its subject

`remember{about:[k]}` where `k` is unknown creates a **provisional** node — label `Entity`,
property `provisional: true` — rather than erroring.

**A provisional node's label is permanent for the life of the node**, in 0.7. `upsert_entity` on
the same key fills in **properties** and clears `provisional` — that is already `upsert`'s
semantics — but it does **not** fill in the label: the engine has no label-mutation path, so a
provisional node is `Entity` for as long as it exists, and `upsert_entity{key:k, label:"Person",
...}` cannot make it a `Person`. Naming a different label than the one stored is now a refusal,
not a silently-accepted no-op, because the earlier version of this sentence claimed the opposite
and nobody tested the direction it covered as a result (fix round 3, corrected after the final
review found `label` was dropped on *every* `upsert_entity` update, not only a provisional
stub's — on the shipped binary, `remember{about:["matthew"]}` then
`upsert_entity{key:"matthew", label:"Person", ...}` reported plain `{"ok":true,"created":false}`
and left the node permanently invisible to `MATCH (n:Person)`).

A caller who **knows** the label must supply it through `remember`'s `entities` at first mention,
not `about` — that path works today and produces a correctly-labelled, non-provisional node with
its `ABOUT` edge intact in the same commit. `about` is for a subject whose type is not yet known;
`entities` is for one that is, and it is the only way to set a label that sticks. Relabeling —
alongside redaction — is a 0.8 candidate, blocked on the same format question: either needs a WAL
discriminant, and this release forbids one.

Guards, because a typo otherwise becomes a permanent node:

- Provisional nodes are listable (`schema`, §4.2) and countable in `stats`.
- A cap per commit, so a malformed batch cannot flood the graph.
- `forget` removes one (§4.2).

**Settled (O-4, §9): provisional nodes never expire.** They are listable and countable, and
removal is always an explicit `forget`. Silent deletion in a store whose selling point is an
audit trail is the wrong default.

> **Correction, 2026-09-30 (C4).** Provisional nodes are **not** countable in
> `stats`, and this release does not make them so: `Stats` carries no such
> field (`crates/core-api/src/db.rs:399-421`), and adding one breaks its
> struct literals and drifts the HTTP and Python stats. They are counted and
> listed by the MCP `schema` tool, from `memory::schema::provisional_keys`.

### 3.3 Layer 3 — identity as a rule, link-first

**Decided 2026-09-29 with the owner: link, do not merge.**

Three conversations produce `matt`, `matthew`, `matthew-sherlin`. All three persist. A derived
`SAME_AS` edge carries the claim that they are one person:

```
SAME_AS:  Person → Person
          Any([ Overlap{field:"names", min:0.6},
                VectorSimilar{field:"embedding", min:0.88} ])
```

What this buys, because it is a rule and not a merge script — all of it existing engine
behaviour, none of it new:

- **Scored.** A weak match is a weak edge, not silent corruption.
- **Explainable.** `explain_association("matt","matthew-sherlin")` answers *why do you think
  these are the same person*, with the values that produced it. Every entity-resolution system
  is asked this; almost none can answer.
- **Retracting.** Contradicting evidence removes the edge in the write that introduced the
  evidence. Identity guesses should be undoable; here they already are.
- **Time-travellable.** `edges_at` answers what the store believed last week; `was_linked`
  answers when it changed its mind.

**Transitivity is clustered, not closed.** `SAME_AS` is derived pairwise. Traversing the
transitive closure daisy-chains weak links until unrelated people collapse into one blob — the
classic failure. Resolution runs a community detection pass over the `SAME_AS` subgraph above
the threshold, using the `communities` (Louvain) algorithm already in
`crates/core-api/src/algo.rs`. Direct-edges-only misses real matches; full closure is unsafe;
clustering is the answer and needs no new engine code.

**Canonical selection is the oldest node** (settled, O-2 §9). Every other tie in this engine
breaks deterministically — seeded HNSW levels, fixed IVF iterations, node key ascending — and
identity is not the exception. `IdMap` allocates dense `u32` ids monotonically and never reuses
one after delete, so the **lowest live id in a cluster is the oldest node** and no new field is
needed to find it.

**The accepted cost of link-first.** A rule evaluates against a node. If a person's properties
are split across three aliases, none may clear a threshold the resolved person would — so link
makes *every other rule in the store* slightly less accurate. This is the strongest argument
for merge and it is accepted, for one release, because the sequencing is asymmetric: link can
gain a canonical node later without a format break, merge cannot gain reversibility at all.
§8.2 measures the size of the cost so 0.8 is decided on a number.

### 3.4 Layer 4 — structured remember

`remember` gains two optional arguments so one call writes the note **and** the structure the
agent extracted, in one commit, so rules fire once:

```jsonc
remember {
  text:     "Matthew wants 0.7 to focus on the write path",
  entities: [ {key:"matthew", label:"Person"}, {key:"v0.7", label:"Release"} ],
  facts:    [ {subject:"matthew", predicate:"WANTS", object:"v0.7"} ]
}
```

The return value is the load-bearing half, and today `remember` returns only a key:

```jsonc
{ note:"note:b11d…", created:1, matched:1, derived:3, provisional:0,
  same_as:[ {a:"matthew", b:"matt", score:0.91} ] }
```

That report is the only signal telling the model whether its extraction agreed with what the
store already believed. Without it, extraction cannot improve across turns.

`text` alone must keep working unchanged — it is the existing contract.

**Provenance, while we are in here.** **[verified]** A `Note` today carries exactly `id`,
`text`, `kind`, `ts`, `source` and `about` (`remember.rs:110-120`) — and `source` is
**hardcoded to the string `"agent"`** (`remember.rs:115`). There is no session id, no actor, no
origin, and no argument on the MCP schema to supply one (`mcp_tasks.rs:2916-2939`); `ts` is
filled from `SystemTime::now()` and the caller cannot pass it either.

For agent memory, *when did I learn this and from where* is what makes a remembered fact
trustworthy enough to act on. Add an optional `source` the caller can set and let `ts` be
supplied, so a fact imported from a transcript is not stamped with the time of import. Both are
properties on a node — no engine change.

### 3.5 The default memory schema

What `install` writes, and what `schema apply --memory-defaults` applies on request.

| | |
|---|---|
| Labels | `Person`, `Org`, `Project`, `Concept`, `Event`, `Note`, `Entity` (provisional) |
| Full-text | `Note.text`, `Concept.summary`, and the name field of each entity label |
| Rules | `SAME_AS` per entity label |
| Property indexes | key-equality on the name fields |

Shipped as a schema file so it is inspectable, diffable and idempotent.

**[verified]** The whole schema is expressible in the existing type. `Schema`
(`crates/core-api/src/schema.rs:51-67`) already carries:

```rust
pub fulltext: Vec<(String, String)>,   // (label, field)
pub indexes:  Vec<(String, String)>,
pub rules:    Vec<RuleDef>,
pub views:    Vec<ViewDef>,
pub roles:    Vec<RoleDef>,
```

and `apply_schema` (`schema.rs:113`) validates every rule, view and role *before* touching the
database and returns a `SchemaDiff` (`schema.rs:75`). So this layer declares a schema file; it
does not extend a format. Nothing new is needed in the engine.

> **Correction, 2026-09-30 (C6).** `install` does **not** write `SAME_AS`, and
> `--memory-defaults` does not apply it. A store never gains a rule silently
> (`SKILL.md:66`), and `memory_defaults()` is also the schema of every
> `ingest-git` store and of the demo store. The rules are the opt-in preset
> `memory_identity()`, applied by `mushroomdb schema apply <db>
> --memory-identity`, which states its backfill before it writes; the
> `suggest_rules` tool offers it. The table's "Rules" row is therefore empty
> for a new store.

## 4. Surface changes

### 4.1 Changed tools

| Tool | Change | Breaking? |
|---|---|---|
| `recall` | reimplemented for natural language; `identifier_terms` gate deleted; distinguishes no-match from no-index | Behavioural — it returns results where it used to return nothing. No caller depended on empty. |
| `remember` | optional `entities` / `facts`; unknown `about` creates a provisional node instead of erroring; richer return | Additive. `text`-only calls unchanged. |
| `find_similar` | `min` default unified across MCP (0.8) and Python (0.0) | **Yes, and silent** — §5.1 |

### 4.2 New tools

Four, taking the memory surface from nineteen to twenty-three. **Settled as O-1 (§9): all four.**
The listing is ranking and costs tokens in every session — 0.6.1 spent a release on a tool-list
token diet (−58%), so §8 records the new listing's per-session cost rather than assuming it is
free.

| Tool | Question it answers | Backing |
|---|---|---|
| `forget` | *"forget that"* | Tombstones a node or retracts a fact and states plainly that history still holds it. **Weaker justification than an earlier draft claimed** — deletion *is* reachable from MCP today, but only by hand-writing Cypher `MATCH … DELETE` through the `query` tool (`mcp.rs:385-396` routes writes to `query_write`). So this tool buys discoverability and a safe shape rather than a missing capability — **except for property removal, which is genuinely unreachable: the Cypher subset has no `REMOVE`**, so `remove_prop` (`db.rs:6840`) has no MCP path at all. |
| `schema` | *"what's in here?"* | **[verified]** The only schema introspection in the tree is `repograph::brief`/`SchemaBrief` (`brief.rs:170`) — CLI-only, and inside the deleted module (§1.4). `stats` returns counts and rules and carries **no labels, property fields, edge types or index declarations** (`db.rs:375-397`). An agent on Claude Desktop has no `SessionStart` brief and no way to learn a store's shape but guessing Cypher. Note `SchemaBrief` also omits indexes, and there is no public enumerator for equality indexes — only `is_index_enabled(label, field)` (`db.rs:7419`) — so a small accessor is part of this tool. |
| `suggest_rules` | *"what relationships are in my data?"* | **[verified]** `GraphDb::suggest_rules` (`db.rs:7167`) → `Vec<RuleSuggestion { def, est_edges, examples, rationale }>`. On CLI (`mushroomdb suggest`) and HTTP (`GET /suggest`), absent from MCP. Completes the "builds itself" story: the store proposes, the agent relays, the human approves, `create_rule` executes — matching the convention that a rule is never created silently (`SKILL.md:74`). It never auto-accepts; the caller must pass `suggestion.def` to `create_rule`. |
| `analyze` | *"what matters here?" / "what clusters exist?"* | One tool, `kind: central\|clusters\|components\|degree`, over `pagerank` (`db.rs:8037`), `connected_components` (:8055), `degree_centrality` (:8075) and `communities` (:8096). **Correction: they are not uniformly exposed** — `communities`, the Louvain pass §3.3 needs, has **no HTTP route at all** and is CLI-only. None of the four is on MCP or in Python. PageRank over a memory graph is a recall primitive: it is how "what matters most here" gets answered. One tool rather than four, for listing economy. |

> **Correction, 2026-09-30 (C7).** As built: `forget` says history holds what
> it removed only until `migrate`, `snapshot --truncate` or `--retention`
> prunes the log; lists, and does not delete, the notes that still state a
> retracted fact; and refuses a rule-derived edge, naming the rule. `schema`
> is backed by `core_api::memory::brief` (moved there by plan 2) plus an
> `index_pairs()` enumerator. `suggest_rules` drops every proposal over a
> bookkeeping field — on a store `remember` filled, those were all of them —
> and emits arguments `create_rule` accepts unchanged; every proposal is global.
> `analyze` runs with no wall-clock budget so the same store gets the same
> answer, bounds its reply at 50 rows, and adds `identities`.

### 4.3 Python binding parity

The binding is the most complete non-MCP surface and still absent: all four graph algorithms,
all of full-text, all of views, all of subscriptions, and the rule lifecycle (`delete_rule`,
`rebuild_rule`, `rules`, `suggest_rules`). 0.7 adds the algorithms, full-text and the rule
lifecycle — the three the memory story depends on. Views and subscriptions stay out.

**Naming hazard for the implementing task.** Python already has `degree()` and `degrees()`
(`bindings/python/src/lib.rs:798`, `:841`), which are the per-node adjacency-degree API
(`GraphDb::degree`, `db.rs:11644`) — **not** `degree_centrality` (`db.rs:8075`). Adding the
centrality algorithm under either existing name would silently change what a working call
returns. Pick a distinct name.

**Also:** `enable_fulltext` is **not idempotent** — it returns `Err(RuleInvalid)` on an
already-enabled pair, and `disable_fulltext` returns `Err(RuleNotFound)` on a disabled one.
`apply_schema` applies full-text idempotently (`schema.rs:272-281`), which is why §3.5 goes
through the schema rather than calling the setter directly.

## 5. Breaking changes and migration

0.7.0 is the first breaking release. Under Cargo semver the minor slot is the breaking position
for `0.x`: `^0.6.x` does not match `0.7.0`, so nothing breaks for anyone who does not
deliberately upgrade.

### 5.1 What breaks

| What | Who | Severity |
|---|---|---|
| 7 code-graph MCP tools (`explore`, `map`, `context`, `impact`, `owners`, `why`, `sync`) | code-graph users | Loud. Documented migration is already published: pin `mushroomdb@0.6.x` (`v0.6.4-data-layer-spec.md:103`) |
| 3 install hooks (`--intercept-grep`, `--impact-before-edit`, `--enrich-grep`) | same | Loud — flags rejected |
| `find_similar` `min` default unified | callers who never named `min` | **Quiet: no error, different results.** The only genuinely dangerous item. Deferred to 0.7 by name twice (`v0.6.11-time-and-vectors-spec.md:222`). Needs the loudest line in the changelog. |
| Tool listing composition | hosts caching a tool set | Mild — hosts rebuild from `tools/list` |

`ingest-git` **stays**, positioned as a data source (`README.md:26`). Only the tools, hooks and
positioning go.

## 8. How this release is measured

§1.2 is the reason this section is not an afterthought.

### 8.1 The gate that was missing

**A first-run round-trip against the real binary over stdio**, not a unit test and not against a
list the test declares itself — the prior version of exactly this test compared against its own
copy of the tool list and passed with the bug reintroduced
(`docs/roadmap/road-to-0.7-plan.md:186-193`).

```
fresh store → upsert_entity → remember → recall   ⇒  recall returns the fact
fresh store → remember{about:[unknown]}           ⇒  succeeds, creates a provisional node
fresh store → recall{topic:"<natural question>"}  ⇒  returns a hit, or names the missing index
```

Reverting any part of §3.1 must fail it.

### 8.2 The fragmentation probe — decides 0.8, runs in 0.7

Take the 2,000-entity association world, split a known fraction of entities into aliases, and
measure how much rule accuracy drops when one entity's properties are fragmented across
several nodes. Report it as a curve against alias count.

- Small degradation ⇒ link-only is correct indefinitely; §3.3's accepted cost is real and cheap.
- Large degradation ⇒ the canonical node is 0.8's headline and the non-goal in §2 is revisited
  on evidence.

Either way Decision 5 stops being an argument and becomes a number. Written before the run, per
the pre-registration convention.

> **Pre-registered, 2026-09-30, before the run:**
> `benchmarks/fragmentation/PREREGISTRATION.md`. The world has no Person and
> only leaf rules, so the probe adds two conjunctions. Result:
> `benchmarks/fragmentation/results/20261001T060009Z/summary.md` — LARGE.

### 8.3 `SAME_AS` quality

A hand-labelled alias set with a pre-registered precision floor. Precision matters more than
recall: a false merge corrupts every downstream answer, a missed one only loses a fact.

> **Pre-registered, 2026-09-30, before the run:**
> `benchmarks/identity/PREREGISTRATION.md`. §8.3 adds a recall floor and a
> true-positive floor, without which a rule that links nothing passes. Result:
> `benchmarks/identity/results/20261001T061131Z/summary.md` — PASSED. The run
> used a debug build rather than the procedure's `--release`, to save disk;
> the gate is deterministic, so the profile does not change its numbers.

### 8.4 Close the failure shape

**A CI step reporting how many `#[ignore]`d tests exist against how many executed.** 28 exist,
CI runs 8, and the 20 that never run include every memory-ceiling and scale-growth assertion.
This project's own retro named this the cheapest durable fix (`road-to-0.7-plan.md:468-472`);
0.7 is adding subsystems, so it lands before them rather than after.

Also: one assertion per test in the scale suite, so a failure cannot mask its successors — the
mechanism that hid two of three red HNSW gates for three releases.

### 8.5 The cost of the listing we just grew

O-1 takes the memory listing from 19 tools to 23. 0.6.1 spent a release cutting that list 58%
because it is sent every session. **Record the new listing's serialized size and per-session
token cost, before and after**, in the release notes. Not a gate — a number, so the 21% growth
is a measured trade rather than an assumed-free one. If it is large, the `Advanced:`
description-prefix trick already used for graph tools is the lever.

> **Correction, 2026-09-30 (C8).** The `Advanced:` prefix is a ranking lever,
> not a size lever — it adds ten bytes per graph tool. Measured: the default
> listing went from 19 tools and 23,548 bytes to 23 and 26,924 (+14.3%);
> `scripts/measure-tool-listing.py` takes it.
