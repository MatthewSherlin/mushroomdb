# v0.6.11 — time in the graph, and a smaller vector store: design

**Date:** 2026-09-23
**Status:** Draft — **three owner decisions assumed, not confirmed** (§7 D1, D4, D6). Every
one is marked; override any of them and the affected contract changes.
**Owner:** Matthew Sherlin
**Branches from:** `main` at `51cfb62` (the v0.6.10 tag plus the docs correction in #26).

**Source:** the v0.6.10 defect ledger's two deferred rows, and a re-reading of the
committed association-benchmark run
[`20260911T065400Z`](../../benchmarks/agent-tasks/results/20260911T065400Z/summary.md)
against the real deployment's size.

**What the benchmark actually says.** The graph arm answers 12 of 20 tasks in **2 turns
and 1 MCP call at 0.17–0.34× the sqlite baseline's cost**, and loses on exactly six —
all four `assoc-timetravel-*` and two of the four `assoc-retraction-*`. Every loser is a
history question. Those six carry ~67 % of the arm's total cost and all of its variance
(sd $0.0883 against sqlite's $0.0347), which is what leaves the pre-registered cost
interval `[-0.0581, +0.0115]` straddling zero. The run's own
[`classification.md`](../../benchmarks/agent-tasks/results/20260911T065400Z/classification.md)
names the mechanism — *"**date→commit mapping**"* — and records that for task 13 the
engine handed back **exactly the eight-key truth set** and the agent discarded it after
guessing commits 503/587/160/300 for a calendar date.

That classification files all seven sub-1.0 cells as `model`, `tool 0`. This spec takes
the opposite view of the two arm-R zeroes and says so plainly: a surface that requires
the caller to derive a commit index from a date, offers no primitive to do it, and
answers a wrong guess with a plausible wrong result, is a **tool** defect. The benchmark
world had to ship a `days.json` to supply what the engine does not.

This is not a rewrite of 0.6.5–0.6.10. Those documents stay. Do not edit other
`docs/roadmap/v0.6.*` files except the three corrections named in §5.5.

---

## 1. Goal

When it ships:

1. **A date is a first-class way to address history.** `edges_at`, `node_history`,
   `edge_history`, `was_linked` and the `asof` CLI accept an instant as well as a
   commit index, and resolve it to *the last commit at or before that instant*. The
   question "what did that look like on 2026-06-19" is one call.
2. **A store that cannot answer says so.** A store written before this release records
   no times. A date query against it, or against a range below the recorded floor,
   fails by name — it never guesses a commit and never returns a plausible wrong graph.
3. **The vector index stops paying a cache penalty that grows with the corpus.** Rows
   are stored quantised; the ranking the caller sees is still computed in full
   precision. All three scale assertions in `hnsw_scale.rs` go green, including the one
   nobody has been able to see.
4. **The scoreboard is honest.** One panicking assertion stops hiding two others, and
   the three documents that inherited the undercount are corrected.
5. **Nothing an existing caller does changes behaviour.** No WAL record is added, no
   snapshot version moves, and a store that never gains a time map behaves exactly as
   it does today.

## 2. What is true today (read, not assumed)

Every claim here was read from the tree at `51cfb62`.

### 2.1 The engine records no wall-clock time, anywhere

- `WalRecord` (`crates/core-storage/src/wal.rs:5`) has no timestamp on any variant.
- There is no `SystemTime` or `UNIX_EPOCH` in `core-storage/src`, `core-api/src` or
  `core-rules/src`. The only time types are `Instant` and `Duration`, used for lock
  waits (`db.rs:WRITE_LOCK_WAIT`) and bench timing — monotonic, not wall-clock.
- `docs/site/mcp.md:385` states the consequence outright: *"commits carry no dates:
  take `at` from node_history/edge_history commit numbers or the dataset's date→commit
  map."*
- `edges_at(key, at)` already takes `edge_type`, `all_of`, `label`, `direction` and
  `limit` (`docs/site/mcp.md:448`), so **the intersection question is already one
  call**. Only the date is missing.

### 2.2 There is an established sidecar pattern that is not part of any format

`FileId` (`crates/core-storage/src/fs.rs:6`) has four variants: `Wal`, `Snapshot`,
`SnapshotBak`, `Roles`. The comment on `Roles` (`fs.rs:13-15`) is the precedent this
spec leans on:

> *RBAC role definitions sidecar. Written atomically by `apply_schema` when roles
> change; loaded at open. **Never part of WAL/snapshot format.***

`Fs::write_atomic(FileId, &[u8])` (`fs.rs:33`, impl at `:310`) is the write path;
`Fs::path(FileId)` (`:279`) resolves the name.

### 2.3 There is already a vocabulary for "history does not reach that far"

`wal_horizon_floor` (`db.rs:1640`), loaded at open by `read_horizon_floor`
(`db.rs:2388`), is what makes `edges_at` refuse below the retention horizon "naming the
range it accepts" (`docs/site/mcp.md:342`). A time map needs the same shape of refusal
and should reuse the vocabulary rather than invent one.

### 2.4 The distance kernel is at the hardware ceiling; the slab is not

- `VecSlab { dim: usize, data: Vec<f32> }` (`hnsw.rs:467`) is a contiguous f32 slab.
- It has **exactly two readers**: `dist_slots(slab, a, b)` (`hnsw.rs:557`, pairwise) and
  `dist_to(slab, slot, q)` (`hnsw.rs:566`, query-to-node). Both return
  `1 - dot.clamp(-1,1)` and both call `dot_f32` (`hnsw.rs:531`), scalar source over
  `chunks_exact(8)` that LLVM autovectorises. There is no `unsafe`, no `std::arch` and
  no `target_feature` in the file.
- Measured standalone at 1536-D on the target machine: **116.6 ns/eval cache-resident
  (26.3 GFLOP/s, ≈3.3 four-wide FMA issues per cycle — at the NEON ceiling)**, rising to
  185.4 ns at n=2,000 (12.3 MB), 337.5 ns at n=10,000 (61.4 MB) and 470.4 ns at
  n=50,000 (307 MB). The rise is cache residency, not arithmetic.
- The committed 15.48× build-growth figure decomposes as 5× (vectors) × ~1.7×
  (evals/insert still climbing toward the `ef_construction × m0` saturation) × **1.82×
  (the measured per-eval penalty, 185.4 → 337.5 ns)**.
- `HNSW_BLOB_MAGIC = b"MHNS"`, `HNSW_BLOB_VERSION: u16 = 4` (`hnsw.rs:1987`, `:2001`),
  header length 6 (`:2007`). The blob is already versioned and already has a
  version-dispatch path at `:2157` and `:2243`.
- **The build is single-threaded.** No `rayon` in any of the ten crates' `Cargo.toml`;
  no `thread::spawn`, `par_iter` or `scope(` in `hnsw.rs`; `HnswIndex::insert` takes
  `&mut self` (`hnsw.rs:1535`). `Cargo.toml:34` instructs *"Do not enable `threading`
  or `cgemm`"* on `matrixmultiply`.

### 2.6 Why this matters at the deployment's real size

The one production consumer holds ~30,000 talent, ~3,000 companies and ~200 jobs.
Interpolating the committed table (13.212 ms/insert at 10k, 20.361 ms at 50k) puts a
full build at **~9 minutes** and a single re-embed at **~11 ms**. A talent profile
changing *is* a re-embed — remove plus insert — so the assertion nobody could see is

### 2.7 `Corrupt` maps to two different HTTP statuses

`role_mask_err` (`crates/server/src/http.rs:653`) and `graph_err` (`:687`) disagree:
the same corrupt store answers 500 or 400 depending on whether the role-mask memo was

### 2.8 The full-text index is built twice on every open

`WalRecord::EnableFulltext` replay backfills its own `(label, field)` pair with a full
`0..ids.len()` scan (`db.rs:4403-4431`). Every snapshot re-emits one such record per
enabled pair into the replacement WAL (`db.rs:13411-13417`). Then
`fulltext.rebuild_all` (`db.rs:2571` → `fulltext.rs:698`) runs **unconditionally**,
clears `postings` and `doc_len` for every enabled field, and rebuilds the lot —
discarding what replay just produced. Its comment says it exists to *"correct drift
from per-record incremental apply during replay"* (`db.rs:2569`); it has been there
unexamined since the original `feat: full-text lite` commit. `rebuild_all` early-returns
when nothing is enabled (`fulltext.rs:705-707`), so a store with no full-text pairs pays
nothing.

## 3. Non-goals

- **No WAL record is added and no discriminant is consumed.** §5.1 is a sidecar
  precisely so that 0.6.11 has no downgrade hazard. Contrast 0.6.10, where
  discriminant 23 nearly caused silent truncation and needed a V10 snapshot stamp to
  make an older binary refuse loudly.
- **No snapshot version bump.** Stores stay V9, or V10 where multiplicity was opted
  into. The only format version that moves in this release is `HNSW_BLOB_VERSION`.
- **The full-text index is not persisted.** Giving it a snapshot section is the right
  end state and is a second format change; it belongs with the fold work (§3, below).
  Task 6 removes duplicated work only.
- **The open path keeps copying three mmap'd sections to the heap.**
  `ensure_v8_base_sections_loaded` (`db.rs:3098`) does `provenance_raw_bytes().to_vec()`,
  `archived_hnsw_to_owned(...)` and `ivf_bytes().to_vec()`. The rules engine's own
  comment (`core-rules/src/engine.rs:2914`) puts the provenance section at up to
  **115 MiB**, so this can be a nine-figure byte copy that defeats the mmap the snapshot
  format exists to provide. It is lazy — guarded by an atomic and a mutex, and fired by
  WAL replay or `stats()` — not unconditional. It is **out of this release** for the
  same reason as the fold: the bytes are retained for the write path and HNSW needs
  owned state to mutate, so making them zero-copy is a restructuring of how the rules
  engine reads provenance, not a guard. Named here, with D7, so the next engine release
  starts with both.
- *(Was a non-goal. **Promoted to §5.8 by owner decision, 2026-09-23**, with the review
  surface understood and accepted — see D9.)*
- **No parallel HNSW build.** `hnsw.rs:1296-1299` states the invariant: deterministic
  expansion order is *"what keeps the graph a function of the WAL."* Concurrent insert
  makes the graph depend on thread interleaving, breaking WAL-replay equivalence and the
  blob round-trip tests. That is a semantics change, not a perf change, and it is not
  how these gates get closed.
- **No hand-written SIMD.** The kernel is already at the NEON ceiling (§2.4). There is
  nothing to win.
- **No recall floor is lowered.** `hnsw_5k_1536_recall`, the clustered gate
  (`hnsw.rs:3250-3262`: `Prune::Both` → min 0.70, mean 0.95) and every floor in
  `crates/sim-harness` stay exactly where they are. A change that cannot hold them is a
  change that does not ship.
- **No code-graph tool, CLI command or hook is removed.** That is 0.7.
- **No new MCP tool.** `ASSOCIATION_TOOLS` stays at sixteen. The date argument is a
  parameter on tools that already exist.
- **No `find_similar` `min`-default unification.** Still proposed for 0.7, where a
  breaking note is affordable.
- **No HTTP-server hardening.** `GET /health` answers with `nodes` and `edges` to an
  unauthenticated caller (`http.rs:471`, `:433-446`) while `/metrics` refuses a
  role-bound token on the stated grounds that *"counters leak graph size"*
  (`http.rs:1060`); there is no request timeout, rate limit or concurrency limit
  anywhere (`crates/server/Cargo.toml` pulls `tower-http` with `fs` only); SIGTERM does
  `serve.abort()`, killing in-flight requests and subscribers before snapshotting
  (`cli/src/main.rs:734`); and there is no `tracing`, `log`, access log or request id in
  the tree. These are real and they are **0.6.12**. This release changes the engine, and
  mixing a security-shaped server patch into a release that moves the vector format
  makes both harder to review.

## 5. Contracts

### 5.1 `commit_times` — a sidecar, not a format

A fifth `FileId` variant, `CommitTimes`, file name `commit_times.bin`, written with the
existing `write_atomic`. **Never part of WAL or snapshot format**, exactly as `Roles`
is not.

**Shape.** An append-only sequence of `(commit_seq: u64, unix_ms: i64)` pairs, sorted by
`commit_seq`, plus a small header carrying a magic, a version and the floor (the lowest
`commit_seq` the map describes). Entries are written for commits this release and later
produce; nothing backfills history that was never recorded.

**Writing.** One entry per commit, stamped from the system clock at commit time. The
executing agent must confirm the single choke-point through which every commit advances
`commit_seq` (`db.rs:1551`) and stamp there, so no path can commit without recording —
the same discipline that made the multiplicity count correct in 0.6.10.

**Resolution.** `resolve_instant(t) -> Result<u64>` returns the **greatest `commit_seq`
whose recorded time is ≤ t**. Defined on commit order, not on time order, so a clock
that steps backwards (NTP correction) cannot make the answer ambiguous: the map is
scanned by `commit_seq`, and a non-monotonic sample is stored as observed.

**Refusals — each by name, never a guess.**

| Situation | Answer |
|---|---|
| No `commit_times.bin` at all (store predates 0.6.11) | `NoRecordedTime { }` — "this store records no commit times; pass a commit index" |
| `t` is before the map's floor | `TimeBeforeFloor { floor_ms, floor_commit }` — names the range it can answer |
| `t` is after the newest recorded commit | resolves to the newest commit — "as of now" is well defined |
| Map exists but the WAL horizon has moved past it | clamp to `wal_horizon_floor`; never return a commit the WAL cannot reach |

**Truncation.** `snapshot --truncate` discards history, so it must truncate the map in
the same operation and raise the floor. A map entry that outlives the commit it
describes is worse than no entry: it would resolve a date to a commit the engine can no
longer replay.

**Downgrade.** An older binary does not know `commit_times.bin`, does not read it, and
opens the store exactly as it does today. This is the whole reason for the sidecar.
*(§7 D1.)*

### 5.2 The date-accepting surface

Five call sites gain an instant alternative. In every case the existing commit-index
argument keeps working unchanged and the two are mutually exclusive.

| Surface | Today | Adds |
|---|---|---|
| `edges_at(key, at, …)` | `at: u64` commit | `at` also accepts an RFC 3339 instant |
| `node_history(key)` | commit-indexed events | each event carries its recorded time when known |
| `edge_history(a, b)` | same | same |
| `was_linked(a, b, at)` | `at: u64` | instant |
| `mushroomdb asof <dir> --commit N` | commit | `--at <rfc3339>` |

A history event whose commit predates the map reports its time as absent, not as zero.

**Python, HTTP and MCP** take the instant as a string. Passing both an instant and a
commit index is `ValueError` at the call, not a silent precedence rule. *(§7 D2.)*

### 5.3 Quantised rows, full-precision ranking

`VecSlab` gains a quantised representation. Rows are stored as int8 with a per-row
scale; the query vector stays f32 (asymmetric quantisation), so no query-side
quantisation error is introduced.

**The contract the caller sees does not change.** `find_similar`, `pairwise_similar`
and `search_hybrid` return the same shape, and scores remain cosine in `[-1, 1]` with
`distance = 1 - sim`. What changes is that the *candidate search* runs against
quantised rows and the **returned ranking is recomputed in full precision** over the
candidate set before `k` is applied. Quantisation is an accelerator for the beam, not
the final arithmetic.

`dist_slots` and `dist_to` (`hnsw.rs:557`, `:566`) are the only two readers of the slab
(§2.4) and are therefore the only two functions that need a quantised path.

**Blob version.** `HNSW_BLOB_VERSION` goes `4 → 5`. A version-4 blob still loads and
still answers — the dispatch at `hnsw.rs:2157` and `:2243` already exists — and is
rebuilt to version 5 on the next index build rather than at open, so no store pays a
migration cost it did not ask for. *(§7 D4 — this is the assumed decision most worth
overriding.)*

**The gate this must hold.** The clustered recall test (`hnsw.rs:3250-3262`) floors
`Prune::Both` at min 0.70 / mean 0.95 and currently measures mean 0.9950. That is the
thinnest margin of any recall gate in the tree and is where this change fails if it
fails. Task 4 spikes it **before** any of Task 5 is written.

#### Spike result, 2026-09-25 (Task 9): **NO-GO — on performance, not recall**

`crates/core-rules/examples/sq8_spike.rs`, Apple M4 Pro, release profile. It quantises
each gate's own corpus to int8 with a per-row scale, keeps the query f32 (asymmetric, so
the query contributes no quantisation error), and measures recall against the same
ground truth the gates use.

**Recall is payable**, and the rerank is load-bearing:

| | direct | 2xK | 4xK | **8xK** | 16xK |
|---|---|---|---|---|---|
| Gate 1 — 5,000 x 1,536-D (floors 0.90 / 0.95) | **PASS** 0.900 / 0.996 | 1.000 / 1.000 | pass | pass | pass |
| Gate 2 — clustered 128-D (floors 0.70 / 0.95) | FAIL 0.400 / 0.575 | FAIL 0.500 / 0.788 | FAIL 0.700 / **0.9475** | **PASS** 1.000 / 1.000 | pass |

Gate 2 is the tighter one exactly as predicted, and it needs **8xK**. At 4xK it misses the
mean floor by **0.0025** — close enough that a single-factor spike would have reported a
coin-flip as a verdict, which is why the factor is swept rather than assumed.

**The premise does not hold.** Best int8 speedup over the shipped f32 slab, both streaming
one contiguous allocation: **0.92x** — int8 is *slower*. At n=2,000 / 10,000 / 50,000 the
f32 slab runs 342 / 508 / 489 ns per eval against int8's 490 / 518 / 544 ns.

`row[i] as f32 * q[i]` needs an i8-to-f32 widening per element, and that conversion costs
about what the saved bandwidth buys: at 1,536 dims streamed sequentially the prefetcher
keeps a 307 MB f32 slab fed well enough that touching 76.8 MB instead wins nothing. A real
SQ8 kernel avoids the conversion with integer SIMD — a widening multiply-accumulate (NEON
`sdot` / `smlal`) over i8 lanes accumulating in i32 — which scalar source will not
autovectorise into. That is `unsafe` intrinsics or a new dependency, and it is a different
piece of work from the one this spike scoped.

**Two measurement defects found and fixed before the verdict was trusted**, both of which
had produced a wrong answer:

1. The first kernel quantised the query *inside the inner loop*
   (`(q[i] * 127.0) as i32`), adding error the asymmetric design does not have and making
   int8 1.5x slower than the baseline. It also reported Gate 1 direct as **FAIL** at
   min 0.600 / mean 0.824, when properly implemented it **passes** at 0.900 / 0.996.
2. The timing harness held rows in a `Vec<Vec<f32>>` — one heap allocation per row — so it
   measured pointer-chasing between blocks rather than streaming a slab, which is the whole
   premise. `VecSlab` is one contiguous `Vec<f32>`; the harness now matches it.

A 2.30x int8 speedup had been reported to this spec from an earlier investigation. **It is
not reproduced here** and should not be quoted until someone demonstrates it with an
integer-SIMD kernel.

**Decision: Task 10 is cut from 0.6.11, per D5.** Taking a recall risk, a blob-version bump
and an index rebuild for a change whose speedup is unproven is the wrong trade. What would
promote it is an integer-SIMD kernel showing a real win on the contiguous slab — at which
point the recall answer above (8xK rerank) is already known and the work is smaller for it.
The three scale gates stay red and are now honestly counted at three.

### 5.8 The fold shares instead of copying

**Today.** `fold_now` (`db.rs:3379-3393`) builds a `FrozenOverlay` by deep-cloning eight
owned structures — `ids`, `syms`, `topo`, `props`, `labels`, `edge_props`, `roles`,
`fulltext`. There is **no `Arc` in any of those types** (`columns.rs`, `topology.rs`,
`idmap.rs`, `interner.rs`, `fulltext.rs` return zero hits for `Arc<`). `IdMap` alone is
`HashMap<String, u32>` plus `Vec<String>`, so every node key is copied twice.

It runs at every open (`db.rs:2595`), after every snapshot (`:13559`), on a role-sidecar
rewrite (`:8723`), every `FOLD_EVERY_K = 64` commits on the write path (`:5039`), and —
with **no** commit threshold — on **every `refresh()` that applies at least one peer
commit** (`:2754`). That last one is the multi-process shape the README advertises, and
it is O(graph) per refresh.

`props` and `topo` were already made cheap a different way: `restore_v8_base` leaves them
as empty overlays over the zero-copy mmap (`db.rs:2965-2972`), with the comment *"avoids
the O(columns) heap copy at every open."* `ids`, `syms` and `fulltext` were not. **That
inconsistency is the defect.**

**After.** `FrozenOverlay`'s fields become `Arc<_>`, and `GraphDb` holds the same `Arc<_>`
for each. `fold_now` becomes eight `Arc::clone` calls — refcount bumps, O(1). Mutation
goes through `Arc::make_mut`, which clones a structure **only when a frozen overlay still
references it, and only the structure actually being mutated**.

Three consequences, in the order they matter:

1. **A reader that never writes pays nothing.** `refresh()` folds; with `Arc` that fold
   is eight refcount bumps rather than a copy of the graph. This is the largest win and
   it lands exactly where the advertised topology is.
2. **A writer pays at most what it pays today, and usually far less.** After a fold, the
   first mutation of a given structure clones it once — then the live `Arc` is unique
   again and subsequent mutations are free until the next fold. A write touching only
   `props` no longer copies `ids` and the full-text index.
3. **Worst case is today's behaviour**, not worse: a write that touches all eight
   structures once per fold interval pays exactly one clone of each, which is what
   `fold_now` does unconditionally now.

**What must not change.** `ReaderSnapshot` already holds `Arc<FrozenOverlay>`
(`reader.rs:73`), so readers already share the fold; this changes how that value is
*built*, not who can see it. Reader isolation is the invariant: a snapshot taken before a
write must answer exactly as it does today, forever, regardless of what the writer does
next. `Arc::make_mut` is what guarantees it — the frozen side keeps the old allocation.
Any code path that reaches a field through `&mut` without going through `make_mut` is a
correctness bug that would let a writer mutate a live reader's view, and is the one thing
this task can get catastrophically wrong.

Read sites are unaffected: `Arc<T>` derefs to `T`, so the ~170 read references to
`self.ids` and ~106 to `self.syms` compile unchanged. Only mutation sites move.

*(§7 D9.)*

## 7. Key decisions

**D1 — the time map is a sidecar, not a WAL record.** *Assumed, not confirmed.*

A new WAL discriminant would be the obvious home and is permitted —
`docs/format-stability.md:120` makes discriminants 0–23 append-only, and `:220` repeats
it as a standing guarantee. It is still the wrong choice here. `decode_all` (`wal.rs`)
treats any undeserialisable frame as a corrupt tail and returns the valid prefix;
`repair_wal` defaults to `true`, so an older binary would **persist that truncation**.
`docs/format-stability.md:140` records exactly that outcome for discriminant 23 — an
older reader would "stop at the first discriminant-23 frame, lose every commit after
it". 0.6.10 had to stamp a V10 snapshot to make old binaries refuse loudly before they
could reach `decode_all` (`format-stability.md:124`).

A sidecar has none of that: an unknown file is simply not read. It also keeps this
release to exactly one format change (the HNSW blob), which is what makes shipping both
halves together defensible.

The cost is that the map is not covered by WAL CRC or snapshot integrity, so a torn or
deleted `commit_times.bin` degrades date queries to `NoRecordedTime` rather than
corrupting anything. That is the correct failure direction and is why §5.1's refusals
are by name.

**D2 — an instant and a commit index are mutually exclusive.** Accepting both with a
precedence rule invites exactly the bug this release exists to fix: a caller believing
it asked for a date while the engine answered a commit. Raise.

**D3 — resolution is "last commit at or before", defined on commit order.** Any other
rule is ambiguous under a backwards clock step, and a date question whose answer depends
on NTP is not a contract.

**D4 — a version-4 blob is not migrated at open.** *Assumed, not confirmed.* It loads,
answers, and is rebuilt to version 5 at the next index build. The alternative —
rebuilding at open — turns one upgrade into a multi-minute stall at 30k vectors on a
store whose owner only wanted to read. Override this if you would rather every store
pay once, immediately, and be done.

**D5 — Task 5 is cuttable and Task 4 is the gate.** Everything else in this release is
confident; SQ8 is speculative and its recall margin is the thinnest in the tree. A
speculative perf change must not hold a confident feature change hostage. If the Task 4
spike cannot hold the clustered gate with full-precision rerank, **ship 0.6.11 without
Task 5** and carry the scale gates forward, red and now honestly counted at three.

**D6 — Task 6 is dropped rather than guessed.** *Assumed, not confirmed.* The duplicate
full-text build is provable waste, but `rebuild_all` is a correctness backstop for
replay drift. Removing a backstop on the strength of "replay looks right" is how a
silently wrong search index ships. Establish it or leave it.

**D7 — superseded by D9.** The fold was a non-goal in this spec's first draft, on the
grounds that at 33k keys it costs single-digit MB and that MVCC surgery does not belong
in a release that already moves the vector format. The owner overrode it. The reasoning
above is preserved in §5.8; the decision is D9.

**D9 — the fold is in, and it is built to be revertible.** *Owner decision, 2026-09-23,
made with the review surface stated and accepted.*

The argument against was never that the change is wrong — it is that this release would
then carry three things a reviewer must hold at once: a new sidecar format, a vector
representation change, and the MVCC reader path. The argument for is that the fold is the
single largest general-engine win available, that `FrozenOverlay` is *already*
`Arc<FrozenOverlay>` at the reader boundary (`reader.rs:73`) so the blast radius is the
construction site rather than the consumers, and that `Arc<T>`'s deref leaves every read
site untouched.

Two conditions make it safe to accept:

1. **It lands as its own task, touching no file the other tasks touch for their own
   reasons**, so `git revert` of that one commit range restores the release without
   unpicking anything else.
2. **It is gated on a reader-isolation proof, not on the test suite passing.** A suite
   that passes proves no *existing* test noticed; it does not prove a writer cannot
   mutate a live reader's view. Task 14 Step 2 writes that proof first.

If the isolation tests cannot be made to hold, revert the task and ship the release
without it — exactly the licence D5 gives Task 10.

**D8 — the benchmark is re-run at the deployment's size, not the harness default.**
The association world defaults to `--scale 2000` (`association/truth.py:646`) while the
real store holds ~33k entities. A gate that justifies a data layer should be measured at
the size that layer actually serves. At 30k the files-and-grep arm should stop being
able to compete at all, which is the honest fight rather than a favourable one — and the
harness already supports the flag.
