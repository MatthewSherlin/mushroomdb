# v0.10 — the graph database for any app that needs a graph

Status: approved by the owner, 2026-10-19. Builds on `main` after v0.9.2.

This is the master spec. Six workstream documents sit beside it in `docs/roadmap/v0.10/`
(W1–W6) with the unit-level detail: surfaces, internal design, tests, build units. **Where a
workstream document and this file disagree, this file wins** — §4 lists every such resolution.

---

## 1. Intent

mushroomdb has been built and pitched as memory for AI agents. In 0.10 it becomes the graph
database a developer picks for *any* app that needs a graph — social features, permissions,
recommendations, knowledge bases, dependency maps, fraud rings — with the agent-memory features
(rules that derive edges, time travel, scoped visibility, explanations, full-text + vector + hybrid
search, MCP tools, `remember`/`recall`) kept whole and repositioned as the reasons to choose it
over another graph database, not as its identity.

Why now: the research for this release (gitignored notes) found that general graph developers
decide first on whether their existing queries, drivers and tools work, then on licensing, then on
embedded-versus-server shape, then on proof of speed and safety. mushroomdb already leads on
licensing (MIT or Apache-2.0), on shape (one Rust binary, embedded or server) and on the
differentiators no other graph database combines. It loses on compatibility and on proof. The
most-used embedded graph database was archived in October 2025, which leaves that position open.

0.10.0 ships as **one release**. Agents build it in parallel on feature branches.

## 2. Goals, non-goals, anti-goals

### Goals — the four parts (owner-approved)

1. **Speaks the language.** Most real openCypher queries run unchanged: the missing standard
   functions, the syntax gaps, list comprehensions, `MERGE` with a relationship, Date / DateTime /
   Duration / Binary property types, unique constraints, range indexes, CSV import and export,
   fast key-anchored traversal at 1M nodes (ledger row 102), and a published openCypher TCK
   conformance score held by CI.
2. **Connects to everything.** The Bolt wire protocol, so the official drivers in every major
   language and the tools built on them connect unchanged; real interactive
   `BEGIN`/`COMMIT`/`ROLLBACK` transactions in the engine, HTTP, Rust, Python, TypeScript and Bolt;
   every read route on the lock-free reader.
3. **Runs anywhere (self-host).** One-command deploy templates (Fly.io, Render, Railway, Docker
   Compose, a Kubernetes manifest); HTTPS in the published image; access keys with an admin /
   write / read split; a readiness endpoint; CORS; structured logs and Prometheus metrics;
   continuous backup to S3-compatible storage with restore, restore-on-boot and point-in-time
   restore.
4. **Proves it.** Published benchmarks at 1M nodes and above, generated from result files and held
   to them by CI; a data-safety page where every claim names the CI job that would fail if it
   became false; README, docs site and package metadata rewritten for general developers; the
   agent-memory API in its own namespace, still fully supported.

### Non-goals (explicitly out of 0.10)

Storage larger than RAM; replication, HA or failover; a managed hosted service; new native Go /
Java / .NET drivers (Bolt makes them unnecessary); multi-label nodes (§9, answer 5);
`CALL { }` / `EXISTS { }` / `COUNT { }` subqueries, `FOREACH`, pattern comprehensions,
`allShortestPaths` (each parses and fails with a precise "not supported" error); composite and
edge-property indexes; NOT NULL constraints; ACME auto-certificates; a Helm chart; Bolt 6;
GQL-only features.

### Anti-goals — 0.10 fails if any of these happen, even if every feature works

- **An existing store fails to open, or an agent-memory user regresses** (MCP server, plugin,
  hooks, `remember`/`recall`).
- **Anything gets slower or less safe.** Every unit that touches a hot path carries a *measured*
  comparison against v0.9.2 on the same machine — open, first write, query latency, ingest. The
  review of 0.9.2 missed a +44 % open-time regression by reasoning instead of measuring (ledger
  row 116); that does not happen again.
- **0.10 drags on with nothing shipped.** It is one release, but it is cut along §6's waves so
  that a late unit is dropped, not waited for. Bolt and transactions are the most likely to slip
  and are built so that the rest of 0.10 ships without them if they must.
- **The pitch still reads as an agent-memory tool.**

## 3. Constraints

- **House rules for engine changes** (each learned from a regression): a check added for new
  writes never runs on WAL replay in a way that can fail (old records legitimately violate new
  rules; a replay error makes a store unopenable). After a snapshot, `self.topo`/`self.props` are
  overlay-only — reads go through `topo_view()`, `build_props_view`, `base_columns`. Behaviour is
  identical across one batch vs separate commits, reopened vs never-closed, snapshotting vs not,
  and live vs WAL replay vs `open_at`; every engine unit's tests include differential probes over
  those axes. Every engine unit is reviewed by an independent reviewer who *runs* such probes and
  a timing comparison.
- **Format.** Old stores always open. A store that uses no 0.10 format feature stays readable by
  0.9.x indefinitely (§4.1). Every format change is documented in `docs/format-stability.md` and
  covered by the `format-compat` CI job.
- **Dependencies.** Only those approved in §9 (answer 1); any other new third-party dependency needs the owner's approval.
- **No competitor names in the repository.** Code, docs, changelog and marketing copy compare by
  category only ("the incumbent server graph database", "embedded graph databases"). Protocol
  constants that carry a vendor name are allowed in code and tests only (§9, answer 2).
- **No time estimates.** Units are sized S / M / L by complexity and risk.

## 4. Cross-workstream resolutions

These override the workstream documents.

### 4.1 Storage format: V11 is opt-in, like V10

W2 proposed that every 0.10 store migrates to a V11 snapshot at first open. That would make
every upgraded store unreadable by 0.9.x the moment 0.10 opens it, whether or not it uses
anything new, and would rewrite a 1M-node snapshot (5.6 s) at open. Instead:

- **V11 is written only by a store that uses a V11 feature**: a value of a new type (Date,
  LocalDateTime, DateTime, Duration, Binary), a unique constraint, or a range-index declaration.
  `snapshot::version_for` (today `version_for(multiplicity)`, `crates/core-storage/src/snapshot.rs:87`)
  becomes the one place that decides, from the store's declared features: it takes a
  `StoreFeatures` value (multiplicity, new value types present, constraints declared, range indexes
  declared) instead of one flag.
- **The first V11-only record is preceded by a V11 snapshot, in the same call**, exactly as
  `enable_multiplicity()` writes V10 before discriminant 23 (`docs/format-stability.md`,
  "Discriminant 23 is opt-in"). A 0.9.x binary that opens such a store stops at
  `snapshot: unsupported version 11` and leaves the WAL byte-identical, instead of truncating the
  WAL at the first record it cannot decode — which, with `repair_wal` on by default, it would write
  back to disk. A new value type inside an existing record (`SetProp` carrying a `Date`) is a
  V11-only record for this purpose. The check lives at one choke point every write path passes
  through before the WAL append (today `commit_logged_batch`, `crates/core-api/src/db.rs`); TY-12
  confirms that `write_batch`, `ingest_batch`, Cypher writes, rule-derived writes and view updates
  all reach it, with a test per path that a first new-type value moves the store to V11 before the
  record lands.
- A store that never uses a V11 feature keeps writing V9 / V10 and stays downgradable. The
  upgrade guide says so in one line.
- Section 16 (`PROV_RECONCILED`, added in 0.9.2) is unaffected; it is optional in every version.
- W5's string interning (PF-05a) would change the snapshot layout for every store, so it is
  **deferred** to keep the downgrade property; it is the first candidate for 0.11.
- One unit owns the format bump (TY-12). WAL discriminants 24–27 are W2's (constraints and range
  indexes); transactions need none (§4.2); 28–30 stay unassigned.

### 4.2 Transactions: optimistic, with write-conflict detection

W3's optimistic buffer stands — no transaction holds the writer lock — with these corrections:

- **Conflicts are detected, not assumed away.** A transaction records the node and edge keys it
  read or wrote, with the `last_change` commit each had in its base snapshot. `COMMIT` submits one
  `WalRecord::Batch` through the existing compare-and-set path (`write_batch_cas` /
  `NodeUnchangedSince`) with a precondition for every key in that set. There is no edge-level
  precondition: an edge read or written puts both its endpoint node keys in the set, which works
  because `last_change` already advances both endpoints on every edge insert and delete. Any change since the base
  snapshot fails the commit as a transient conflict, which drivers retry. The isolation level is
  **snapshot isolation**: lost updates are impossible; write skew through a label scan (a phantom)
  is possible and documented.
- **Reads inside a transaction see its own writes** by layering the buffered records over the
  base `ReaderSnapshot` as a private, uncommitted delta — the same mechanism the reader already
  uses for its committed delta tail (`crates/core-api/src/reader.rs`) — rather than a separate
  projection. Rules fire at commit only; rule-derived edges from a transaction's own writes are not
  visible inside it (documented).
- Constraint checks (W2) run at commit, under the write guard, against committed state plus the
  batch.
- A committed transaction is one commit number for time travel; a rolled-back one leaves nothing
  in the WAL.

### 4.3 Bolt version set is verified before it is built

W3 targets Bolt 4.4 + 5.0 and defers `LOGON` (5.1). Current official drivers may require a newer
minimum. **TX-9 starts by reading the current official drivers' handshake code and release notes**
(Python, JavaScript, Java, Go, .NET) and records, in `docs/site/bolt.md`, the minimum and maximum
Bolt version each offers. The server supports the smallest set that every one of the five current
drivers negotiates — adding 5.1 `LOGON`/`LOGOFF` (and any later 5.x message a current driver
requires) if that is what it takes. The driver matrix in CI (TX-18) is the proof.

Two handshake rules are already known and are requirements, not findings (technical review,
2026-10-19): current drivers put a **manifest indicator** (`0x000001FF`, the Bolt 5.7+ manifest
handshake) in one of the four slots — the server either implements the manifest exchange or skips
that slot and negotiates from the others; and each slot carries a **version range**
(`[pad, range, minor, major]`, e.g. 5.8 with range 8 = 5.0–5.8), so a slot matches any server
version of that major whose minor lies in `[minor − range, minor]`. A server that matches exact
versions only will not connect to the current Python driver. At a negotiated 5.0, `LOGON` is not
required.

### 4.4 Continuous backup ships the WAL, not just snapshots

W4 set the recovery point to the snapshot interval and re-uploaded `snapshot.bin` every cycle.
Instead:

- **WAL segments are shipped continuously.** The live WAL is append-only; the backup worker
  uploads each new byte range as an immutable segment object (`{prefix}/wal/{generation}/{start}-{end}`)
  on a short cadence (default 1 s, configurable), after the bytes are fsynced locally. The recovery
  point is that cadence, not the snapshot interval.
- **Snapshots and `wal.N.archive` files are uploaded when they are written**, and a manifest
  records which snapshot, archives and segments make a consistent restore point. A truncating
  snapshot starts a new WAL generation.
- Restore (latest or `--at <commit | timestamp>`) is snapshot + archives + segments, replayed with
  the existing open / `open_at` paths. Everything else in W4 §3.1–§3.2 (manifest checksums,
  `LATEST`, retention, restore-on-boot, the advisory bucket lease, `snapshot.intent` excluded,
  shutdown flush) stands.

### 4.6 Smaller calls

- Default Bolt port 7687, configurable. Bolt `basic` auth treats `credentials` as a mushroomdb
  token and ignores `principal`.
- Python and JavaScript drivers are required CI gates; Java, Go and .NET are best-effort
  (connect + read) and become required if they prove stable.
- The openCypher TCK is **vendored** at a pinned tag under `vendor/opencypher-tck/` with its
  Apache-2.0 licence, not a submodule (worktree-built agents and CI need no submodule step). The
  gate fails on any drop below the recorded baseline; the 0.10 target is ≥ 65 % of non-skipped
  scenarios.
- Unique constraints check globally across scopes with an error that does not name or describe the
  conflicting node (W2 TY-D2, option A); the residual probing channel is documented.
- `Binary` values are capped at 1 MiB by default (configurable).
- Range indexes rebuild at open; a range index may cost at most 1.5× the no-index open time at 1M
  nodes, or it gets snapshot persistence (W2 TY-D3).
- Prometheus text format is written by hand (no crate); CORS and JSON logs use features of
  dependencies already present.

## 6. How it gets built

### 6.1 Branches

- `release/0.10` is cut from `main` once v0.9.2 is tagged. It is the integration branch; `main`
  keeps taking 0.9.x patches, merged forward into `release/0.10`.
- Every unit is built on its own branch from `release/0.10` (`v0.10/<unit-id>-<slug>`), in its
  own worktree with its own `CARGO_TARGET_DIR`, and lands by pull request into `release/0.10` on
  green CI. Engine units also need the independent review in §3.
- `release/0.10` merges to `main` as one pull request, and v0.10.0 is tagged on that merge.

### 6.2 Hot files

Four files take edits from several workstreams. Units touching the same one land one at a time,
in wave order, each rebased on the last:

## 7. Release gates for 0.10.0

All must hold on the release commit:

- Full workspace suite green on Linux and macOS; Windows build green.
- **Measured against v0.9.2 on one machine** (median of ≥ 5): open time, first write, second
  write, ingest throughput and the PF-02 query shapes at 100k and 1M nodes, for a plain store, a
  memory store and a store with top-k rules. No regression above noise (> 5 %) without a line in
  the changelog explaining it and the owner's sign-off.
- Row 102 shape: p50 < 1 ms at 1M nodes.
- The first write that moves a store to V11 costs one snapshot write at that size (5.6 s at 1M
  nodes today); measured, documented in the upgrade guide, and not counted as a regression.
- TCK pass rate ≥ 65 % of non-skipped scenarios and not below the recorded baseline.
- Driver matrix green for the required drivers (§4.6).
- `format-compat`: every fixture V5–V10 opens; a V11 store is refused by name by the pinned 0.9.x
  binary with its WAL byte-identical; a store using no V11 feature still opens under 0.9.x.
- Backup round-trip and PITR green against MinIO; template lint green.
- Concurrency gate: read p99 under sustained writes no worse than v0.9.2, target ≤ 2 ms at 10k
  nodes, 50 writes/s.
- Data-safety page: every claim names a job, and every named job runs on the release commit.
- `scripts/check-defect-ledger.sh` OK; the changelog and upgrade guide list every break.
- No competitor names: the existing claims check extended to `deploy/`, `integrations/` and new
  docs.

## 9. Decisions

### Decided by the owner

- Positioning: any app that needs a graph; agent memory a strength, not the identity.
- Hosting in one form: a finished self-host story; no managed service.
- One big release, built by agents in parallel on a feature branch.
- The four parts in §2 and the out-of-scope list (larger-than-RAM storage, replication, managed
  service, native drivers).

### Answered by the owner (2026-10-19: "continue with your best thoughts" — the recommendations stand)

1. **Dependencies approved:** `object_store` (`aws` feature) for S3 backup, `csv` for import,
   `gherkin` for the TCK runner (test-only crate), and `time` (preferred; or `chrono`) and `rand`
   promoted from transitive to direct. Any further new dependency still needs approval.
2. **Vendor-named protocol constants** (Bolt error-code prefixes, the drivers' default database
   name, the routing URI scheme) may appear in code and tests only — never in docs prose,
   marketing copy or the changelog, which say "standard error codes" and "routing-scheme URIs".
   The claims check enforces the docs side.
3. **Scale proof:** 1M and 3M nodes are measured on the reference laptop (24 GiB) and published in
   0.10. A 10M run on a rented ~32 GiB cloud machine is an optional, owner-only step on the release
   checklist; 0.10 does not wait for it.
4. **LangChain and LlamaIndex adapters are published** to PyPI in 0.10, versioned in lockstep
   (PS-7).
5. **Multi-label nodes stay out of 0.10.** Multi-label patterns fail with a precise "not supported"
   error, and the docs' compatibility claim states the caveat.
