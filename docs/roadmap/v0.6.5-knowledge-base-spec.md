# v0.6.5 — the knowledge-base release: design

**Date:** 2026-09-11
**Status:** draft for owner review
**Branches from:** `feat/v0.6.4-data-layer` (0.6.4 is on PR #18)
**Owner decision it implements (2026-09-11):** a team running mushroomdb as a sidecar graph beside a
document knowledge base wrote down what stops it becoming the primary store. Every blocker on that
list is small and concrete. 0.6.5 fixes the ones that are engine and CLI work, and says plainly
which ones are not this release's.

## 1. Goal

Make the engine honest about what it retains, stop it throwing away history by default, stop a
snapshot costing nine times the data it holds, and let the two things the product sells —
time travel and per-caller visibility — compose with each other. Seven items, each small. When it
ships:

1. Every history read reports the horizon. No read answers "nothing happened" when the truthful
   answer is "that is no longer retained".
2. The default is **keep everything**. Retention is a thing you configure, never a thing that
   happens to you. `stats` and `doctor` say where history starts.
3. A snapshot carries one copy of its string table instead of one per string column.
4. `as-of` composes with a role token and with a client mask, on HTTP and on MCP.
5. A role can be `label in [...]` plus one equality/`in` property predicate — the smallest mask
   shape that expresses "this reader sees published documents", evaluated at read time and memoised
   between writes.
6. `serve` can open from the newest snapshot in a directory, and there is a page that tells an
   operator what to mount, how often to snapshot, how to back up, how to restore, and what a restart
   without a volume costs.
7. The rule-derived-edges-survive-a-snapshot bug class has a test per rule kind, including the
   via-hop and chained shapes that shipped broken in 0.5.x.

No benchmark gate. Nothing in this release is a claim about agent performance; it is a set of
defects and a format fix, each with its own test.

## 2. What we learned

The findings below are a deployment report from the owner's team, written after running the engine
as a sidecar graph beside a document knowledge base. They are **not** committed measurements in this
repository, and no number from this section may appear in `README.md`, `docs/site/**`, `llms*.txt`
or `CHANGELOG.md`. Every number that reaches a product-facing document in 0.6.5 comes from a test
this release commits.

**What blocks it from being the primary store**

| Finding | What 0.6.5 does |
|---|---|
| History silently expires. Automatic snapshots keep the newest **8** WAL archives; past that horizon `node_history`, `edge_history` and `query_at` answer as if nothing happened. Revision history is the knowledge base's core promise. | §3 (horizon honesty) + §4 (keep-all default) |
| Durability is self-managed. Whole graph in RAM, one node. On a container platform the store vanishes on restart unless someone owns a volume-plus-snapshot-plus-restore runbook, and nobody does. | §8 (restore on boot + the runbook page) |
| ACL primitives are not there. Masks are key allow-lists only; no predicate masks; time travel refuses to compose with role tokens or masks. | §6 (time travel × masks) + §7 (predicate masks) |
| Pre-1.0 track record: 0.5.x shipped a data-loss bug — via-hop rules retracted all their edges after a snapshot — caught by dogfooding, not by a test. | §9 (a round-trip test per rule kind) |

**What is live but costs more than it should**

| Finding | What 0.6.5 does |
|---|---|
| **Snapshot bloat.** 37 MB on disk for under 4 MB of properties, because each string column carries a full copy of the string table, and snapshots are now automatic. | §5 (one shared interner section) |
| **Scoped readers pay the mask query** — about **10 ms at 2,000 nodes**, growing with the readable set. Needs a short-TTL cache, or predicate masks upstream. | §7 (predicate masks + a commit-keyed memo) |
| `was_linked` commit numbers reset every boot, because the store is disposable. | §8 documents it; the volume makes it stop being true |
| Two copies to keep in sync; the write hook is post-commit and swallows failures. | Out of scope — the sidecar's own code |

**Deferred, with their numbers** (see §11): HNSW build is superlinear and welded to rule creation —
**23 s at 2,000 documents, 252 s at 10,000**, did not finish 50,000 inside ten minutes, then about
**111 ms per embedding write**. The sidecar therefore runs brute-force vector search (about 5 ms at
2,000, 106 ms unmasked at 50,000) and keeps semantic edges on an external vector index, because the
exact rule that would replace it is quadratic (about 41 s at 5,000). That is 0.6.6's item, not this
one.

Not a concern any more, per the same report: packaging, the Python binding gaps (`edge_history`
shipped in 0.6.3), CI gates, and write-path correctness.

## 3. History horizon honesty

### 3.1 What is true today (read, not assumed)

The engine is **already honest on three of the five reads**, and the sidecar report is wrong about
`was_linked`:

| Read | Below `wal_horizon_floor` today | Where |
|---|---|---|
| `edges_at(key, commit)` | `CommitOutOfRange { commit, total }` | `crates/core-api/src/db.rs:9606-9611` |
| `was_linked(a, b, t, at_commit)` | `CommitOutOfRange { commit, total }` | `crates/core-api/src/db.rs:9445-9456` |
| `open_at` / `query_at` (`asof`) | `CommitOutOfRange { commit, total }` | `crates/core-api/src/db.rs:2597-2602`, and again at `2615-2617` when the genesis chain is broken |
| `node_history(key)` | **returns `Vec<HistoryEntry>` over whatever survives, silently short** | `crates/core-api/src/db.rs:9032`, scans `all_frames()` at `8882` |
| `edge_history(a, b)` | **returns `HistoryResult { items, total_commits }` — `total_commits` is `floor + frames.len()`, so the reader cannot tell `floor` from zero** | `crates/core-api/src/db.rs:9237`, result built at `9417-9420` |

So the real defect is narrower than reported and has two halves:

**(a) The error never names the floor.** `GraphError::CommitOutOfRange { commit, total }`
(`crates/core-storage/src/types.rs:75`) prints *"commit {commit} is out of range; valid range is
`0..{total}`"* (`types.rs:140-143`). On a pruned store the valid range is `floor..total`, so the
message is actively misleading: it tells a caller to retry at commit 0, which will also fail. The
HTTP layer is worse — `crates/server/src/http.rs:2020-2024` and `2036-2040` throw the range away
entirely and return `{"error": "commit N is out of range"}`.

**(b) The two commit-less reads carry no floor.** `HistoryResult` (`crates/core-api/src/history.rs:12`)
has `items` and `total_commits` and nothing else; `node_history` returns a bare `Vec`. The wire
shapes follow: `node_history_json` (`crates/server/src/json.rs:229`) emits
`{key, history, total_commits}`, `edge_history_result_json` (`json.rs:200`) emits
`{a, b, events, total_commits}`. `docs/site/timetravel.md:353` already states the gap in prose —
*"a pruned commit's events are missing with no error"* — which is honesty in the documentation and
dishonesty in the API.

### 3.2 New behaviour

**The error names the range.** `GraphError::CommitOutOfRange` gains a third field:

```rust
CommitOutOfRange { commit: u64, total: u64, floor: u64 }
```

`Display` becomes, for `floor == 0`, byte-identical to today; for `floor > 0`:

```
commit 3 is out of range; valid range is 12..40 — events before commit 12 are not retained
```

Six construction sites in `db.rs` (`2598`, `2601`, `2616`, `9446`, `9452`, `9607`) pass
`self.wal_horizon_floor`. HTTP's two hand-written 400 bodies are replaced by the `Display` string so
one sentence is the answer everywhere.

**The commit-less reads carry the floor.** `HistoryResult<T>` gains `horizon: u64` — the oldest
commit index still reachable — and `node_history` changes shape to match `edge_history`:

```rust
pub struct HistoryResult<T> { pub items: Vec<T>, pub total_commits: u64, pub horizon: u64 }

pub fn node_history(&self, key: &str) -> Result<HistoryResult<HistoryEntry>>  // was Result<Vec<_>>
pub fn edge_history(&self, a: &str, b: &str) -> Result<HistoryResult<EdgeHistoryEvent>>  // unchanged shape
```

Wire shapes gain one field each and lose none: `{key, history, total_commits, horizon}` and
`{a, b, events, total_commits, horizon}`. When `horizon > 0`, every rendering surface adds one line
of prose after the list:

```
events before commit 12 are not retained
```

**Surfaces that must say it** (each verified present today):

| Surface | File | Change |
|---|---|---|
| MCP `node_history`, `edge_history` | `crates/server/src/mcp.rs:759`, `:775` | `horizon` in the JSON; the tool descriptions at `mcp.rs:1164`, `:1175` say a pruned store reports it |
| MCP `was_linked` | `crates/server/src/mcp.rs:792` | error text is `Display`, which now names the range |
| HTTP `GET /node/{key}/history`, `GET /history/edge` | `crates/server/src/http.rs:1873`, `:1932` | `horizon` in the JSON (both the role-masked branch and the full branch) |
| HTTP `GET /history/was_linked` | `crates/server/src/http.rs:2020`, `:2036` | 400 body carries the full `Display` string |
| CLI `asof` | `crates/cli/src/lib.rs:1171` | the header line becomes `as-of commit N of M (history reaches back to commit F)`; today it reads `wal_commit_count_at` (`crates/core-api/src/lib.rs:90`), which counts **only live `wal.bin` frames** and so already prints the wrong `M` on any archived store — fixed to `wal_total_commits()` / `wal_horizon_floor()` off the opened handle |
| Python `node_history`, `edge_history` | `bindings/python/src/lib.rs:583`, `:604` | `node_history` returns a dict `{key, history, total_commits, horizon}` instead of a list; `.pyi` follows |

### 3.3 Implications

- **Breaking, Rust API:** `CommitOutOfRange` gains a field (exhaustive matches must add it or use
  `..`); `GraphDb::node_history` changes return type. Both are pre-1.0 and both are named in the
  changelog. Eight exhaustive matches exist in this repository's own tests
  (`crates/core-api/tests/asof.rs:308,320,380`, `history.rs:372,380,394`, `edges_at.rs:217`) and are
  updated in the same commit.
- **Breaking, Python:** `db.node_history(key)` returns a dict, not a list. Named in the changelog
  with the one-line migration (`db.node_history(k)["history"]`).
- **Additive, wire:** every JSON body gains `horizon` and loses nothing.
- **No format change** for this item.

### 3.4 Test

`crates/core-api/tests/wal_archives.rs` gains `horizon_is_reported_by_every_history_read`: build a
store, snapshot to two archives with `set_wal_archive_retention(Some(1))` so the floor advances past
0, then assert (i) `node_history(k).horizon == db.wal_horizon_floor()` and the same for
`edge_history`; (ii) `was_linked`, `edges_at` and `open_at` at `floor - 1` each return an error
whose `to_string()` contains `valid range is {floor}..{total}` and `not retained`. Server tests
assert the `horizon` key is present in all four JSON bodies and that the 400 from
`/history/was_linked` carries the range. A Python test asserts the dict shape.

## 4. Retention default: keep everything

### 4.1 What is true today

`AUTO_SNAPSHOT_RETENTION: u32 = 8` (`crates/cli/src/lib.rs:74`) is applied by
`snapshot_automatically` (`crates/cli/src/lib.rs:85-88`), which is the single place the automatic
disposition and the automatic bound are set together. It is reached from `serve --snapshot-every`
and graceful shutdown (`snapshot_shared`, `lib.rs:109`), and from `ingest-git` / `sync`
(`crates/cli/src/ingest_git.rs:1085`). The engine stores the policy in
`set_wal_archive_retention(Option<u32>)` (`crates/core-api/src/db.rs:8841`) and prunes at
`db.rs:10355`. A manual `mushroomdb snapshot` with no `--retention` already keeps everything
(`crates/cli/src/lib.rs:1427`, asserted at `lib.rs:3893-3906`).

The doc comment at `crates/cli/src/lib.rs:46-73` argues for eight, and the argument is sound about
disk and wrong about priority: it trades a bounded directory for an unbounded loss of the thing the
archives exist to hold. `docs/site/durability.md:55` and `docs/site/timetravel.md:370-384` both
state the 8 as the default.

### 4.2 New behaviour

```rust
/// How many WAL archives a snapshot mushroomdb takes on its own keeps.
/// `None` = all of them. Retention is configured, never defaulted.
pub const AUTO_SNAPSHOT_RETENTION: Option<u32> = None;
```

`snapshot_automatically` calls `db.set_wal_archive_retention(AUTO_SNAPSHOT_RETENTION)`. Nothing else
changes: the pruning code path, `--retention N`, and `set_wal_archive_retention` all stay exactly as
they are, and a user who wants a bound sets one.

Disk growth becomes the operator's to see, so the two commands that can see it report it:

- `Stats` (`crates/core-api/src/db.rs:267`) gains `history_floor: u64`, read straight off the
  `wal_horizon_floor` field — free, no WAL scan, so `stats()` stays infallible and `&self`.
  `format_stats` (`crates/cli/src/lib.rs:2275`) prints `history: reaches back to commit N` and, when
  `N == 0`, `history: complete (nothing pruned)`.
- `doctor`'s `store` check (`crates/cli/src/doctor.rs:617-635`) appends
  `, history from commit N of M` using `wal_horizon_floor()` and `wal_total_commits()` — doctor can
  afford the scan, `stats()` cannot.

### 4.3 Implications

- **Behaviour change, not API change.** A store that previously self-pruned now accumulates
  `wal.<N>.archive` files. Named in the changelog with the one-line opt back in
  (`mushroomdb snapshot <db> --retention 8`, or `--truncate` to drop history outright).
- `Stats` gains a serialised field — additive on HTTP `/stats`, MCP `stats` and Python `stats()`.
- No format change.

### 4.4 Test

`crates/cli/src/lib.rs` tests: `automatic_snapshots_keep_every_archive` — the existing
`snapshot-retention` test at `lib.rs:3832` currently asserts the count equals
`AUTO_SNAPSHOT_RETENTION as usize` (`lib.rs:3856`); it is inverted to assert that after ten
automatic snapshots there are ten archives and `wal_horizon_floor() == 0`. A second test asserts
`--retention 2` still prunes to two. `format_stats` and `doctor` get string assertions for the
horizon line on a pruned and an unpruned store.

## 5. Snapshot string-table bloat

### 5.1 What is true today

`ColumnData::Str { ids, present, strings }` (`crates/core-storage/src/v8/layout.rs:60-65`) holds a
`Vec<String>` per column. The encoder builds columns by packing the `ColumnStore` and re-decoding it
(`columnstore_to_data`, `crates/core-storage/src/v8/encode.rs:567-583`). The pack format writes the
intern table **once** (`decode_all_columns`, `encode.rs:643-656`) and then hands every string column
a `strings: intern_strings.clone()` (`encode.rs:710-714`) — the *whole* table, not that column's
values. `encode_v8` then rkyv-encodes the resulting `ColumnsData` as section 1
(`encode.rs:144-147`, `:211`).

So a snapshot with K string columns carries K full copies of the global string table. That is the
reported 37 MB for under 4 MB of properties, and the same arithmetic is already written down in
this repository's own docs: *"37 MB for an 8 MB WAL on a 435-file repository"*
(`docs/site/durability.md`, the **Disk** paragraph).

Readers: the zero-copy seam at `crates/core-storage/src/v8/seam.rs:587-606` and the materialising
`archived_to_columnstore` at `encode.rs:832-846` both index `strings[sid]` inside the column.

### 5.2 New behaviour

One shared section, referenced by every string column.

```rust
// crates/core-storage/src/v8/mod.rs
/// Shared string table for every `ColumnData::Str` in the columns section.
pub const SECTION_STRINGS: u8 = 12;
pub const V8_MAGIC_SECTION_COUNT: usize = 13;   // was 12

// crates/core-storage/src/v8/layout.rs
#[derive(Archive, Serialize, Deserialize, Clone, Debug)]
pub struct StringTableData { pub strings: Vec<String> }
pub type ArchivedStringTable = ArchivedStringTableData;

// crates/core-storage/src/v8/mod.rs — impl MappedBase
/// `None` when the snapshot predates the shared section (every column carries its own).
pub fn string_table(&self) -> Option<Result<&ArchivedStringTable>>;
```

`encode_v8` writes `StringTableData` as section 12 and leaves `strings` **empty** in every
`ColumnData::Str`. Readers resolve in one place:

```rust
// crates/core-storage/src/v8/seam.rs
pub struct ColumnsView<'a> {
    pub overlay: &'a ColumnStore,
    pub base: Option<&'a ArchivedColumns>,
    pub mixed: Option<&'a MixedCache>,
    /// Shared table; `None` for a pre-0.6.5 snapshot, where the column's own
    /// `strings` is authoritative.
    pub strings: Option<&'a ArchivedStringTable>,
}
```

Resolution rule, one line, used by both the seam (`seam.rs:587-606`) and
`archived_to_columnstore` (`encode.rs:832-846`):

> if the shared section is present, it is the table; otherwise the column's own `strings` is.

An old snapshot has no section 12, so `string_table()` is `None` and the per-column vectors answer
exactly as they do today. **No migration is needed and no old snapshot is rewritten.**

### 5.3 The version bump, and exactly why

A new *optional* section alone would be safe for a reader that knows about it and silently wrong for
one that does not: a 0.6.4 binary opening a 0.6.5 snapshot finds `strings` empty on every string
column and `sid >= strings.len()` on every lookup, which `seam.rs:600-601` turns into `None` — every
string property silently disappears. That is data loss on downgrade, so this release stops the
downgrade instead of risking it:

```rust
// crates/core-storage/src/snapshot.rs
pub const VERSION_9: u16 = 9;
pub const VERSION: u16 = VERSION_9;   // was VERSION_8
```

This is what the existing versioning is already built for and it costs seven lines:

- `decode` (`snapshot.rs:230-262`) gains a `VERSION_9 =>` arm beside `VERSION_8 =>`; both go through
  `MappedBase`, because V9 is the same container (`GDB1` magic, 4 KB header page, 16-byte directory
  entries, per-section CRC) with one more section and empty per-column `strings`. An unknown version
  already produces `GraphError::Corrupt { "snapshot: unsupported version 9" }`, so a 0.6.4 binary
  refuses cleanly rather than reading holes.
- The two `== VERSION_8` gates that decide whether to mmap a base (`db.rs:1857`, `db.rs:2637`) become
  `matches!(ver, VERSION_8 | VERSION_9)`.
- The auto-migrate path at `db.rs:1589` (`Some(ver) if ver < snapshot::VERSION`) already rewrites any
  older snapshot at the current version on open. V8 stores therefore upgrade in place the first time
  they are opened read-write; nothing else is needed.
- `SNAPSHOT_VERSION` (`crates/core-api/src/lib.rs:37`) follows `snapshot::VERSION` automatically.

**What the `format-compat` CI job means here.** `.github/workflows/ci.yml:56-64` runs
`cargo test -p mushroomdb --test snapshot --test migrate` and its comment states the contract:
*"every historical snapshot format (V5..V8) must open, migrate, and preserve data, forever."* The
fixtures are `crates/core-api/tests/fixtures/golden_v{5,6,7,8}.bin`, pinned by `golden_v5_pin`
(`snapshot.rs:1015`), `golden_v6_pin` (`:1051`), `golden_v7_pin` (`:1458`) and `golden_v8_pin`
(`:1494`), plus the migration matrix in `migrate.rs:16,50,98,143`. Compatible therefore means:
**those four fixtures keep opening unchanged, and their tests are not edited.** 0.6.5 adds
`golden_v9.bin` and a `golden_v9_pin` beside them, generated the documented way
(`cargo run -p mushroomdb --example gen_golden_fixture -- crates/core-api/tests/fixtures/golden_v9.bin`,
`snapshot.rs:1492`), and adds a V8→V9 row to `migrate.rs`. `V8_MAGIC_SECTION_COUNT` moves from 12 to
13, which the `debug_assert!` at `mod.rs:351-355` exists to catch if it is forgotten.

### 5.4 Implications

- **Format change, one-way for downgrade.** A store snapshotted by 0.6.5 cannot be opened by 0.6.4
  or earlier — it fails with `snapshot: unsupported version 9`, never with wrong data. Upgrading is
  automatic and in place. This is the one breaking item in the release and it leads the changelog.
- Section 12 joins the `is_large_section` list (`mod.rs:99-109`) so it is not CRC-hashed on every
  touch; `mushroomdb verify` covers it like any other section, and `verify_integrity`'s name table
  (`mod.rs:248-262`) gains `"strings"`.
- No WAL change, no rule change, no API change.

### 5.5 Test

Two, in `crates/core-api/tests/snapshot.rs`:

- `shared_string_table_is_written_once` (fast, in `cargo test --workspace`): a store with 200 nodes
  and eight string fields, every field drawn from the same vocabulary containing the marker
  `"mushroom-marker-42"`. After `snapshot()`, the raw bytes of `snapshot.bin` contain that marker
  **exactly once**; reopening returns every property unchanged on every node and every field. The
  same test, run against the committed `golden_v8.bin`, still reads its string props — the
  compatibility half.
- `snapshot_size_is_near_the_property_payload` (`#[ignore]`, run in the `format-compat` job with
  `cargo test --release -p mushroomdb --test snapshot -- snapshot_size --ignored --nocapture`):
  12,000 nodes × 8 string fields × 40-byte values ≈ 3.84 MB of property bytes drawn from a
  2,000-string vocabulary. Assert `snapshot.bin` is **under 2×** the property payload. The same store
  under 0.6.4's encoder is 8 copies of the table and lands near 9×, so the test fails loudly if the
  sharing regresses. The measured before/after byte counts printed by this test are the only numbers
  about snapshot size that may enter `CHANGELOG.md` or `docs/site/durability.md`.

## 6. Time travel composes with roles and masks

### 6.1 What is true today

`crates/server/src/http.rs:813-819`:

```rust
// Time-travel is currently supported only on the full-token, unmasked read
// path (temporal + RBAC-mask composition is a follow-on).
if as_of.is_some() && (matches!(identity, AuthIdentity::Role(_)) || mask_keys.is_some()) {
    return err_response(
        "as_of (time-travel) is not yet supported with role tokens or a client mask",
    );
}
```

The stated reason is that the mask is evaluated against the live graph. Reading the mask path shows
the reason no longer holds. `mask_for_role` (`crates/core-api/src/db.rs:6340-6374`) resolves against
**that handle's** state: the key leg through `self.ids`, the label leg through `self.labels` and
`self.syms`. And `open_at_with` already loads the roles sidecar into the temporal handle —
`crates/core-api/src/db.rs:2700-2701`, comment and all:

```rust
// Load roles sidecar (current roles, not point-in-time).
db.roles = Self::load_roles_from_fs(&db.fs)?;
```

So `GraphDb::open_at(dir, c).mask_for_role(role)` *already* produces the mask as it would have been
at commit `c`, and `query_masked` on that handle already works. What is missing is one method and
the removal of the refusal.

MCP `query` (`crates/server/src/mcp.rs:246-321`) has **no** as-of argument at all — verified by
searching the file for `as_of`/`asof`: no hits. So there is no MCP form to fix; there is one to add.

### 6.2 New behaviour

```rust
// crates/core-api/src/db.rs, beside query_at (db.rs:1664)

/// How an as-of read is restricted.
pub enum AsOfScope<'a> {
    /// A role name, resolved against the graph as it was at `commit`.
    Role(&'a str),
    /// An explicit key allow-list, resolved against the graph as it was at `commit`.
    Keys(&'a [String]),
}

/// Read-only Cypher at `commit`, restricted by `scope`.
///
/// The **graph** is as of `commit`. The **role definition** is as it is now:
/// `roles.json` is a sidecar, never a WAL record, so there is no past version of
/// it to read. The role's `keys` and `labels` are then resolved against the
/// commit-`commit` graph, so a node that did not exist then is not visible, and a
/// node whose label changed since is judged by the label it carried then.
pub fn query_at_scoped(
    &self,
    commit: u64,
    cypher: &str,
    params: &BTreeMap<String, Value>,
    scope: AsOfScope<'_>,
) -> Result<ResultSet>;
```

Implementation is `open_at` → build the mask on the temporal handle (`mask_for_role`, or
`NodeMask::from_keys`) → reject write Cypher exactly as `query_at` does (`db.rs:1672-1680`) →
`query_masked`. Never-widen is preserved by construction: a role token that also sends a client mask
intersects them on the temporal handle, the same `NodeMask::intersect` the live path uses
(`crates/core-api/src/mask.rs:100-105`).

**HTTP.** The refusal at `http.rs:815` is deleted. `POST /query` with `as_of` routes to
`query_at_scoped` for a role token, for a client mask, and for both. `stub_hidden` stays refused
with `as_of` — stub mode discloses existence and an as-of view is exactly where "did this key exist
then" is the question being asked; a role path is already hard-coded to `Omit`
(`crates/core-api/src/mask.rs:98-99`).

**MCP.** `query` gains an optional `as_of` integer, documented in its schema
(`crates/server/src/mcp.rs:1007`) as *"a 0-based WAL commit index; the graph as it was at that
commit. Composes with `role` and with `mask`. Writes are refused."* It routes to `query_at_scoped`
when `role` or `mask` is present and to `query_at` otherwise.

### 6.3 Implications

- Additive on both wires. Nothing that worked stops working; one error stops being returned.
- The semantics of "role definitions are current, graph is historical" are stated in
  `docs/site/timetravel.md` and `docs/site/masks.md` in one sentence each, because it is the one
  thing a reader can get wrong.
- An as-of scoped read opens a temporal view per call, which is what `query_at` already costs

## 7. Predicate masks (small form)

### 7.1 What is true today

`RoleDef` (`crates/core-api/src/roles.rs:77-88`) is `{ name, keys, labels, write }`. `mask_for_role`
(`db.rs:6340`) is a union of two legs: explicit keys resolved through `self.ids`, and a **live scan
over `self.labels`** for each named label (`db.rs:6362-6371`). `ReaderSnapshot` has the same
function against the frozen overlay (`crates/core-api/src/reader.rs:366-392`). That label leg is the
10 ms at 2,000 nodes: it is O(nodes × labels) and it runs on every scoped call, with no memo
anywhere.

`roles.json` is `{version, roles}` with version 1 (no write scopes) or 2 (some role has one), and an
unrecognised version poisons the roles state (`roles.rs:90-117`, `db.rs:6314-6328`).

### 7.2 New behaviour

One optional field on `RoleDef`, and nothing else in the shape changes:

```rust
// crates/core-api/src/roles.rs

/// One property test a role's visibility may carry, in addition to `labels`.
/// Equality and membership only — no ranges, no negation, no nesting.
#[derive(Serialize, Deserialize, Clone, PartialEq, Debug)]
pub struct PropPredicate {
    /// Property name on the node.
    pub field: String,
    /// Exactly one of `eq` / `in_` is set; both or neither is a schema error.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub eq: Option<Value>,
    #[serde(default, rename = "in", skip_serializing_if = "Option::is_none")]
    pub in_: Option<Vec<Value>>,
}

pub struct RoleDef {
    pub name: String,
    pub keys: Vec<String>,
    pub labels: Vec<String>,
    /// Narrows the `labels` leg only. A node is visible through that leg iff it
    /// carries one of `labels` AND satisfies this predicate. Absent = no narrowing.
    /// `keys` is never narrowed: an explicitly named key is always visible.
    #[serde(default)]
    pub visible_where: Option<PropPredicate>,
    pub write: Option<WriteScope>,
}
```

Schema JSON:

```json
{ "roles": [
  { "name": "reader",
    "labels": ["Document", "Note"],
    "visible_where": { "field": "status", "in": ["published", "archived"] } },
  { "name": "editor",
    "labels": ["Document"],
    "visible_where": { "field": "workspace", "eq": "core" } }
] }
```

**Semantics, stated once.** `visible = keys ∪ { n : label(n) ∈ labels ∧ pred(n) }`. A missing
property fails the predicate — absent is not a match, so a role narrowed by `status` never sees a
node that has no `status`. Comparison is `Value` equality, the same one Cypher `=` uses; list
properties are compared whole, not by membership. `in` with an empty list matches nothing.

**Persistence.** `roles.json` gains **version 3**, written only when some role carries
`visible_where`; versions 1 and 2 keep being written when they suffice, exactly as
`RolesFile::new_versioned` (`roles.rs:110-117`) already decides between 1 and 2. Load accepts 1, 2
and 3 (`db.rs:6324`); 4 and up still poison. An older binary meeting a version-3 file poisons its
roles state and denies every role, which is the never-widen direction and the only acceptable one.

**Validation** at `apply_schema`: exactly one of `eq` / `in` set; `field` non-empty; a
`visible_where` with no `labels` is rejected, because it would narrow nothing and read as a mistake.

**The memo.** A resolved mask is cached per role and invalidated by any write:

```rust
// crates/core-api/src/mask.rs
/// Role → resolved mask, valid for one commit sequence.
pub struct RoleMaskCache { /* Mutex<HashMap<String, (u64, Arc<NodeMask>)>> */ }
impl RoleMaskCache {
    pub fn get_or_build(
        &self, role: &str, version: u64,
        build: impl FnOnce() -> Result<NodeMask>,
    ) -> Result<Arc<NodeMask>>;
}
```

`version` is `GraphDb::commit_seq()` (`db.rs:8691`). `GraphDb` holds one behind interior mutability
so `mask_for_role(&self)` keeps its signature; `GraphDb::reader()` stamps the same value onto the
`ReaderSnapshot` and passes the cache `Arc` down, so the HTTP role path
(`http.rs:844`, via `ReaderSnapshot::mask_for_role`, `reader.rs:475`) and the MCP role path
(`mcp.rs:283`, via `GraphDb::mask_for_role`) share one memo. An entry is used only when its recorded
version equals the current one, so a mask is never stale across a write — the cache can only be
cold, never wrong. *(To confirm at implementation: that `GraphDb::reader()` can read `commit_seq()`
on the same borrow it clones the `Arc`s on; `SharedDb::reader()` is `self.read().reader()`,
`crates/core-api/src/shared.rs:592`, so it should.)*

The predicate leg needs property reads, which `mask_for_role_from` cannot do today — it takes only
`&FrozenOverlay` (`reader.rs:366`). It gains the `&Option<Arc<MappedBase>>` its caller already holds
and builds a `ColumnsView` through the existing `build_cv` helper (`reader.rs:100-110`).

### 7.3 Implications

- **Additive, opt-in.** A role with no `visible_where` behaves byte-identically, including the
  `roles.json` it writes.
- `roles.json` version 3 is forward-incompatible by design: an older binary denies rather than
  over-grants.
- The memo changes timing, never results. It is not a TTL cache and there is no staleness window.
- `docs/site/masks.md` gains the predicate form; the MCP `query` tool description
  (`mcp.rs:1007`) gains one clause saying a role may be narrowed by a property.

### 7.4 Test

`crates/core-api/tests/rbac.rs`: `visible_where_narrows_the_label_leg` — three `Document` nodes with
`status` `published` / `draft` / absent; a role with `labels: ["Document"]` and
`visible_where: {field: "status", in: ["published"]}` sees exactly one; the same role with an
explicit `keys: ["draft-doc"]` also sees that one, proving `keys` is never narrowed;
`eq` behaves the same for a single value; an empty `in` sees nothing.
`roles_json_version_3_round_trips` — apply, reopen, resolve identically; a version-4 file poisons.
`mask_memo_is_invalidated_by_a_write` — resolve, write a node that the predicate admits, resolve
again, assert the new node is visible (the memo did not serve a stale mask).
`crates/server/tests/http.rs` and `mcp.rs`: a role token and `query role:` both honour

## 8. Durability: restore on boot, and the runbook

### 8.1 What is true today

`mushroomdb serve <db-dir>` has `--snapshot-every <secs>` (`crates/cli/src/lib.rs:501`, parsed at
`lib.rs:1020-1028`, driven at `crates/cli/src/main.rs:554-581`) and snapshots once more on graceful
shutdown. `mushroomdb backup <db> <dest>` exists (`crates/cli/src/lib.rs:1564`) and copies
`snapshot.bin`, `snapshot.bin.bak`, `wal.bin`, `wal.floor`, `wal.genesis`, `roles.json` and every
`wal.<N>.archive`, then verifies by CRC-checking and opening the copy
(`crates/core-api/src/db.rs:7233-7293`). There is **no** restore: `grep -rn restore crates/cli/src`
returns two unrelated comments. Restoring today means knowing to copy a directory back by hand.

`docs/site/durability.md` explains recovery and archives; `docs/site/deployment.md` is 105 lines
about terminating TLS at a reverse proxy. Neither tells an operator what to mount or what a restart
costs.

### 8.2 New behaviour

**`serve --restore-from <dir>`.** Before opening, if `<db-dir>` holds no store (no `snapshot.bin`
and no `wal.bin`), seed it from `<dir>`:

- If `<dir>` itself contains a `snapshot.bin`, that is the backup.
- Otherwise `<dir>` is treated as a directory **of** backups: its immediate subdirectories that
  contain a `snapshot.bin` are ranked by `snapshot.bin` mtime and the newest is chosen. A
  subdirectory literally named `latest` wins outright if it holds a `snapshot.bin`, so a symlink or
  a rolling copy can name itself.
- The chosen backup's files are copied into `<db-dir>`, then the store is opened normally — which
  runs the same CRC and replay checks any open runs. A copy that does not open is a hard failure
  with the path named; `serve` exits non-zero rather than starting empty.
- If `<db-dir>` already holds a store, `--restore-from` **does nothing and says so** on stderr. It
  is boot-time seeding for a fresh volume, not a rollback command, and it must be safe to leave in a
  container command line forever.

```rust
// crates/cli/src/lib.rs
pub enum RestoreOutcome { AlreadyPresent, Restored { from: PathBuf, files: Vec<String>, bytes: u64 }, Empty }

/// Seed `db_dir` from the newest backup under `from`, if `db_dir` has no store.
pub fn restore_if_empty(db_dir: &Path, from: &Path) -> Result<RestoreOutcome, CliError>;
```

`Command::Serve` gains `restore_from: Option<PathBuf>`; `main.rs` calls `restore_if_empty` before
`SharedDb::open` and prints one line per outcome.

**`docs/site/service.md` — "Running it as a service".** A new page covering, in this order:

1. **The volume.** The store is a directory; mount it. Which files live there and that all of them
   matter (`snapshot.bin`, `wal.bin`, `wal.floor`, `wal.genesis`, `roles.json`, `wal.<N>.archive`,
   `LOCK`). One writer per store directory, which is what `LOCK` enforces across processes.
2. **The snapshot interval.** `--snapshot-every`; what it bounds (replay after a hard crash, per
   `docs/site/durability.md`); that graceful shutdown takes one too; that a tick is skipped, never
   queued, when another process holds the write lock (`crates/cli/src/lib.rs:99-111`).
3. **Backup.** `mushroomdb backup <db> <dest>` and its verification; the warning already in the
   usage text that it is unsafe against a live `serve`, and that `POST /backup` is the live form.
4. **Restore.** `serve --restore-from`, and the manual equivalent (copy the directory back).
5. **What a restart without a volume costs.** Everything: nodes, edges, derived edges, rules, the
   WAL, the archives and all history. The graph is in RAM and on that directory, nowhere else.
6. **Commit numbers are per store lifetime.** `was_linked`, `edges_at`, `asof` and the `commit`
   field in every history event are indices into *this store's* WAL, counted from its genesis. A
   store restored from a backup keeps its numbering; a store recreated from scratch starts again at
   0, and a commit number recorded by the old one means something different in the new one. If a
   commit index must survive a rebuild, record a timestamp beside it.
7. **A worked container command line** with volume, `--addr`, `--token`, `--snapshot-every` and
   `--restore-from`.

### 8.3 Implications

- Additive CLI flag; no existing invocation changes.
- No format change, no API change.
- `docs/site/index.md` gains the page in its list. It is **not** added to `SITE_DOCS` in
  `scripts/gen-llms-full.sh`, matching `deployment.md`, `durability.md` and `masks.md`, which are
  also linked but not concatenated.

### 8.4 Test

## 9. Tests for the v0.5.x data-loss bug class

### 9.1 What the bug was

From `CHANGELOG.md` under **v0.6.0 → Fixed in this release (data loss in shipped 0.5.x)**:

> **Via-hop rules could retract all their edges after a snapshot.** The rule engine read topology
> from the write overlay only, so a via rule evaluated on a snapshot-opened store saw no via edges
> and retracted the ones already derived — `KNOWS` on this repository's own store went from 20 edges
> to 1 after a snapshot followed by an incremental `ingest-git`.

Caught by dogfooding, not by a test. Today the coverage is real but uneven: `via_rebuild.rs:304`
(`via_hop_overlap_scores_are_the_same_after_replay_and_after_snapshot`), `rules.rs:1086`
(`via_hop_survives_snapshot_and_wal_replay`) and `chaining.rs:136`
(`chained_edges_survive_wal_replay_and_snapshot`) cover the two shapes that broke. Nothing covers
the other predicate kinds systematically, and nothing covers **retraction after reopen** — which is
the half that actually lost data: not "do the edges come back", but "does a write after the reopen
retract the right ones and only those".

### 9.2 New behaviour

No behaviour change. One test file, `crates/core-api/tests/snapshot_rules.rs`, with a table-driven
round trip per rule kind. The kinds are the `Predicate` variants at
`crates/core-rules/src/def.rs:85-114` — `KeyMatch`, `FieldEqual`, `Overlap`, `NumericWithin`,
`GeoRadius`, `VectorSimilar`, `All`, `Any` — plus the two structural modifiers that are not
predicates: `via_label`/`via_edge` (via-hop) and a two-rule chain where one rule's edge type is
another's `via_edge`.

Each case runs the same five steps:

1. Seed nodes so the rule derives a known edge set `E₀`; assert it.
2. `snapshot()`, drop the handle, reopen.
3. Assert the derived set is still exactly `E₀` — **the 0.5.x bug, per kind**.
4. Mutate one node so the predicate stops holding for a strict subset `R ⊂ E₀`.
5. Assert the set is exactly `E₀ \ R` — nothing extra retracted, nothing stale left. This is the
   step the old coverage did not have.

`explain_association` is asserted to still name the rule for a surviving edge after the reopen, so
provenance is covered alongside topology.

### 9.3 Implications

None. Tests only. `VectorSimilar` uses a small fixed-dimension vector set so it stays inside the
debug-build budget; if any case exceeds a few seconds it is split out with `#[ignore]` and added to
the `format-compat` job line (**to confirm at implementation** — measure, then decide).

## 10. Non-goals

- **Removing the code door.** Deprecated in 0.6.4, removed in 0.7. Nothing here touches it.
- **Incremental HNSW, and an index-backed `VectorSimilar`.** The 23 s / 252 s / did-not-finish
  numbers in §2 are real and they are 0.6.6's. Vector-rule creation stays what it is in 0.6.5.
- **Namespaces.** A second axis of visibility beside roles and masks. 0.6.6.
- **Larger-than-RAM.** The graph is in memory; that is the design, not a defect to be fixed in a
  patch release.
- **Ranges, negation or nesting in predicate masks.** `eq` and `in` only. A mask that can express
  arbitrary predicates is a query language with a security boundary attached, and it needs its own
  design.
- **A durable history log independent of the WAL.** Keep-all retention (§4) makes the WAL archives
  the retention story; making history a first-class persisted structure is not this release.
- **Making `was_linked` commit numbers portable across stores.** §8 documents that they are not.
- **Rewriting the sidecar's own code**, and the CTL wrapper.

## 12. Decisions taken on the owner's behalf (revisit if wrong)

1. **The snapshot format goes to V9.** Keeping V8 while writing empty per-column `strings` would let
   a 0.6.4 binary read a 0.6.5 store and silently lose every string property (§5.3). A version bump
   is seven lines, the existing auto-migrate upgrades in place, and a downgrade fails with a clear
   message instead of with holes. This is the release's one breaking change.
2. **The sidecar's report is wrong about `was_linked`, and the spec says so.** `was_linked` and
   `edges_at` both check the floor today (`db.rs:9445`, `db.rs:9606`). The real defect is that the
   error never names the floor and the two commit-less reads carry no horizon. Fixing what is
   actually broken is cheaper and more honest than fixing what was reported.
3. **`node_history` changes return type rather than gaining a sibling.** `edge_history` already
   returns `HistoryResult`; two reads of the same kind returning two different shapes is the reason
   the horizon was easy to miss. Pre-1.0, three call sites, named in the changelog.
4. **`AUTO_SNAPSHOT_RETENTION` becomes `Option<u32> = None` rather than being deleted.** The constant
   is the documented name for the policy and `ingest_git.rs` links to it; keeping it, with `None` as
   its value, leaves one place to change if a bound is ever wanted back.
5. **`Stats` gets `history_floor` and not `total_commits`.** The floor is a struct field and free;
   the total needs a WAL scan, and `stats()` is `&self` and infallible. `doctor` prints both because
   `doctor` can afford it.
6. **The role-mask memo is keyed by commit sequence, not by a TTL.** The owner asked for a per-query
   cache; a commit-keyed memo is strictly better — it serves every read between two writes, and it
   cannot be stale, whereas a TTL can hand a scoped reader a mask that no longer matches the graph.
7. **`visible_where` narrows the `labels` leg only, never `keys`.** An explicitly named key is an
   administrative grant; silently withdrawing it when a property changes would be a surprising way
   to lose access.
8. **A missing property fails the predicate.** Absent is not a match. The alternative — treating
   absence as visible — makes a new, un-tagged node visible to a narrowed role the moment it is
   written, which is the wrong default for a visibility rule.
9. **`--restore-from` is boot-time seeding, not a restore command.** It is a no-op when the store is
   already there, so it can stay in a container command line forever without ever overwriting live
   data.
10. **`docs/site/service.md` is not added to `scripts/gen-llms-full.sh`.** `deployment.md`,
    `durability.md` and `masks.md` are linked from the index and excluded from the concatenation;
    the operator page follows them.
11. **`docs/site/timetravel.md:45` loses the phrase naming another vendor's product.** The page is
    being edited for the horizon anyway, and nothing committed should name or compare against
    another database, graph or vector product.
12. **Version 0.6.5, not 0.7.** One format bump, two small Rust-API breaks, no tool removed, no
    listing changed.

## 13. Sequencing

Horizon errors and the `horizon` field (§3) first — it is self-contained and every other item's
tests read better once an out-of-range answer explains itself. Keep-all retention (§4) next, because
it changes what the horizon tests in §3 have to construct on purpose. The snapshot interner (§5) and
the per-rule round-trip tests (§9) follow in that order: the round-trip tests exercise the new
encoder and are the safety net under the format change. Then time travel × masks (§6), then
predicate masks (§7) — §7's memo sits on the same `mask_for_role` path §6 makes temporal, so doing
§6 first means the memo is written once for both. `serve --restore-from` and the runbook page (§8)
last before the release commit, because the page describes the retention default and the restore
flag that the earlier items settle.
