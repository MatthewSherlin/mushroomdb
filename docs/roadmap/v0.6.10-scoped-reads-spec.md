## 1. Goal

When it ships:

1. **A scope is a property of the handle, not of each call.**
   `db.scoped(role=…, namespace=…, keys=[…])` returns a child handle whose
   every read is filtered by that scope. An app that enforces "this caller sees
   these nodes" can use the whole read surface without leaking, instead of the
   half of it that takes a `mask=`.
2. **Hidden behaves exactly as absent, on every scoped read.** A scoped
   `node_edges` on a node outside the scope raises `KeyNotFound`, it does not
   return that node's visible-endpoint edges. A scoped `degree` counts only
   visible neighbours. A scoped `pairwise_similar` never returns a hidden key
   and never lets one influence a score.
3. **The RBAC semantics live in the engine, once.** Today the correct role
   behaviour for `node_edges` is implemented in the HTTP layer
   (`crates/server/src/http.rs:1425`–`1458`) and nowhere else, which is exactly
   why the Python handle leaks. This patch moves that pattern down into
   `*_scoped` engine methods and has HTTP call them.
4. **`ingest_batch(on_conflict=…)`.** A mirror can be rebuilt onto a store that
   already has content without wiping the directory first, and without one
   duplicate key rejecting a 100k-row frame.
5. **Every failure is a stable class.** `MushroomError(RuntimeError)` base, one
   subclass per `GraphError` variant, a stable `.code`, and the variant's own
   fields as attributes. Existing `except RuntimeError` keeps working.
6. **The supported multi-process topology is written down**, with the failure
   mode of each alternative named, instead of left to be inferred from the
   presence of `LOCK`.
7. **Restore is a tested round trip.** `restore + refresh` answering
   identically to the source store is pinned by a committed test, and is
   reachable from the Python wheel.

No snapshot-format change. No MHNS change. No recall floor moves. No benchmark
**gate**: the one benchmark this patch adds (§5.12) decides whether a single
optional task ships, and nothing in the release is a performance claim unless a
committed benchmark produced the number.

## 2. What is true today (read, not assumed)

Verified against the tree at `v0.6.8` plus the committed part of 0.6.9.

**Scope resolution already exists and already composes.**
- `GraphDb::mask_for_role(role)` (`crates/core-api/src/db.rs:7239`) builds a
  `NodeMask` through `role_masks.get_or_build(role, self.commit_seq, …)` — a
  cache **keyed on commit seq**, so a resolved mask cannot go stale: the next
  commit rebuilds it. A handle-level scope can therefore hold an *unresolved*
  descriptor and re-resolve per read at no cost.
- `GraphDb::mask_for_namespace(ns)` exists, and `NodeMask::intersect` is the
  documented never-widen composition. Python `query` already does exactly this
  (`bindings/python/src/lib.rs:236`–`266`).
- `AsOfScope` (`db.rs:7250`) already enumerates the four descriptor shapes this
  patch needs: `Role`, `Keys`, `RoleAndKeys`, `Namespace`.
- A role may carry a `visible_where` property predicate
  (`crates/core-api/src/roles.rs:249`), so a scope can be a predicate rather
  than an id list. Roles come from `roles.json` in the store directory, loaded
  at open; a corrupt file poisons roles and `mask_for_role` refuses rather than
  widening.

**Masked engine entry points exist for five surfaces and not for four.**

| Surface | Masked engine method | Python exposes scope? |
|---|---|---|
| `query` | `query_masked` (`db.rs:7912`) | yes — `role=` / `namespace=` |
| `neighborhood` | `neighborhood_masked` (`db.rs:7957`) | no |
| `node_info` | `node_info_masked` (`db.rs:8038`) | no |
| `node_edges` | `node_edges_masked` (`db.rs:8063`) | no |
| `find_similar` | `find_similar_vector_masked` (`db.rs:8692`) | `mask=` only |
| `pairwise_similar` | **none** (`db.rs:8966`) | no |
| `search_hybrid` | **none** (`db.rs:6555`) | no |
| `explain` | **none** (`db.rs:9922`) | no |
| `degree` / `degrees` | **none** (`db.rs:10047`, `10069`) | no |

**`node_edges_masked` does not check the subject.** It resolves the key,
raises `KeyNotFound` only when the key is unknown, and then filters the *other*
endpoint. A hidden subject's edge list comes back. This is deliberate and
documented — its doc comment says "**SECURITY**: only call from client-mask
(full-token) paths", where the caller already knows those keys exist — and it
is honoured: the only caller is the full-token branch at `http.rs:1483`. The
role-token branch above it (`http.rs:1425`) implements the stricter contract by
hand: resolve the key, `key_not_found` unless the role mask contains it, then
filter every edge whose other endpoint is hidden. **That hand-written contract
is the one §5 moves into the engine.** Reusing `node_edges_masked` for a
role-scoped handle without the subject check would be a disclosure bug.

**`find_similar` scoping is not exact by default.** `skip_hnsw = exact ||
where_.is_some()` (`db.rs:8749`). With `mask=` alone the call rides the 0.6.7
widening beam and is approximate unless the beam reaches `EF_MAX` and falls
back to the scan. `where=` and `exact=True` are the exact paths; `where=` uses
the property index only when a `label` is also given and
`enable_index(label, field)` is on (`vector_candidates`, `db.rs:8866`).

**`ingest_batch` is all-or-nothing with no conflict policy.**
`bindings/python/src/lib.rs:935` builds a `BatchBuilder` of `InsertNode` /
`InsertEdge` ops and commits. Batch commit is validate-then-apply, so one
pre-existing key rejects the whole frame with `DuplicateKey`. `upsert_node`
exists but is per-node.

**Errors are flattened at the binding.** `graph_err`
(`bindings/python/src/lib.rs:1248`) maps `QueryError` to `RuntimeError` with
its detail string, `Busy` to `MushroomBusy` (the one typed class,
`lib.rs:1617`), and **every other variant** to `RuntimeError(e.to_string())`.
`GraphError` (`crates/core-storage/src/types.rs:46`) has eighteen variants and
already carries the structure callers are parsing back out of English:
`CommitOutOfRange { commit, total, floor }`, `CasConflict { key, expected,
actual }`, `RoleWriteDenied { reason }`, `ViewPropReadOnly { view_name }`,
`NamespaceImmutable`, `CrossNamespace`, and so on. There is no
`DimensionMismatch` variant — a wrong-dimension vector is skipped as a
candidate, never raised.

**Multi-process pieces exist; the topology is not written down.** An advisory
cross-process write lock (`LOCK`, since 0.6.0) is taken by every WAL-appending
path; `GraphDb::refresh()` applies peers' commits and is safe on a read-only
handle; `Busy` means nothing was written and a retry is safe. What no page
states is which deployment shapes are supported.

**Restore exists, in the CLI only.** `restore_if_empty`
(`crates/cli/src/lib.rs:1935`) with tests for the empty-dir and backup-dir
cases. `snapshot()` is already crash-safe — temp file, full fsync
(`F_FULLFSYNC` on macOS), atomic rename (`db.rs:1684`). There is no Python
`restore`, and no test asserts that a restored store answers queries
identically to its source.

**`roles()` is Rust-only.** `GraphDb::roles()` (`db.rs:7338`) returns the
defined roles; the Python handle has no equivalent, so a sidecar cannot
validate a role name at startup or discover what scopes exist.

## 3. Non-goals

- **No write scoping.** A scoped handle refuses mutations (§7 D2). Routing
  scoped writes through the `RoleWriteDenied` decision table is a larger
  surface and is not this patch.
- **No `MaskMode::Stub` on scoped handles.** Omit only. Stub discloses
  existence and is a full-token concept.
- **No new HNSW work**, no `HnswParams` change, no recall-floor change, and no
  attempt on the 0.6.6 growth gates. They stay red and stay named in
  `benchmarks/results/hnsw-scale-0.6.6.md`.
- **No `max_distance` alias** on `find_similar` / `pairwise_similar`. One
  spelling for one floor (§7 D5).
- **No server mode** and no distributed coordination. §5.9 documents what the
  lock already guarantees; it does not build anything new.
- **No query-defined scope** — a scope whose membership is a traversal rather
  than a key list or a field predicate. This is the thing that would let an
  embedder stop computing its readable set in another database, and it is
  deliberately deferred; see §7 D7 for the condition that would promote it.
- **No MCP or HTTP tool added or reordered.** `ASSOCIATION_TOOLS` stays at
  whatever 0.6.9 Task 5 leaves it (sixteen). HTTP gains no route; the two
  role-path handlers are refactored onto the new engine methods with
  byte-identical responses.

## 5. Contracts

### 5.1 `Scope` — one descriptor, one resolver

A new type in `crates/core-api/src/mask.rs`:

```rust
pub struct Scope {
    role: Option<String>,
    namespace: Option<String>,
    keys: Option<Vec<String>>,
}
```

Resolution is `Scope::resolve(&self, db) -> Result<NodeMask>`: resolve each
present leg (`mask_for_role`, `mask_for_namespace`, `NodeMask::from_keys`) and
**intersect** them. Absent legs contribute nothing. A `Scope` with no legs is
invalid and is refused at construction, not silently treated as unscoped — an
empty scope must never be the accident that widens a caller to everything.

Mode is hard-coded `MaskMode::Omit`. `AsOfScope` keeps its current shape;
`Scope` is the live-read analogue, and the two resolve through the same
`mask_for_role`, so a role means one thing on both.

Resolution happens **per read**, not once at construction. `role_masks` is
cached on `commit_seq`, so a repeated read costs a hash lookup while a read
after a write rebuilds — the scope can never serve a stale allow-list. A
`keys=` leg is re-resolved on the same terms: a key that did not exist when the
scope was built and exists now is visible, and a key that was deleted is not.

**The `keys=` leg must be cached on `commit_seq` too, on the `Scope` itself.**
`NodeMask::from_keys` is one hash lookup per key, so a naive re-resolve of a
50,000-key allow-list costs 50,000 lookups on *every* read — which would make a
handle scope slower than the per-call `mask=` it replaces, for exactly the
caller who needs it most. Cache the resolved `NodeMask` beside the key list,
keyed on the `commit_seq` it was resolved at; a read at the same seq reuses it,
a read after a write rebuilds. The freshness guarantee is unchanged and the
steady-state cost is one integer comparison.

### 5.2 `db.scoped(...)` — the Python child handle

```python
db = GraphDb.open(path)                      # unscoped, writes
s  = db.scoped(role="reader-a")              # no reopen; shares store + mutex
t  = db.scoped(namespace="tenant-a", keys=visible_ids)
```

- Returns a new `GraphDb`-shaped Python object sharing the same underlying
  store handle and mutex. It is not a second open; it does not take the write
  lock; it costs one small allocation.
- At least one of `role` / `namespace` / `keys` is required; none raises
  `ValueError`.
- An unknown role raises at `scoped()` call time, not on first read — a typo in
  a role name must not silently produce a handle that reads unscoped or reads
  nothing.
- `scoped()` on a scoped handle intersects further and never widens.
- **Every mutation raises `MushroomReadOnly`** (§7 D2), including `snapshot()`,
  `create_rule`, `enable_index`, and `ingest_batch`.
- `refresh()` is permitted (it writes nothing) and applies to the parent store.
- `close()` on the parent closes the child. A closed handle raises as it does
  today.

### 5.3 The scoped read surface

Every read method on a scoped handle applies the scope. The contract is
uniform, and is the one `http.rs:1425` already implements by hand:

> **The subject is checked first. A key outside the scope is indistinguishable
> from a key that does not exist. Then every other node the answer would
> mention — neighbour, endpoint, candidate, evidence — is filtered to the
> scope.**

| Method | Scoped behaviour |
|---|---|
| `query` | as today (`query_masked`); a write statement raises `MushroomReadOnly` |
| `query_at` | as today, `AsOfScope` from the handle's `Scope` |
| `node_info` | hidden or unknown subject → `None` |
| `node_edges` | hidden or unknown subject → `KeyNotFound`; edges to hidden endpoints dropped |
| `neighborhood` | hidden or unknown subject → `KeyNotFound`; expansion never crosses a hidden node |
| `neighbors` | same as `neighborhood` |
| `explain` | either endpoint hidden → `KeyNotFound`; an explanation whose evidence path crosses a hidden node is omitted entirely, not redacted |
| `degree` | counts only visible neighbours; hidden subject → `KeyNotFound` |
| `degrees` | hidden keys omitted from input and output; label/`where` legs intersect the scope |
| `find_similar` | candidate set intersects the scope; per-call `mask=` intersects further (§5.5) |
| `pairwise_similar` | hidden keys dropped from the input set **before** the matmul, so a hidden vector cannot influence a score or appear as a neighbour |
| `search_hybrid` | both legs filtered **before** RRF fusion, so ranks are the ranks of the visible corpus and `k` is honoured |
| `what_if_set_prop` | hidden or unknown subject → `KeyNotFound`; hidden endpoints dropped from `lost` / `gained` |
| `node_history` | hidden subject → empty `history`, as an unknown key answers; edge events naming a hidden partner dropped |
| `edge_history` | either endpoint hidden → empty `events`, as an unknown key answers |
| `edges_at` | hidden subject → `[]`, as an unknown key answers; edges to hidden endpoints dropped |
| `was_linked` | hidden endpoint → `False`, as an unknown key answers |
| `get_edge_prop` | either endpoint hidden → `None`, as an unresolvable key answers |
| `stats` | store-wide counts as today; the namespace roster is narrowed to the scope |
| `has_vector_rule`, `is_index_enabled` | unscoped — schema facts, not node data |

#### The subject check is "answers as absent", not "raises"

The contract's first sentence is the binding one: *a key outside the scope is
indistinguishable from a key that does not exist*. Which answer that is, is a
per-method fact, and the rule follows from it:

> **A surface that does not raise for an absent key must not raise for a hidden
> one.**

`node_history`, `edge_history`, `edges_at`, `was_linked` and `get_edge_prop`
WAL-scan or resolve by key and answer empty / `False` / `None` for a key the
store has never heard of. Raising `KeyNotFound` for a hidden subject there would
say *this key exists but you may not see it* — the existence oracle the sentence
above forbids, reintroduced by the very check meant to prevent it. So they
answer exactly as absent does, and the six rows are spelled out separately
because they do not all answer the same way.

`node_info` (`None`), `node_edges`, `neighbors`, `explain`, `degree` and
`what_if_set_prop` (`KeyNotFound`) each match what *they* already answer for an
unknown key, by the same rule.

*Recorded as defect #10: this table originally gave all six the `KeyNotFound`
answer. The implementation deviated, correctly, and the deviation went
unrecorded. The spec is what the release gate reads, so a reader reconciling
the two would have "fixed" the code back into a leak.
`bindings/python/tests/test_scope_leaks.py` asserts the per-method answers.*

`degree` counting only visible neighbours is a correctness requirement, not a
nicety: an unfiltered count discloses the existence of hidden neighbours to a
caller who cannot see them, which is the same leak the edge-list filter exists
to prevent.

### 5.4 New masked engine entry points

Four surfaces have no masked variant and need one. Each is `_scoped` taking
`&NodeMask`, each is additive, and each is the only place its filtering logic
lives:

- `pairwise_similar_scoped(keys, field, k, min, mask)` — intersect `keys` with
  the mask first, then the existing Gram / gemv path unchanged. The caps
  (Gram ≤ 4096, gemv ≤ 8192 unique keys, then the named `QueryError`) apply to
  the **post-filter** count, so a scope can bring an over-cap call under it.
- `search_hybrid_scoped(…, mask)` — filter each leg's candidates before fusion.
  The RRF constant stays 60; over-fetch stays `4*k` per leg measured in visible
  hits, so a scoped call is not short.
- `explain_scoped(a, b, mask)` — subject check on both endpoints, then drop any
  `Explanation` whose evidence mentions a hidden node.
- `degree_scoped` / `degrees_scoped(…, mask)` — visible-neighbour counts. Must
  compose with whatever 0.6.9 Task 6 leaves `multiplicity` meaning: a scoped
  multiplicity count sums insert-counts of **visible** pairs only.

`node_edges_scoped` and `neighborhood_scoped` are added as thin wrappers that
do the subject check and then delegate to the existing `_masked` variants, and
`http.rs:1425`'s hand-written role branch is rewritten to call
`node_edges_scoped`. The full-token client-mask branch keeps calling
`node_edges_masked` — its looser subject contract is correct for that path and
must not change.

### 5.5 Scoped `find_similar` and the exactness rule

A scope contributes a mask. It does **not** change which kernel runs:

- scope alone, or scope + `mask=` → widening beam, approximate, exactly as
  0.6.7 defined it;
- scope + `exact=True`, or scope + `where=` → GEMM brute over the scoped
  candidate set, exact.

This is the one place the integration team's note was measuring something other
than what it thought. The remedy here is documentation, not a behaviour change:
`docs/site/api.md`, `docs/site/mcp.md` and the Python README must each state,
in the `find_similar` entry, that **`mask=` alone is the approximate path** and
name the two exact ones. A behaviour change — making a scope imply `exact` —
is rejected: it would silently turn a fast ANN call into an O(n) GEMM for every
existing masked caller.

### 5.6 `ingest_batch(on_conflict=…)`

```python
db.ingest_batch(nodes, edges, on_conflict="error" | "skip" | "replace")
```

- `"error"` is the default and is today's behaviour exactly: one duplicate key
  rejects the whole frame with `DuplicateKey`. Existing callers see no change.
- `"skip"` leaves a pre-existing node untouched — properties, label and edges
  as they were — and counts it.
- `"replace"` keeps the key and makes the node's properties **exactly** the
  supplied props: supplied fields are set, fields absent from the supplied
  props are removed (§7 D4). A supplied label that differs from the stored
  label is a **row error**, not a silent relabel — relabelling is `rename_node`
  / an explicit write, not a side effect of a mirror rebuild.
- Edges take the same argument and the same three policies. A duplicate edge
  under `"skip"` is a no-op; adjacency is a set, so `"replace"` on an edge is
  also a no-op on topology and only replaces edge properties.
- The frame stays atomic. `skip` and `replace` are decided during the existing
  validate pass, so a batch still applies wholly or not at all; only the
  definition of "valid" changes.
- The returned report gains `skipped` and `replaced` counts beside `inserted`
  and `edges_inserted`. `row_errors` carries label-mismatch rows.
- Reserved-property rules (`ns` immutability, reserved names) are unchanged and
  still refuse: `replace` cannot move a node between namespaces. That refusal
  is a row error under `skip`/`replace`, matching `upsert_entity`'s
  all-or-nothing contract from 0.6.7.

### 5.7 Error classes

A base plus one subclass per variant (§7 D3):

```python
class MushroomError(RuntimeError): ...        # base; keeps `except RuntimeError` working
class KeyNotFound(MushroomError): ...         # .key
class DuplicateKey(MushroomError): ...        # .key
class CommitOutOfRange(MushroomError): ...    # .commit .total .floor
class CasConflict(MushroomError): ...         # .key .expected .actual
class RoleWriteDenied(MushroomError): ...     # .reason
class ViewPropReadOnly(MushroomError): ...    # .view_name
class MushroomBusy(MushroomError): ...        # existing class, reparented
...                                           # one per GraphError variant
```

- Every class carries `.code`, a stable snake_case string equal to the variant
  name lowercased (`"key_not_found"`, `"commit_out_of_range"`). **`.code` is
  the compatibility surface**: the class list may grow, the codes may not
  change spelling.
- Each class carries the variant's own fields as attributes, typed as the Rust
  fields are. `str(e)` keeps today's message verbatim, so existing logs and
  substring checks do not change.
- `MushroomBusy` is reparented from `RuntimeError` to `MushroomError`. It
  remains a `RuntimeError` subclass, so no existing `except` stops matching.
- `QueryError` keeps its detail string as the message and gains
  `.code == "query_error"`. It is not decomposed further in this patch.
- There is no `DimensionMismatch`. If the integration team wants a raise rather
  than a skip on a wrong-dimension vector, that is a separate behaviour change
  with its own decision, and it is not in this spec.
- The `.pyi` stub declares every class and attribute. A test asserts that every
  `GraphError` variant maps to a distinct class — add a variant in Rust without
  adding a class and the test fails.

### 5.8 `db.roles()`

Read-only passthrough of `GraphDb::roles()` returning a list of dicts
(`name`, `labels`, `keys`, `namespaces`, `visible_where`). Empty list when no
roles are defined; raises when `roles.json` was corrupt at open, matching
`mask_for_role`. This is what lets a sidecar validate a role name at boot
instead of discovering it on the first request.

### 5.9 Multi-process: the documented topology

A new page, `docs/site/multiprocess.md`, added to `SITE_DOCS` in
`scripts/gen-llms-full.sh`. It documents what the code already does, and names
the failure mode of each shape:

- **Supported: one writer, N readers.** The writer holds the advisory lock;
  readers open read-only and call `refresh()` to pick up commits. A reader that
  never refreshes sees a consistent but frozen store — that is the documented
  cost, not a bug.
- **Supported: N writers, serialised by the lock.** Each write takes `LOCK`
  and fails loud with `Busy` after `WRITE_LOCK_WAIT` (2 s). Nothing was written
  and no in-memory state changed, so a retry is always safe. Suitable for
  occasional writes; not for a write-heavy fan-out.
- **Not supported: a store directory on a network filesystem.** Advisory locks
  over NFS/EFS are the folklore the note is right to distrust. Say so.
- **Not supported: two processes writing without the lock** (a handle opened
  with the lock disabled). Named so nobody infers it is an option.
  **AMENDED, 2026-09-18 — see below. There is no such handle; this bullet as
  written asks for a shape the code cannot be put into.**
- A worked snippet for the disposable-sidecar shape: rebuild on boot, one
  writer per task, readers refreshing on an interval.

No code changes in this section. If writing it uncovers a gap between the
documented contract and the code, that gap becomes its own task with its own
failing test — it does not get papered over in prose.

**AMENDMENT, 2026-09-18 (defect #20).** Writing the page under the instruction
directly above found the gap, and the gap is in this section rather than in the
code. Nothing in the public surface disables the cross-process lock:

- `OpenOptions` has `read_only` and no lock field, and a `read_only` handle takes
  no lock *and* refuses every mutation — so it is not an unlocked writer.
- Python `GraphDb.open(path, read_only=False)` passes only `read_only`.
- `GraphDb::open_unlocked` is `pub(crate)`; its only callers are in
  `crates/core-api/src/shared.rs`, where `SharedDb` takes the lock **per write**
  instead of per handle. That is a change of granularity, not an opt-out — every
  `SharedDb` write still goes through `poll_cross_process_lock`.
- No CLI flag and no environment variable configures one.

Writing "not supported: X" where X is unreachable teaches a reader that X is
reachable, which is the opposite of what the bullet is for — and it leaves the
*actually* reachable failure undocumented. The fourth bullet is therefore
replaced by:

- **Not supported: bypassing the lock.** No API, flag or environment variable
  turns it off, so say that plainly instead of implying a configuration. The
  lock is **advisory**, so what is genuinely reachable is (a) a non-mushroomdb
  process editing the store directory, and (b) two paths to the same directory,
  where the lock is held per inode. Document (a) and (b) as the real shapes.

`docs/site/multiprocess.md` shipped against this amended bullet, not against the
original. A later reader must not "correct" the page back toward the pre-amendment

### 5.12 `NodeMask` representation — the one performance item

This patch puts `contains_id` inside the inner loop of nine more surfaces:
every vector candidate, every neighbour counted by `degree`, every hop of a
scoped expansion, every key of a scoped `pairwise_similar`. Today
`NodeMask.visible` is a `HashSet<u32>` (`crates/core-api/src/mask.rs:45`), so
each of those is a hash probe, and `intersect` allocates a fresh set element by
element. There are fifteen `contains_id` call sites in the tree now; §5.3 and
§5.4 roughly double that and move them somewhere hotter.

Dense node ids make a better representation available. `NodeMask` becomes:

```rust
enum Visible {
    Sparse(HashSet<u32>),   // few visible nodes in a large id space
    Dense(Box<[u64]>),      // bitset over the dense id space
}
```

- `contains_id` on `Dense` is a bounds check, a shift and an AND — no hashing,
  and the bitset is cache-resident at realistic sizes (50,000 ids = 6.25 KB,
  against roughly half a megabyte for the equivalent `HashSet<u32>`).
- `intersect` on two `Dense` masks is a word-wise AND with no per-element
  allocation. This is the operation §5.1 runs on every multi-leg scope.
- `from_keys` still pays one key→id lookup per key, which is irreducible, but
  writes into a bitset instead of growing and rehashing a set.

**Choose the representation by density at construction**, not always-dense: a
role that sees 10 nodes in a 10-million-node store would pay 1.25 MB as a
bitset against a few hundred bytes as a set, and `role_masks` caches masks, so
that cost would persist. The rule is a single documented threshold — dense when
`visible.len() * 64 >= id_space`, sparse otherwise — evaluated once, with the
variant fixed for the mask's life.

**This task is conditional on measurement.** The claim above is a design
argument, not a number, and this repo does not ship design arguments as
performance claims. The task adds a criterion benchmark over the existing
masked paths (`query_masked`, masked `find_similar`, `neighborhood_masked`) at
2k / 50k visible ids before touching the representation. If the win is inside
noise, **drop the task** and keep the `HashSet` — the correctness work in
§5.1–§5.4 does not depend on it. Whatever the outcome, no figure from it enters
the CHANGELOG unless a committed benchmark produces it.

Two smaller items ride along, both already implied elsewhere and both free:

- **`pairwise_similar_scoped` measures its caps post-filter** (§5.4). A scope
  that cuts a key set in half quarters the Gram. This is the single largest
  algorithmic win available to a scoped caller and it costs nothing but
  ordering the filter before the cap check.
- **Idempotent re-ingest must stay O(n).** `skip` / `replace` decisions are
  made during the existing validate pass with an O(1) id-map lookup per row.
  Pin it: ingest 100,000 nodes, then ingest the same 100,000 again with
  `on_conflict="skip"`, and assert the second pass is within a small constant
  factor of the first. A quadratic conflict check would satisfy every
  correctness test in §5.6 and be useless at the size that motivated it.

Explicitly **not** done here, having been checked:

- **`refresh()` needs no work.** The no-op path is two filesystem metadata
  calls and an integer comparison before it returns `Ok(0)`
  (`crates/core-api/src/db.rs:2428`–`2450`). A reader polling on an interval,
  which is the topology §5.9 documents, already costs almost nothing. State
  that in the page rather than optimising it.
- **Label-less `where=` index lookup.** `vector_candidates` uses the property
  index only when a label accompanies the predicate (`db.rs:8866`), because the
  index is keyed per `(label, field)`. Serving a label-less predicate from the
  index means unioning across every indexed label for that field. It is a real
  gap but a narrow one — a predicate without a label is rare, and correctness
  is unaffected — and it is not in this patch.

### 5.13 Insert-count multiplicity — deferred here from 0.6.9

0.6.9 planned this as its Task 6 and could not ship it. The reason is the whole
design constraint, so it is restated rather than summarised.

**What is true today.** A duplicate `insert_edge` is a total no-op:
`prepare_insert_edge` returns `false`, `insert_edge` returns `Ok(false)`, and
**no WAL record is written** (`crates/core-api/src/db.rs:5807`). Adjacency is a
set. Edge properties *are* snapshotted (section 5, `EDGE_PROPS`), but there is
**no edge-property WAL record** — zero `EdgeProp` variants in `WalRecord`. Rules
never needed one because they re-derive their edge props on replay; an
insert-driven count has no such derivation.

**Why counting the records does not work.** `InsertEdgeId`'s apply path carries
an idempotency guard that says why in its own comment (`db.rs:3502`): "prevents
double-counting when pre-snapshot WAL records are replayed over a V8 base."
Pre-snapshot records *are* replayed over a snapshot base, and that guard cannot
distinguish "already folded into the snapshot" from "a genuine second insert".
Counting records would silently drop increments.

**So the count must be written.** A new WAL discriminant — **23**, the next
available — carrying `(etype, src, dst, count)`. `docs/format-stability.md:108`
makes discriminants append-only and explicitly permits adding at the end, so
this is inside the format contract, not a violation of it.

**Multiplicity is opt-in per store, and that is what keeps the release
two-way** (§7 D8). `GraphDb::enable_multiplicity()` — persisted the way
`enable_index` already is — gates whether discriminant 23 is ever written. A
store that never enables it contains no record 0.6.9 cannot read and stays
readable by 0.6.9 forever. A store that enables it has made a one-way choice
**at the moment its operator asked for the feature**, not at the moment they
took a patch release.

This matters because an unreadable WAL record cannot degrade the way 0.6.9's
MHNS v4 blob does. An unreadable blob falls back to an exhaustive scan — slower,
never wrong. A reader meeting an unknown WAL discriminant cannot know what the
record would have changed, so it must refuse the open. Imposing that on every
store to serve a counter one caller already works around with a property write
is disproportionate; imposing it on stores whose operator asked for the counter
is not.

The CHANGELOG entry is therefore **Added**, not **BREAKING**, with the one-way
consequence stated inside it and repeated under known limits.

Contract:

- Reserved edge property `count`, absent meaning 1. Cypher `SET` on it is
  refused, as the other reserved names are.
- `degree(key, edge_type, direction, multiplicity: bool)` — **default false**,
  so every existing caller keeps unique-neighbour semantics. `degrees` takes the
  same argument.
- A duplicate insert increments the count and leaves unique degree unchanged.
  `insert_edge` still returns `Ok(false)`: its contract is "was this pair new",
  and that has not changed.
- `delete_edge` removes the pair **and** its count.
- CSR stays a set. No multi-edges, no snapshot-format change (V9 unchanged).
  **AMENDED, 2026-09-18 — see the amendment block at the end of this section.
  A store that opts in writes V10.**
- Unresolved NULL targets stay outside the readout, as they do today.
- **Composes with §5.4**: a scoped multiplicity count sums insert-counts of
  visible pairs only. An unscoped count leaking through a scoped handle is the
  same disclosure the degree filter exists to prevent.

Pin: `duplicate_insert_increments_count_not_unique_degree`,
`delete_edge_clears_multiplicity`, `multiplicity_survives_reopen` (snapshot
**and** WAL-replay paths, separately — the replay path is the one the design
argument above turns on), `cypher_set_on_count_is_refused`, and a compat test
that a 0.6.9 decoder refuses discriminant 23 rather than skipping it. The
existing `duplicate_edge_does_not_increase_degree` must stay green.

**AMENDMENT, 2026-09-18 — an opted-in store writes a V10 snapshot.** Shipped by
`f9d1033`; this block is the spec catching up with it, the way §5.3's history row
was caught up by defect #10.

The bullet above — "no snapshot-format change (V9 unchanged)" — was written
believing that gating discriminant 23 behind `enable_multiplicity()` was enough
to keep an opted-in store safe from an older binary. It is not, for the reason
the D8 `CORRECTION` block in §7 found: a 0.6.9 reader does not *refuse*
discriminant 23, it reads the WAL prefix before it, and with `repair_wal` (the
default) it persists that truncation. The opt-in gate keeps the record off
stores that never asked for it, but it does nothing for the store that did.

So the version stamp carries the announcement instead:

- `snapshot::VERSION_10` is V9's container with a different stamp — no new
  section, no new field (`v10_is_v9_with_a_different_stamp`,
  `crates/core-storage/src/snapshot.rs`). `snapshot::version_for(multiplicity)`
  decides per store; `snapshot::VERSION` stays `VERSION_9` and remains what a
  store that has opted in to nothing writes.
- `enable_multiplicity()` writes that snapshot **before** appending the
  declaration record, so no interruption point leaves the record on disk without
  the stamp that announces it (`enable_multiplicity_snapshots_immediately`,
  `no_crash_leaves_discriminant_23_unguarded`).
- The snapshot is read before the WAL, so a 0.6.9 binary stops at
  `snapshot: unsupported version 10` with the WAL byte-unchanged
  (`a_0_6_9_reader_refuses_a_v10_snapshot`, which carries a V9 control half
  proving the difference is the refusal and not an empty tail).

What this **does not** change: a store that never opts in still writes V9 and
still carries no discriminant-23 record (`a_store_that_never_opts_in_still_writes_v9`),
which is the whole property "opt-in" was bought for. The release is still
two-way for every store that did not ask for the counter.

## 7. Key decisions

**D1 — `db.scoped()` child handle, not scope-at-open and not per-call kwargs.**
*Assumed, not confirmed.* A sidecar serves many callers with different scopes
from one process; scope-at-open forces one `open()` per scope, and per-call
kwargs are the shape whose forget-one-call failure mode the note is complaining
about. The child handle is also the only option that makes the leak test above
expressible as "every method on this object", which is what makes the guarantee
checkable.

**D2 — a scoped handle is read-only.** *Assumed, not confirmed.* Writes raise
`MushroomReadOnly`, matching `query_masked`'s existing contract. Routing scoped
writes through the `RoleWriteDenied` decision table is a materially larger
spec and test matrix; the integration team dual-writes through an unscoped
handle and does not need it. Override this and Task 5 roughly doubles.

**D3 — base class + per-variant subclass + `.code` + attributes.** *Assumed,
not confirmed.* The load-bearing property is that `MushroomError` subclasses
`RuntimeError`, which makes the whole change non-breaking for callers currently
writing `except RuntimeError`. A flat HTTP-shaped set (NotFound / Conflict /
Invalid) loses the variant identity and forces a `.code` check anyway; classes
without a `RuntimeError` base break every existing caller.

**D4 — `on_conflict="replace"` is wholesale property replacement.** *Assumed,
not confirmed.* A mirror rebuild must be able to clear a field the source
dropped, which merge semantics cannot express. Merge is already available as
`upsert_node`, so the two policies stay distinct rather than duplicating. If
this is wrong, the fallback is shipping `"error" | "skip"` only — it solves the
note's stated problem (a second boot must not abort) with less semantics.

**D5 — no `max_distance` alias.** *Confirmed 2026-09-17: the requester withdrew
the ask.* Two spellings for one floor, where one is the complement of the
other, is a silent-failure generator: a caller who passes `0.35` to the wrong
one gets results, just the wrong ones. `distance = 1 - sim` stays documented in
one direction, and §5.11 puts it where it was missing.

**D6 — the RBAC contract moves into the engine.** The alternative — leaving
`http.rs` as the only correct implementation and writing a second one in the
binding — guarantees the two drift. Moving it down means HTTP's existing route
tests become the regression net for the engine method, which is why §4 requires
byte-identical responses.

**D7 — a query-defined scope is deferred, and this patch does not close the
requester's stated bottleneck.** Be honest about this in the reply, not only in
the spec.

The requester's access rule is a join — grants × visibility × tagged node —
not a field test. Three consequences:

1. `visible_where` cannot express it. It is a single `PropPredicate` (field
   plus `eq` / `in`) narrowing the label leg of a role
   (`crates/core-api/src/roles.rs:249`). Asking for "`visible_where` on the
   handle" would not have helped them even once delivered.
2. A `keys=` handle scope helps, but less than they expect. It collapses N
   per-call mask round-trips into one readable-set query per request, removes
   the leak, and makes the whole read surface usable — it does **not** remove
   the readable-set query itself. Their stated targets assume that query is
   gone.
3. What would remove it is a scope whose membership is computed inside the
   engine by a traversal — `db.scoped(query="MATCH …", params=…)`, resolved
   once per `commit_seq` like every other leg. Mechanically this is small: the
   engine already runs the query and already builds a `NodeMask` from a key
   list.

It is deferred anyway, on two unknowns that are theirs to answer and ours to
think through:

- **Is the grant topology mirrored into the graph at all?** If grants live only
  in a named system, no engine feature removes the readable-set query, and building
  one on the assumption would be speculative. Ask before specifying.
- **What is the invalidation cost under dual-write?** A scope cached on
  `commit_seq` re-evaluates after every commit. A sidecar that dual-writes on
  every mutation, serving many distinct per-user scopes, re-runs one ACL
  traversal per scope per write. That may be fine or may be a thundering herd;
  it needs a number before it becomes a contract, and an unbounded-cost ACL
  primitive is not something to add to a patch on assumption.

Promote to 0.6.11 when both are answered. Until then §5.2's `keys=` leg is the
supported shape and the spec says plainly what it does and does not buy.

**D8 — multiplicity is opt-in, so the release stays two-way.**
*Owner-approved 2026-09-17, revised the same day.* The first version of this
decision made 0.6.10 one-way for every store. That was the wrong trade and the
requester's own note says why: "We currently stash those counts as props." They
have a working shim. Making every user's store unreadable by 0.6.9 to spare one
caller a property write is disproportionate.

`enable_multiplicity()` gates the new WAL record. Opting in is a choice an
operator makes when they want the feature; taking a patch release is not. The
rest of this decision — why the record is needed at all, and why a snapshot-only
count is rejected — stands as written below.

The WAL discriminant §5.13 needs is permitted by
`docs/format-stability.md:108` — discriminants are append-only and new ones may
be added at the end — so this is the contract working as designed, not an
exception to it.

**CORRECTION, 2026-09-18, found while implementing Task 10 and verified
independently.** This decision said an older binary "must refuse the open" and
that the compat test should assert "a clean, named error". **That is wrong, and
wrong in the dangerous direction.**

`decode_all` (`crates/core-storage/src/wal.rs`) treats *any* undeserializable
frame as a corrupt tail — `Err(_) => return (recs, pos)` — and returns the valid
prefix. `GraphDb::open_with` replays that prefix and, when `repair_wal` is set,
**writes the truncation back to disk** (`db.rs:2448`). `repair_wal` defaults to
`true`.

So a 0.6.9 binary opening a multiplicity-enabled store does not refuse it. It
**silently discards every commit after the first discriminant-23 record and
persists that loss.** That is data loss on downgrade, not a read failure.

Three consequences:

1. The opt-in gate is load-bearing for **data integrity**, not merely
   readability. `multiplicity_off_writes_no_new_record` is protecting more than
   this decision assumed.
2. The CHANGELOG must say this plainly. "An older binary cannot read the store"
   understates it to the point of being misleading.
3. What *is* true, and what the compat test asserts, is the narrower claim: a
   0–22 decoder returns a clean named error rather than panicking or skipping
   the record and applying its neighbours. The store-level consequence —
   decoding stops before that frame — is asserted separately.

**AMENDMENT TO THE CORRECTION, 2026-09-18 (later the same day), shipped by
`f9d1033`. The truncation above is no longer reachable, and consequences 2 and 3
are superseded.** The correction was right about the mechanism and right that the
opt-in gate alone did not cover it. The fix is not to describe the truncation
better — it is to make an older binary stop before it can happen.

An opted-in store now writes a **V10 snapshot**, and `enable_multiplicity()`
writes it *before* appending the declaration record. The snapshot is read before
the WAL, so a 0.6.9 binary meets `snapshot: unsupported version 10` and stops
with the WAL byte-unchanged. It never reaches `decode_all`, so it never truncates
and never persists a truncation. See the amendment block at the end of §5.13 for
the mechanism and its pins.

What each consequence reads as now:

1. **Stands, and more strongly.** The gate still decides which stores take the
   one-way step at all, and it is now also what decides which stores get the V10
   stamp. `a_store_that_never_opts_in_still_writes_v9` is the pin.
2. **Superseded.** The CHANGELOG must *not* say a downgrade silently discards
   commits — that would now be false. What it must say is: an opted-in store is
   refused by name by every earlier binary, with nothing written; a store that
   never opted in is unaffected. **Task 12 should be pointed at `f9d1033`'s
   state, not at this block's original text.**
3. **Superseded as the store-level claim.** The record-level claim stands — a
   0–22 decoder still returns a clean named error for discriminant 23
   (`a_0_6_9_decoder_refuses_discriminant_23`) — but that decoder is no longer
   reached, because the snapshot refusal comes first. The test that carries the
   store-level claim is now `a_0_6_9_reader_refuses_a_v10_snapshot`.

What makes it heavier than 0.6.9's MHNS v4 step is the failure mode, and the
difference is worth stating plainly. An unreadable *blob* degrades: the reader
falls back to an exhaustive scan, slower and never wrong. An unreadable *WAL
record* cannot degrade, because the reader cannot know what the record would
have changed. It must refuse the open. So:

- The CHANGELOG carries a `#### BREAKING` section naming the one-way step.
- A store is only affected once it actually records a duplicate edge; a store
  that never does stays readable by 0.6.9.
- The compat test asserts the refusal is a clean, named error — not a silent
  skip, and not a panic.

The alternative — a count that lives only in snapshots — was rejected in 0.6.9
and stays rejected: it loses increments on a crash and would satisfy
`multiplicity_survives_reopen` only because the test snapshots first. A test
that passes for the wrong reason is worse than the feature being absent.
